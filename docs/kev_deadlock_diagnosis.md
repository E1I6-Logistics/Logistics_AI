# N5·N7·N9 정지 원인과 KEV 기반 복구 설계

분석일: 2026-10-26 (한국 시간). 첨부 이미지, 현재 코드, 실행 중인 백엔드의 읽기 전용 API 응답을 대조했다. `.agents/`는 비어 있었고 프로젝트 안에 `SKILL.md`나 `AGENTS.md`가 없어 추가 로컬 스킬은 적용하지 못했다. 문서의 설명은 참고 자료로 취급하고 실제 동작은 코드와 재현 결과로 확인했다.

## 1. 실제 정지 관계

`GET /api/mode`는 `simulation` / `ai`를 반환했다. `GET /api/robots`에서 세 로봇 모두 `WAITING`, `route_source=llm`, `departure_at=null`, 노드 위 정지 상태였다.

| 로봇 | 현재 점유 | 남은 경로 | 현재 경로를 막는 로봇 |
| --- | --- | --- | --- |
| R-01 | N5 | N5 → N7 → N11 → N3 | N7의 R-02 |
| R-02 | N7 | N7 → N9 → N1 | N9의 R-03 |
| R-03 | N9 | N9 → N7 → N11 → N6 | N7의 R-02 |

따라서 `R-01 → R-02 ↔ R-03`이다. R-02와 R-03이 맞교착이고 R-01은 그 뒤에서 막힌다. 사진의 색만 보고 추정한 결과가 아니라 API에서 확인한 노드·잔여 경로에 따른 판단이다. 최초로 정지를 일으킨 `SegmentPermission.reason`은 저장되지 않아, 최초 사건이 예약 시간 초과였는지 점유 충돌이었는지는 기존 로그만으로 확정할 수 없다. 현재 교착이 지속되는 원인은 확인할 수 있다.

## 2. 기다려도 풀리지 않는 코드상의 이유

### AI 경로 재생성과 예약 재시도가 연결되어 있지 않다

- `traffic_manager.py:358`: 대기로 전환할 때 실행 예약을 해제하고 경로 객체는 남겨 둔다.
- `traffic_manager.py:367`: `_try_schedule()`은 `_required_paths`의 같은 노드 순서를 `plan_timed(required_path=...)`에 다시 전달한다. 여기서 재계산되는 것은 주로 예약 시간이며 KEV 재질의가 아니다.
- 다른 정지 로봇의 점유는 비울 시각을 모르면 무한 점유로 취급한다. 서로가 움직여야 예약이 가능한 현재 경로는 계속 실패한다.
- `traffic_manager.py:491`: 일반 교착 해소는 `rid not in self._required_paths`인 로봇만 대상으로 삼는다. AI 고정 경로는 제외된다.
- `traffic_manager.py:672`: AI 고정 경로 전용 순환 처리는 `route is None`인 로봇만 대상으로 삼는다. 현재 세 로봇은 대기 중이지만 경로 객체가 남아 있어 이 분기에 들어가지 않는다. 이 함수도 새 우회 경로를 만들지는 않는다.

**현재 경로로 안전하게 움직일 수 없어서 정지하는 것은 맞지만, 정지 후 다른 경로를 요청하는 복구 흐름이 없다.**

### KEV-MAPF를 활성화하는 것만으로 해결되지 않는다

- `routers/commands.py:106`: 수동 AI 목적지 이동은 `preview_llm_route()`를 `traffic` 없이 호출하고 바로 고정 경로를 전달한다. 주문용 MAPF 게이트를 거치지 않는다.
- `order_route_dispatcher.py:34`: 주문 이동에서만 `FMS_SIM_MAPF_ENABLED=1` 조건으로 MAPF 배차 게이트에 들어간다.
- `kev_coordinator.py:451`: 이미 Active인 로봇에 대한 WAIT/HOLD/REROUTE 결정은 `ACTIVE_ROBOT_ACTION_REQUIRES_STOP`으로 거부된다. 정지 확인 뒤 현재 작업을 유지하며 경로를 교체하는 절차가 필요하다.
- `kev_engine.py:163`: `_reroute()`는 충돌 구역과 타 로봇 목적지 등을 제외하지만, 양보 로봇 한 대의 현재 위치에서 원래 목적지까지 우회하는 형태다. 통로를 비우기 위한 임시 대피와 작업 재개를 별도로 표현하지 않는다.

### 현재의 트래픽 정보도 절대 제약은 아니다

`iterative_route_policy.py:127`의 `_apply_traffic()`은 점유 회피 후보가 하나도 없으면 원래 후보를 다시 사용한다. `TRAFFIC_INSTRUCTIONS`도 총거리 최소화를 먼저 두고 비슷한 후보에서 공유가 적은 쪽을 선호한다. 트래픽 정보를 전달하는 개선은 필요하지만, 그 자체로 교착 방지를 보장하지 않는다.

## 3. 실제 재현과 복구 검증

운영 서버에는 이동·정지·취소 명령을 보내지 않았다. API 스냅샷을 복사한 별도 프로세스에서 검사했다. 결과와 입력은 `kev_deadlock_probe_evidence.json`에 저장했다.

1. 현재 잔여 고정 경로와 대기 상태를 복원해 0.2초 간격으로 600회 예약 재시도를 실행했다. 가상 시간 120초 뒤에도 상태가 같았고 예약은 0개였다.
2. R-03에 대해 현재 그래프와 다른 로봇 점유 N5·N7을 `traffic`으로 전달해 기존 `preview_llm_route(selector="kev", model="kev-08b")`를 호출했다.
3. 결과는 **N9 → N10 → N8 → N12 → N11 → N6**이었다. N10·N8·N12는 첨부 이미지의 잘린 위쪽에 있으며 실제 그래프에 존재한다. 유향 간선과 출발·도착을 `Graph.check_path()`로 검증했다.
4. 이 우회 경로, 실제 대기 관계, 원래 경로 유지라는 두 선택지를 진단용 KEV `choice` 요청에 제공했다. 실행 중인 `kev-08b`가 `reroute_robot3`를 선택했다. 이는 제안 경로가 주어진 1회 진단이며 운영 복구 기능이 이미 구현되었다는 의미는 아니다.
5. 복사본에서 R-03의 고정 경로만 교체하고 기존 예약·주행기를 실행하자 세 로봇 모두 목적지에 도착했다.

| 로봇 | 최종 위치 | 복구 시작 후 시뮬레이션 완료 시점 |
| --- | --- | --- |
| R-02 | N1 | 4.9초 |
| R-01 | N3 | 6.5초 |
| R-03 | N6 | 11.6초 |

복구의 의미는 R-03이 N9를 비워 R-02가 N7에서 빠져나갈 수 있게 만드는 것이다. R-01과 R-02의 경로는 그대로 두었다. 세 대를 전부 다시 계획할 필요는 없었다. 0.1초 간격 샘플의 최소 중심 거리는 약 0.1362m였다. 이는 해당 시뮬레이터와 현재 0.12m 간격 제한에 대한 결과이며 실제 로봇의 물리 안전 검증을 대체하지 않는다. 완료 시간은 재현 결과이며 KEV가 예측한 ETA가 아니다.

**추론 구분:** 우회 경로 생성 단계의 `calls`는 0이었다. 현재 후보 필터 뒤 매 단계의 합법적 다음 노드가 하나씩만 남아 강제 진행했기 때문이다. 실제 모델 추론은 별도의 복구 행동 `choice` 1회였다. 따라서 이 실험을 “KEV가 모든 노드를 추론해 경로를 만들었다”고 표현하면 부정확하다.

## 4. 요청한 KEV 중심 해결 방식

권장 흐름은 다음과 같다.

`점유·진행 상태 수집 → 막힘 관계 전달 → KEV가 복구 대상과 행동 선택 → KEV 경로 제공자로 재경로 요청 → 경로·예약 검증 → 정지 확인 상태에서 경로 교체 → 점유 해제에 따라 재개`

KEV가 누구를 우회시킬지, 대기·재경로·임시 대피 중 무엇을 할지 결정하도록 한다. 일반 교착 해소기의 최초 접수순·최단 대피 경로 선택으로 대신 처리하는 방식은 요청 취지에 맞지 않는다. 그래프 연결성, 현재 점유, 충돌, 예약, 실제 정지 여부를 코드가 검사하는 것은 실행 검증 역할로 유지해야 한다.

발생 전 예방도 가능하다. 저장된 경로의 출발점처럼 R-03이 아직 N2에 있다면, KEV가 R-02 우선 통과와 R-03의 N2 대기를 선택하는 계획은 N9를 비워 두어 맞교착을 막는다. 반대로 R-03을 N9까지 진입시킨 뒤 WAIT시키면 R-02의 통로를 막는다. 이는 유효한 예방 계획의 예시이며 로봇 번호별 우선순위를 하드코딩하자는 의미는 아니다. 이미 N9에 있는 현재 상태에서는 N2에 있는 것으로 처리할 수 없으므로 검증된 우회 또는 실제 대피 이동이 필요하다.

### 구현 우선순위

1. **수동 목적지 이동과 주문 이동을 같은 KEV 조정 입구로 통합한다.** 수동 이동에도 `live_traffic()`을 전달하고, 출발 전 모든 관련 로봇의 점유와 잔여 경로를 함께 검토한다. 설정 하나로 주문과 수동 이동이 서로 다른 정책을 쓰지 않게 한다.
2. **대기 이유와 진행 변화를 기록한다.** `blocking_robot_id`, `blocked_resource`, `last_progress_at`, `navigation_id`, 잔여 경로를 저장한다. 진입 실패 때마다 KEV를 반복 호출하지 말고, 지속적인 상호 차단이나 상태 변화 없는 대기를 복구 요청으로 올린다. 단순 예약 지연과 구조적 교착을 구분한다.
3. **KEV 복구 행동에 재경로와 임시 대피를 제공한다.** 현재 사례에서는 R-03 재경로가 유효하다. 일반 상황에서는 양보 로봇을 잠시 통로 밖으로 이동시키고 원래 작업을 재개하는 `MOVE_ASIDE` 같은 행동도 필요하다. 타 로봇이 비워야 하는 노드에서 계속 WAIT하는 결정을 실행 검증에서 반려하고 KEV에 구체적인 반려 사유를 전달한다.
4. **현재 작업을 보존하는 경로 교체 API를 만든다.** 기존 `request_navigation_after_stop(required_path=...)`는 IDLE만 허용한다. 별도 `replace_required_path_after_stop` 형태의 API에서 목적지·주문 단계·취소 토큰을 보존하고 새 경로와 예약을 함께 검증·반영해야 한다. 정지 확인 이전에 점유를 해제하거나 좌표를 변경하면 안 된다.
5. **추론은 잠금 밖에서, 반영은 최신 상태 재확인 후 수행한다.** 그래프 버전, 각 로봇의 점유, 목표, `navigation_id`를 스냅샷으로 만들고 추론 후 다시 비교한다. 달라진 결과는 폐기한다. 간선 중간 정지는 출발 노드 위 정지로 간주하지 않는다.
6. **KEV 실패 시 자동 알고리즘 대체를 끈다.** `kev_client.py:222`에는 A* 경로 대체가 있고 `:184`에는 첫 후보 선택 대체가 있다. 점수 오류도 기본 작업 우선순위로 대체한다. KEV 의사결정이 필수인 모드에서는 이런 대체를 명시적 실패/보류로 바꾸고 재질의해야 한다. 모델 실패를 KEV 성공으로 기록하지 않는다.

프롬프트에도 “거리보다 교착 해소와 실제 진행 가능성을 먼저 고려”, “다른 로봇이 통과해야 하는 점유 노드에서 WAIT하지 않기”, “우회 실패 근거를 받은 뒤 다른 로봇/대피 행동 선택”을 반영한다. 프롬프트만 변경하면 실행기 경로 교체 제약은 그대로 남으므로 위 연결 작업이 함께 필요하다.

## 5. 추가로 발견한 MAPF 오류

현재 스냅샷의 잔여 경로를 기존 `KevMAPF`에 넣고 실제 점유도 전달한 오프라인 검사에서 `KeyError: 'yield_robot'`를 재현했다. 모델 대역은 정책 분기를 실행하기 위한 것이며 실제 KEV 판단 검증으로 취급하지 않았다.

`kev_engine.py`의 일부 HOLD 분기에는 `yield_robot`가 없는데 반환 결과를 만들 때 `:593`에서 모든 WAIT/HOLD에 `d["yield_robot"]`를 요구한다. 점유 차단이나 우선순위 순환을 만나는 실제 경로에서도 발생한다. 이 오류가 현재 운영 정지의 최초 원인이었다는 증거는 없지만, 복구 기능을 기존 엔진에 연결하기 전에 HOLD 결과 스키마를 일관되게 고쳐야 한다.

초기 분석에서는 애플리케이션 제어 코드나 실행 중인 로봇 상태를 변경하지 않았다. 아래는 후속 코드 변경 결과다.

## 6. 후속 구현 및 검증

- `kev_mapf/kev_recovery.py`: 시뮬레이션에서 점유로 막힌 KEV 경로가 1초 동안 변하지 않으면 복구를 검토한다. 관련 로봇의 KEV 우회 후보를 읽기 전용으로 생성·검증하고, 실패 근거와 유효 경로를 KEV choice에 제공한다. 실제 행동은 KEV가 선택한다. 실패 또는 WAIT 결과에서는 기존 경로와 점유를 유지하고 5초 간격으로 재검토한다.
- 복구 경로에서는 다른 로봇의 현재 점유 노드 및 점유 간선 양 끝점을 가상 그래프에서 제거한다. 초기 경로의 소프트 트래픽 후보 복구와 달리 점유 노드를 다시 허용하지 않는다.
- `main.py`: 모델 추론을 시뮬레이션/텔레메트리 루프와 별도의 비동기 작업에 연결했다. 서버 종료 시 복구 작업을 취소한다.
- `traffic_manager.py`: 노드 위 대기 상태에서 기존 작업 ID·목적지·우선순위를 보존하며 고정 경로와 예약을 교체한다. 먼저 사본에서 예약하며 실패 시 기존 상태를 유지한다.
- 수동 AI 목적지 이동에도 트래픽 컨텍스트를 전달하고 활성 경로를 코디네이터에 등록한다. 주문 이동과 같은 복구 작업이 처리한다. 수동 이동을 기존 주문용 MAPF 배차 게이트로 보내는 변경은 하지 않았다.
- 추론 이후 로봇 상태·고정 경로·등록 요청·보호 자원을 다시 대조하고 지도 및 모드 변경 결과도 폐기한다.
- `LiveKEV`의 A* 경로 대체, 첫 후보 대체, 작업 우선순위 점수 대체를 제거했다. 구역 HOLD의 `yield_robot` 누락으로 발생하던 예외도 수정했다.

초기 자동 복구는 시뮬레이션에서 노드 위에 대기 중인 KEV 요청의 우회만 지원했다. 임시 대피 후 작업 재개와 KEV 판단 범위 확대는 아래 후속 수정에 추가했다. 실제 로봇과 간선 중간 정지는 여전히 자동 교체 범위 밖이다.

검증:

- 관련 테스트 75개 통과. 새 테스트는 사진의 맞교착 복구, 작업 보존, 실패 시 무변경, 추론 중 정지·지도·모드 변경, 위험 경로 거부, KEV 오류 시 알고리즘 대체 금지 등을 확인한다.
- 실제 실행 중인 `kev-08b`를 사용한 독립된 시뮬레이션에서도 KEV가 R-03 재경로를 선택하고 세 대가 각각 N3·N1·N6에 도착했다. 운영 서버의 로봇에는 명령을 보내지 않았다.
- 전체 테스트에서 실패 3개와 오류 4개가 확인되었다. HEAD의 변경 전 소스를 임시 디렉터리에서 같은 환경변수로 실행했을 때도 동일한 항목이 실패했다. 기존 경로 벤치마크의 그래프/후보 기대값 문제이며 이번 변경의 회귀는 아니다.

코드 적용에는 백엔드 재시작이 필요하다. 실행 중인 서버는 재시작하지 않았다.

## 7. 두 번째 사진과 KEV가 모든 복구 행동을 선택하는 후속 수정

두 번째 사진의 실시간 API 상태는 R-01 N8→N6, R-02 N9→N5, R-03 N7→N2였다. R-02와 R-03의 원래 목적지까지 다른 현재 점유를 모두 피하는 우회가 없었다. 이전 구현에는 MOVE_ASIDE가 없어 이 경우를 해결하지 못했다.

후속 구현은 다음과 같다.

- KEV에게 모든 관련 로봇의 현재 점유, 원래 목적지, 남은 경로, 이전 결정, 합법적인 로봇/노드 이동 선택지를 제공한다. KEV choice 하나가 로봇·행동·임시 대피 노드 또는 재개 경로를 선택한다.
- 코드가 대피 후 다른 로봇의 길이 열리는지를 계산해 후보를 추리는 규칙과 복구 로봇 우선순위 규칙을 제거했다. 이동이 합법적이면 후속 로봇의 후보도 KEV에 제공한다. 재개를 코드가 자동 우선 선택하지 않는다.
- KEV 프롬프트가 상호 차단 관계, 어떤 점유를 해제해야 하는지, 불필요한 이동을 피할지, 대피 후 언제 원래 작업을 재개할지 판단하도록 한다. 합법적인 선택이 비효율적이어도 코드는 임의의 다른 로봇 행동으로 바꾸지 않는다.
- FMS에는 물리적 점유, 유향 간선, 예약, 정지 확인, 최신 요청 일치 검사와 실행 상태 관리가 남는다. 재개 경로도 기존 KEV 경로 제공자로 생성한다. 모델 실패 시 알고리즘 경로로 대체하지 않는다.
- 임시 대피 지점은 현재 한 간선으로 연결된 빈 대기/통과 노드를 제공한다. 임시 목적지와 업무 목적지를 구분하고 작업 ID·업무 목적지를 보존한다. 대피 도착 후에는 KEV의 RESUME 선택을 기다린다. 취소된 작업은 재개하지 않는다.
- 예약 시간 갱신은 물리적 진행으로 취급하지 않도록 정체 감지와 추론 후 일치 검사를 보완했다. 반영할 때는 최신 예약표를 다시 검사한다. 미예약 로봇의 가상 다음 노드 때문에 예약된 로봇이 무한 양보하던 실행기 문제도 수정했다.

실제 `kev-08b`를 연결한 `tools/verify_kev_recovery.py` 검증 결과:

| 입력 배치 | 결과 | 시뮬레이션 경과 | KEV 복구 선택 횟수 |
| --- | --- | --- | --- |
| 첫 사진 N5·N7·N9 | 세 대 모두 원래 목적지 도착 | 12.8초 | 1 |
| 두 번째 사진 N8·N9·N7 | 세 대 모두 원래 목적지 도착 | 29.1초 | 4 |
| 추가 3대 순환 교착 | 세 대 모두 원래 목적지 도착 | 14.2초 | 2 |

위 시간은 검증용 가상 시계의 경과이며 실제 모델 추론 시간이나 운영 처리 시간을 예측한 수치가 아니다. 두 번째 배치에서는 KEV가 R-03 대피, R-01 추가 대피, R-03 재개, R-01 재개를 선택했다. 가장 짧은 해결 순서를 코드가 강제하지 않았기 때문에 추가 이동이 포함된다. 테스트 배치의 통과가 모든 그래프에서 교착 해소나 최적성을 보장하지는 않는다.

입력 상태, 선택지, 프롬프트, 실제 KEV 선택과 최종 위치는 `kev_prompt_validation.json`에 저장했다. 관련 자동 테스트는 84개가 통과했다. 대피 상태 보존, KEV가 후속 로봇을 선택할 때 코드가 덮어쓰지 않음, 예약 갱신 중 정체 감지 및 추론 반영, 취소 후 재개 금지를 확인한다.
