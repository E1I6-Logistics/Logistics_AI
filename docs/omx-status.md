# OMX 상태·팔레트 관측 및 서비스 재시작

지도에서 **OMX 아이콘**을 누르면 우측 상태 패널이 열립니다. 로봇을 다시 선택하면 기존 로봇 제어 화면으로 돌아갑니다.

- OMX1: A/B 팔레트, OMX2: C/D 팔레트의 `물건 있음 / 비어 있음 / 확인 불가` 표시.
- OMX3·4: 하차 장비 상태·작업 진행 표시. 팔레트 검사는 적용하지 않습니다.
- `connected`는 MQTT 장치 통신 여부입니다. `ERROR / RECOVERY_WAIT`도 통신 자체는 연결된 상태일 수 있습니다.
- 동작 횟수(`motion_cycles`)는 물건 전달 성공 개수와 다릅니다.
- 팔레트 결과는 **관측용**입니다. 기존 주문 수량·배차·AI/알고리즘 모드 정책을 변경하지 않습니다.

## 적용

FMS에서 현재 `ugie-dev-merge` 브랜치의 변경을 받은 뒤 백엔드와 프론트엔드를 기존 방법으로 다시 실행합니다.
기존 실행 방법은 [README](../README.md)를 참고하세요. 구버전 백엔드와 신버전 프론트엔드는 함께 사용하지 마세요.

OMX1·2의 기존 `omx_stock` 기능이 켜져 있고 실제 빈 팔레트 기준과 ROI가 등록되어 있어야 합니다.
이 기능을 위해 모델·팔레트 기준을 다시 등록할 필요는 없습니다.

```bash
# 각 OMX1·2 Pi에서 관측 상태 확인
omx_stock status --json
```

OMX가 `omx1/stock`, `omx2/stock`으로 발행한 기존 메시지를 FMS에서 수신합니다.
팔레트 프레임의 `observed_at`과 `valid_for_s`를 검사하며, heartbeat가 계속 와도 오래된 프레임의 수명은 연장하지 않습니다.
장치 단절·재연결·작업 시작 시 이전 관측은 해제합니다. 보존 MQTT 메시지(retain), 다른 장치 ID, 잘못된 스키마·품목·시간은 사용하지 않습니다.
Pi와 FMS의 시스템 시간이 크게 다르면 확인 불가가 되므로 시간을 동기화하세요.

```bash
# FMS에서 상태 API 확인
curl http://127.0.0.1:8000/api/omx
```

응답에는 기존 지도 좌표와 함께 `state`, `detail`, `last_seen`, `job_id`, `current_count`, `total_count`, `stock`이 포함됩니다.
아직 메시지를 받지 못한 장비도 연결 끊김 상태로 4대 모두 표시합니다.

## 선택 기능: OMX 서비스 재시작

**Pi OS 재부팅이 아니라 `omx-manager@omxN.service` 프로그램 재시작입니다.**
현재 OMX에는 MQTT 관리 명령 수신기가 없어서, FMS 서버에서 SSH로 고정된 사용자 서비스 명령만 실행합니다.
작업 진행·접수 대기·미완료 FMS 명령이 있으면 HTTP 409로 거절하고, 재시작 처리 중 새 주문 전송도 차단합니다.
확인 버튼을 누른 요청만 실행하며 SSH 실패·응답 시간 초과를 자동 재시도하지 않습니다.
응답 성공은 재시작 요청 처리 성공이며 홈 복귀·모델 준비 성공을 뜻하지 않습니다. 이후 상태가 `IDLE/READY`로 돌아오는지 확인하세요.

1. **FMS를 실행하는 사용자 계정**에서 각 Pi에 SSH 키로 접속할 수 있게 준비하고, 실제 장비의 호스트키를 확인·등록합니다.
2. Pi 사용자 서비스 등록·부팅 자동 실행 설정을 유지합니다. `sudo` 비밀번호 입력은 사용하지 않습니다.
3. FMS 환경 파일에 재시작을 허용할 장비만 등록한 뒤 백엔드를 다시 시작합니다.

```dotenv
FMS_OMX_SSH_TARGETS={"omx1":"omx01@192.168.0.151","omx2":"omx02@192.168.0.152","omx3":"omx03@192.168.0.153","omx4":"omx4@192.168.0.154"}
```

주소·사용자 이름은 실제 장비에 맞게 수정하세요. 기본값 `{}`에서는 모든 재시작 버튼이 비활성화됩니다.
SSH 호스트키 검증을 생략하거나 비밀번호를 환경 파일에 저장하지 않습니다.

실제 로봇 모드에서 OMX 상세 패널의 **OMX 서비스 재시작**을 누르고 확인합니다.
직접 호출할 경우:

```bash
curl -X POST http://127.0.0.1:8000/api/omx/omx1/restart \
  -H 'Content-Type: application/json' -d '{"confirm":true}'
```

정상 종료·자원 반납·홈 복귀·중단 작업 보관은 기존 Pi OMX 관리 프로그램이 수행합니다.
FMS는 작업 기록을 삭제하거나 홈 위치·모터 설정을 변경하지 않습니다.
SSH 작업이 최대 65초 걸릴 수 있으며, 실패하면 오류 내용을 보여주고 장치 상태를 계속 조회합니다.

## 현장 확인 순서

1. OMX1·2에서 팔레트에 물건을 넣고 뺀 뒤 기존 관측 주기(기본 5초×3회) 동안 기다립니다. FMS 표시와 `omx_stock status --json`을 비교하세요.
2. OMX 하나의 서비스를 멈추면 연결 끊김·팔레트 확인 불가로 바뀌고, 다시 켜면 새 관측으로 복구하는지 확인합니다.
3. 기존 주문을 1회 실행하여 기존 로봇·픽업·하차 진행이 유지되는지 확인합니다.
4. SSH 설정을 마쳤다면 대기 중에만 재시작을 시험하고, 작업 중 요청은 거절되는지 확인합니다.

## 개발 검증

`tests/test_omx_status.py`는 모의 MQTT 메시지와 모의 SSH만 사용합니다. 실제 Pi·브로커에는 접속하지 않습니다.
기존 도킹 MQTT·주문·모드 분리·충전 회귀 테스트와 함께 확인했습니다.


## OMX1~4 SSH 간편 설정

**FMS를 실행하는 리눅스 PC에서, FMS 실행 사용자 계정으로** 실행하세요. Windows 노트북이나 Pi에서 실행하는 명령이 아닙니다.

```bash
cd ~/AX_Logistics
git pull --ff-only origin ugie-dev-merge
bash scripts/setup_omx_ssh.sh
```

다음 순서로 접속합니다. 각 장비의 호스트키를 확인하고 로그인 비밀번호를 직접 입력하세요.

| OMX | SSH 계정·주소 |
| --- | --- |
| OMX1 | `omx01@192.168.0.151` |
| OMX2 | `omx02@192.168.0.152` |
| OMX3 | `omx03@192.168.0.153` |
| OMX4 | `omx4@192.168.0.154` |

도우미는 기존 사용자 키를 덮어쓰지 않고 `~/.ssh/fms_omx_ed25519` 전용 키를 사용합니다.
4대 접속과 사용자 서비스 환경을 확인한 다음 `.env`에 주소와 `FMS_OMX_SSH_IDENTITY` 키 경로만 저장합니다.
비밀번호는 파일에 저장하지 않습니다. Pi의 모터·모델·실행 상태는 변경하지 않습니다.

코드 업데이트를 처음 적용할 때는 터미널에서 한 번 재시작하세요.

```bash
./stop_fms.sh
unset FMS_OMX_SSH_TARGETS FMS_OMX_SSH_IDENTITY
./start_fms.sh
```

이후 OMX 아이콘 → **OMX 서비스 재시작**을 사용할 수 있습니다.
Pi OS 재부팅이 아니라 해당 OMX 사용자 프로그램을 재시작합니다. OMX 단독 재시작은 기존처럼 작업 중 거절합니다.

## 웹에서 전체 FMS 종료 후 자동 시작

상단 **FMS 전체 재시작** → **전체 종료 후 재시작**을 누릅니다.

- **작업 중이어도 차단하지 않습니다.** 실제 `stop_fms.sh` → `start_fms.sh` 순서로 전체 FMS를 다시 시작합니다.
- 백엔드·프론트엔드·Zenoh 브리지·MQTT/Zenoh 컨테이너·Kev 등 기존 스크립트가 관리하는 대상이 모두 포함됩니다.
- 메모리에 있는 주문·운영 상태는 기존 수동 stop/start처럼 초기화될 수 있습니다. Pi OS나 OMX 서비스를 직접 재부팅하는 명령은 아닙니다.
- 자기 자신이 종료돼도 재시작 절차가 죽지 않도록 분리된 프로세스가 시작을 이어받습니다.
- 중복 클릭은 거절하고, 종료 중 화면을 유지하며 새 백엔드 인스턴스와 전체 시작 완료를 확인한 뒤 자동 새로고침합니다.
- 현재 `.env` 설정을 다시 읽습니다. 개발 서버가 스스로 종료돼도 복구 화면은 브라우저에 남고 수동 새로고침 때도 대기 상태를 이어받습니다.
- 요청 가능한 환경은 기존 `start_fms.sh`로 시작된 FMS입니다. 버튼이 비활성이면 먼저 이 스크립트로 실행하세요.
- 웹 실행에는 터미널 비밀번호 입력이 불가능합니다. FMS 사용자에게 기존 Docker·ROS·Node 실행 권한과 환경이 준비돼 있어야 합니다.

실제 종료를 수행하는 API:

```bash
curl -X POST http://127.0.0.1:8000/api/system/web/restart \
  -H 'Content-Type: application/json' -d '{"confirm":true}'
```

실패하면 자동으로 무한 재시도하지 않고 기록을 남깁니다. FMS PC에서 확인하세요.

```bash
cd ~/AX_Logistics
tail -n 100 logs/web_restart.log
cat logs/web_restart.json
# 원인을 해결한 뒤 수동 시작
./start_fms.sh
```

개발 검증은 임시 가짜 stop/start 스크립트와 모의 SSH로 수행했습니다. 실제 서비스와 Pi는 종료하지 않았습니다.
