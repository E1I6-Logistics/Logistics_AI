## 화면

- **시험**: D01~D06 선택, 대상·수량 설정, 실행 확인, 현재 장비/주문/집기대·작업대 점유, 지도·경로 펼쳐 보기.
- **통신·속도**: 기존 API의 응답 헤더까지 소요 시간, 성공/실패, WS 수신량, REST 로봇 수신 간격, 위치 기반 추정 속도·각속도.
- **실행 기록**: 이 브라우저 세션의 최근 20건, 각 최대 160개 상태 변경. 교통 시험은 기존 서버 기록 링크 제공.
- **관측 기록 다운로드**: 현재 화면의 상태·통신·시험 내역 JSON. 서버가 보증하는 영구 데모 기록이나 실물 전달 성공 증명은 아닙니다.
- 주문 입력은 기본 접힘. 오른쪽 패널 경계선을 좌우 드래그하거나 경계선에 포커스 후 ←/→로 너비를 조절합니다. 아래 주문 현황의 기존 높이 조절은 유지됩니다.

화면/하위 탭 이동은 실행을 취소하지 않습니다. 새로고침·브라우저 닫기도 로봇 정지가 아닙니다. 통합 관제와 데모는 기존 로봇·주문·OMX·시나리오 조회를 공유하고, 별도 ROS/MQTT/카메라 구독을 만들지 않습니다.

## 항목별 사용

| 항목 | 선택·실행 | 기존 API와 확인 기준 |
|---|---|---|
| D01 주문 전체 흐름 | A/B/C/D 합계 1~5개 → 실행 확인 | POST/GET/DELETE `/api/orders`. AMR은 기존 배차기가 선택. **status=COMPLETED와 phase=COMPLETED 모두 확인**해야 전체 완료. 하차 후 RETURNING이면 아직 진행 중 |
| D02 교통 제어 | 교통 상황 선택 → 시작 배치 확인 → 실행 | `/api/scenarios`의 기존 run/status/stop/records. 현재 알고리즘/AI에 맞는 기존 시나리오 사용. 시작 위치·그래프·연결·점유는 기존 서버가 검사 |
| D03 AMR 단독 이동 | robot1~3 + 유효 노드 → 실행 | POST `/api/command/goal-node`. 이동 상태를 관측한 뒤 목표 노드·빈 경로·IDLE을 서로 다른 REST 수신에서 연속 확인. 독립 Action 결과는 API 미제공 |
| D04 OMX 관측·관리 | omx1~4 선택 | GET `/api/omx`. 상태·작업 ID·사이클/진행 수량·A/B/C/D 팔레트 관측. 기존 `/api/omx/{id}/restart`로 서비스 재시작, 실제 모드 및 기존 서버 제약 유지 |
| D05 마커 이동·정렬 | robot1~3 + 목표 마커 선택 → 실행 | 실제 모드: 기존 goal-node → AMR 자동 정렬 → IDLE 상태 관측. 시뮬레이션은 노드 이동만 확인하며 실제 인식·정렬 성공을 주장하지 않음 |
| D06 충전 도킹 | robot1~3 선택 → 충전소 이동 확인 | 실제 모드만 POST `/api/command/charging`. 접점 검증 ON 필요. 목표 노드·CHARGING·기존 docking_complete·신선한 접점 상태를 연속 확인. 충전 전류는 미제공 |

D02는 기존 전용 `test.geojson`과 같은 그래프가 필요합니다. 실제 로봇은 카드의 시작 노드에 현장에서 배치합니다. 프런트엔드가 실제 좌표를 옮기거나 여러 임의 주행 명령으로 시작 위치를 강제하지 않습니다. 교통 시험의 AI 모델은 기존 서버 시나리오 설정을 따르며 화면의 개별 이동용 모델 선택과 다를 수 있습니다.

마커 매핑: **N5→24, N6→25, N4→26, N3→27**. 충전 노드: **robot1→N0, robot2→N1, robot3→N2**. 충전소 번호는 기존 도킹 API의 로봇 매핑을 우선합니다.

### 현재 API가 없는 기능

백엔드 추가·수정 금지 조건에 따라 다음은 제한 이유와 비활성 버튼을 표시합니다.

- AMR 없이 웹에서 OMX 단독 집기·하차 전송. 기존 주문용 MQTT 콜백을 우회하거나 덮어쓰지 않습니다.
- 현재 위치에서 ArUco **정렬만** 재실행. 같은 노드 이동을 정렬 전용 명령으로 위장하지 않습니다.
- 실제 검출 마커 ID, 정렬 오차, ROS Action feedback의 속도 명령, 전체 예약 테이블은 서버가 노출하지 않아 생성하거나 추정해 표시하지 않습니다.
- Pi 자체 재부팅. 기존 OMX 서비스 재시작과 FMS 전체 재시작만 사용합니다.

## 실행 중 취소

- **실행 준비 취소**: 조건 조회 중 취소. 현재 조회가 끝난 뒤 동작 명령 없이 종료합니다.
- **이 실행 취소**: D01은 이 화면이 접수한 주문 ID, D02는 같은 서버 시나리오 실행 ID만 취소합니다. 다른 시나리오로 바뀌면 그 실행을 중지하지 않습니다.
- 접수 응답 대기 중에도 취소 요청이 가능합니다. 주문 ID를 아직 받지 못했으면 고유 주문명으로 확인하고, 접수 응답이 늦게 오면 해당 작업에 취소를 적용합니다. 시나리오는 자기 실행 ID를 받은 뒤 취소합니다.
- D03/D05/D06의 **이동 취소·정지**는 기존 `/api/command/stop`을 사용합니다. **AMR 비상정지 상태가 되므로 이후 해제가 필요**합니다. 일반 취소 전용 API가 없다는 점을 확인창에 표시합니다.
- D01에서 물품 처리는 완료됐지만 AMR이 복귀 중이면 기존 주문 DELETE로 정지되지 않습니다. 이 경우 같은 주문에 배정된 AMR을 기존 비상정지 API로 멈춥니다. 확인창에 이 차이를 안내합니다.
- 취소 버튼을 눌렀다는 이유로 즉시 완료 처리하지 않습니다. 취소 후 복귀가 남으면 계속 추적하고, 서버 종료·로봇 정지 상태를 확인합니다. 결과가 불명확하면 취소 재확인 및 AMR 전체 비상정지를 사용할 수 있습니다.
- **AMR 전체 비상정지**는 모든 데모 상태와 무관하게 접근 가능합니다. OMX 물리 정지까지 수행하는 명령은 아닙니다.

## 상태가 불명확할 때

1. 진행 상태·현재 로봇·서버 ID·오류 메시지를 먼저 확인합니다. 통신이 끊겨도 같은 동작을 자동 재전송하지 않습니다.
2. 주문/교통 시험은 같은 서버 ID를 조회합니다. 개별 이동에는 고유 서버 작업 ID가 없어 새로고침 후 `상태 확인 필요`로 둡니다.
3. FMS 인스턴스 또는 운영 모드가 바뀌면 이전 실행을 완료로 추정하지 않습니다. 개별 이동에서 3분 동안 완료를 확인하지 못한 경우도 관측을 보류하고 실제 동작은 자동 재실행하지 않습니다.
4. `상태 확인 후 기록 닫기`는 **브라우저 기록만** 닫습니다. 실제 작업 취소·재고 삭제·복구 승인 기능이 아닙니다.
5. 필요하면 **FMS 재시작 확인**을 누릅니다. 기존 전체 종료→시작 확인창을 엽니다. 자동 재부팅하지 않습니다. 실제 주문/메모리 상태가 초기화될 수 있습니다.

여러 브라우저·사용자 사이의 원자적 데모 잠금, 재시작 후 영구 실행 엔진은 기존 API에 없습니다. 전송 직전 최신 모드/주문/시나리오/로봇/연결을 다시 확인하지만 다른 클라이언트와의 동시 요청을 서버 확장 없이 완전히 봉쇄할 수는 없습니다. 한 작업자가 데모 명령을 실행하고 기존 서버 인터록을 유지하세요.

## 통신 값 읽는 법

- HTTP 시간은 브라우저 요청부터 응답 헤더까지이며 서버 처리 시간을 포함합니다. 단방향 네트워크 지연이나 로봇 제어 지연과 같지 않습니다.
- REST 수신 간격은 보통 기존 로봇 조회 주기 약 2초입니다. ROS 센서 발행 주파수를 뜻하지 않습니다. 6초 이상 수신이 없으면 현재 속도는 표시하지 않습니다.
- 추정 선속도/각속도는 기존 위치·방향 차이를 시간 차이로 나눕니다. 원본 시각이 있으면 사용하고, 없으면 수신 시각을 사용했다고 표시합니다. 시간 중복/역전, 긴 공백, 위치 순간 이동은 제외합니다.
- 실제 모드 WS는 초기 스냅샷 뒤 메시지가 적을 수 있습니다. 소켓 연결과 REST 상태 수신을 별도로 표시합니다.
- HTTP/WS 버퍼 각각 최대 120건, UI 갱신 1초. 통신 표시를 위해 새 네트워크 폴링을 추가하지 않습니다.
- 팔레트 PRESENT/EMPTY/UNKNOWN은 관측값입니다. 신선하지 않거나 OMX 연결을 확인하지 못하면 유효 재고로 표시하지 않습니다. 실제 개수·적재 성공을 증명하지 않습니다.

## 검증 기록

세 차례 검토 기준을 분리했습니다.

1. **계약 검토**: 실제 FMS 라우터·주문 종료/복귀·시나리오 정의·마커 매핑·충전 문서와 AMR Action/OMX 셸 계약을 읽고 프런트엔드 기능 범위를 결정. 백엔드 API 추가 및 ROS/MQTT 우회 없음.
2. **논리 검증**: Node 회귀 테스트 8건. 실제 매핑 대조, 완료 후 RETURNING 차단, 취소 후 복구 점유, 새로고침의 확인 보류, 손상된 기록, 속도 계산 경계, 관측 버퍼·내역 상한. 타입 검사와 프로덕션 빌드 확인.
3. **모의 브라우저 검증**: 실제 API 주소와 분리한 localhost 모의 서버(18870)·개발 화면(18871) 사용. 주문 접수/완료/취소, robot2 N7 이동, robot3 마커 N4 선택, OMX2 C/D 관측, 교통 시험 접수/중지, robot3 충전소 N2 도킹 완료 모의 응답, 이동 중 새로고침 후 정지, 조회 장애 시 실행 차단, 기본 주문 입력 접힘, 패널 키보드 너비 조절, 탭 이동 시 불필요한 cmd_vel 0 미전송 확인.

실제 AMR·OMX를 움직여 검증한 결과는 아닙니다. 현장에서는 먼저 시뮬레이션으로 각 항목과 취소를 확인한 뒤 실제 모드에서 한 대씩 시험하세요. OMX 단독 실행 및 정렬만 재실행은 백엔드 확장 허용 전까지 사용할 수 없습니다.
