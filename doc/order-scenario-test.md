# 일반 주문 다중 등록 시나리오

기존/추가 파일과 변경 전후 흐름:
[KEV-MAPF 구현 현황](kev-mapf-implementation-map.md).

2026-10-19. 기존 주문 API에 주문을 등록해 관제 화면에서 연속 처리를 확인한다.
일반 주문의 새 출발 요청에 KEV 교통조정을 연결했다. 다른 로봇의 실행·예약은 유지한다.
기본 AI 경로 생성은 기존 방식을 사용하고, `FMS_ORDER_ROUTE_SOURCE=EXISTING_SHORTEST_PATH`로 A*와 교통조정을 분리 시험할 수 있다.
실행 설정과 화면 안내는 [일반 주문 연결](order-traffic-integration.md)을 먼저 확인한다. 이미 켜 둔 백엔드는 재시작해야 새 연결이 반영된다.

## 무작위 주문을 공급하고 기록·분석하기

`tests/random_order_observer.py --run --target 20 --timeout 600`으로 기존 관제의 연속 공급을 시작하고 목표 건수에서 공급을 멈춘다.
실행 전 시뮬·AI·새 교통조정 설정과 기존 주문·주행 종료를 확인한다. 기본 실행은 설정 출력뿐이며 `--run`이 있어야 주문을 등록한다.
약 0.5초 간격으로 주문 단계·위치·교통조정 선택을 `logs/random-order-runs/<시각>/`에 기록한다.
실패하면 새 공급만 멈추고 접수 주문을 자동 취소하지 않는다.
2026-10-20 결과와 한계는 [무작위 20건 시험](experiments/random-order-run-20261020.md)에 있다.

## 같은 주문표로 KEV와 계산 방식 비교하기

`tests/order_traffic_comparison.py`는 기존 관제의 일반 주문 API를 사용한다. 기본 실행은 주문표 출력이다.

```bash
# 주문을 넣거나 서버를 재시작하지 않고 계획만 확인
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python tests/order_traffic_comparison.py

# 시뮬·AI, A* 경로 + 일반 주문 교통조정이 켜진 로컬 관제에서 실행
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python tests/order_traffic_comparison.py --run --count 8 --seeds 42 17
```

- 같은 seed의 8건 주문표를 두 선택 방식에 그대로 사용한다. 처음 3건, 이후 5초마다 1건이며 이번 시험에서는 대기 주문 수에 따라 공급 시각을 늦추지 않는다.
- seed 42는 KEV → 계산, seed 17은 계산 → KEV 순서다. 이것만으로 통계적 우수성이 입증되지는 않는다.
- 비교를 위해 로컬 백엔드를 작업이 없을 때만 재시작한다. 기존 이력·모드·위치를 백업하고 이력을 복원하며, 각 시험은 같은 시작 위치·자세·배터리를 사용한다.
- 지도·속도·후보 생성·예약 검사는 유지한다. `FMS_TRAFFIC_SELECTION_POLICY`만 다르다. 끝나면 원래 선택 방식으로 복원한다.
- 주문 이름 `CMP-KEV`·`CMP-CALC`로 화면에서 구분한다. 다른 주문·시나리오·모드 변경이 감지되면 추가 공급과 뒤 시험을 중단한다. 이미 접수한 주문을 자동 취소하지 않는다.
- 등록 시각은 목표 시각과 실제 요청·응답 시각을 모두 저장한다. 목표에서 0.5초 이상 늦으면 비교 조건을 검토하도록 실패로 표시한다.
- 약 0.15초 간격의 관측 시간이다. 완료 시각·대기는 오차가 있으며, 실행마다 실제 상태와 이후 후보가 달라질 수 있다. 같은 입력을 그대로 재질문하는 시험과 구분한다.

기록은 `logs/order-traffic-comparisons/<시각>/`에 주문표·시험별 상태 관측·입력/응답·비교 요약을 저장한다. 재시작 백업도 각 시험 폴더에 있다.

## 관제 시나리오에서 계속 주문 공급하기

**시뮬·AI → 테스트 시나리오 → 연속 주문 · AI 자동 공급 / 시작·중지 → 테스트 실행**.
이 항목은 로봇 위치를 초기화하지 않고 현재 위치에서 기존 주문 등록·배차·주행을 사용한다.

- 시작 시 3건을 등록하고, 이후 5초마다 1건 추가한다.
- 대기 상태 PENDING은 전체 가상 주문 기준 최대 3건을 목표로 한다. 상한이면 추가하지 않고 자리가 생길 때 재개한다.
- A/B/C/D를 무작위로 조합하되 주문당 합계는 1~5개다. seed=42로 같은 품목 순서를 재현할 수 있다.
- **주문 공급 중지** 버튼은 새 등록만 멈춘다. 이미 접수된 주문은 계속 처리한다.
- 기존 개별/전체 비상정지는 공급도 중지하고, 이 시험이 만든 미배정 주문을 취소한다. 로봇 정지와 배정 주문 취소는 기존 명령 흐름을 따른다.
- 주문 또는 복귀가 실패하면 추가 공급을 중지하고 원인을 표시한다. 실패를 숨기고 계속 쌓지 않는다.
- 화면을 닫아도 서버 공급은 계속된다. 다시 접속해 중지할 수 있으며 서버 종료 시 공급 작업을 취소한다.

시작 전 기존 주문·복귀·복구와 다른 시나리오를 종료한다. 실행 중에는 모드 전환·지도 이동 시험을 차단한다.
공급 중지는 주문 완료와 다르다. 중지 후에도 주문 목록에서 남은 작업을 확인한다.
이 단계는 **일반 주문의 연속 처리 시험**이다. 시뮬·AI에서 `FMS_ORDER_TRAFFIC_ENABLED=1`이면 새 출발 요청의 교통조정도 거친다.

정의는 `tests/traffic_scenarios.json`의 `continuous_ai_orders.order_stream`,
실행은 `backend/simulation/order_stream_scenario.py`에 있다.
상태는 기존 `/api/scenarios/status`, 공급 중지는 `POST /api/scenarios/stop`을 사용한다.
실행 로그는 `logs/order-scenarios/stream-<run_id>.json`에 기록한다.

### 2026-10-19 검증 결과

- 관련 자동 검사 90개 통과, 프런트엔드 타입 검사·빌드 통과. 자동 검사에는 모델 대역을 사용한다.
- 실제 관제의 시작 버튼으로 5건이 등록·배차됐고 주문당 합계 1~5개, PENDING 상한 3건을 확인했다.
- 기존 KEV 경로 생성에서 N5→N3 탐색이 `current=10`의 순환 방지 조건 때문에 실패했다. 공급기는 이를 감지해 추가 등록을 중지했다.
- 해당 5건의 후속 처리 결과는 1건 완료, 4건 실패 후 복구 복귀 완료였다. 연속 주문이 모두 정상 완료됐다는 검증은 아니다.
- 별도 실행에서 화면의 공급 중지 버튼을 눌렀다. 초기 3건은 유지되고, 공급 주기보다 긴 6초 후에도 새 주문이 등록되지 않았다.
- 기록: `logs/order-scenarios/stream-ui-smoke-20261019.json`, `stream-stop-ui-20261019.json` 및 각 실행의 stream 로그.

공급·중지 기능과 별개로 **기존 KEV 경로 생성의 안정성 문제**가 드러났다.
이 단계에서 A*로 대체하거나 경로 생성·KEV-MAPF의 판단 구조를 변경하지 않았다.
연속 물류의 정상 완료 검증을 계속하려면 해당 경로 생성 실패를 먼저 다뤄야 한다.

## 테스트 준비

1. 관제 `http://100.81.82.30:5173/`를 연다. 주문 현황 패널을 펼쳐 둔다.
2. 처음에는 **시뮬 · 알고리즘**으로 확인한다. 이후 **시뮬 · AI / KEV 0.8B**로 반복할 수 있다.
3. 진행 중 주문, 지도 시나리오, 복귀·실패 복구를 정리한다. 실행기는 기존 주문을 취소하거나 로봇 위치를 초기화하지 않는다.
4. 원격 Ubuntu 터미널에서 Logistics_AI 루트로 이동해 아래 명령을 실행한다. Python 표준 라이브러리만 사용하므로 가상환경 활성화는 필수가 아니다.

```bash
cd ~/dev/Logistics_AI

# 미리보기: 주문을 등록하지 않는다.
python3 tests/order_scenarios.py bulk_six

# 실제 가상 주문 등록 + 상태 조회
python3 tests/order_scenarios.py bulk_six --run
```

## 1. 6건 연속 등록: bulk_six

| 순서 | 품목 | 방문 픽업대 | 확인 목적 |
| --- | --- | --- | --- |
| 1 | A1+B1 | OMX1, 노드 5 | 첫 픽업대 작업 |
| 2 | C1+D1 | OMX2, 노드 6 | 다른 픽업대 작업 |
| 3 | A1+C1 | 5→6 | 앞선 주문과 픽업대 공유 시 대기 |
| 4 | B2 | 5 | 가용 로봇이 생긴 뒤 다음 주문 할당 |
| 5 | D2 | 6 | 후속 주문 처리 |
| 6 | B1+D1 | 5→6 | 여러 픽업대 방문 후 마무리 |

6건은 기존 API에 빠르게 순차 등록한다. 원자적인 일괄 등록 기능은 아니다.
등록 도중에도 0.1초 배차 루프가 동작하므로 모든 주문이 동시에 PENDING인 화면을 보장하지 않는다.
로봇 시작 위치는 현재 관제 상태를 사용한다. 로봇 ID와 정확한 이동 순서를 고정한 시나리오는 아니다.

## 2. 처리 중 추가 유입: continuous_six

실제 작업 시간이 짧으면 다음 유입 전에 앞선 작업이 끝날 수도 있다.


## KEV 경로 생성까지 확인

기존 주문·복귀가 끝난 뒤 관제에서 **시뮬 · AI**로 바꾸고 다음 명령을 실행한다.
실행기가 모드를 자동 변경하지 않으며, 실제 모드에서는 주문 등록 전에 거부한다.

```bash
python3 tests/order_scenarios.py bulk_six --operation ai --model kev-08b --run
```

AI 주문의 일반 경로는 `dispatch_order_route → preview_llm_route(selector=kev)`다.
MAPF 입력 연결 테스트도 관제 모드를 따라 알고리즘이면 plan_route(A*), AI면
동일한 preview_llm_route(selector=kev)를 사용한다. 조정안 선택 호출 수는 경로 생성 호출 수와 별도로 기록한다.
AI 경로 생성의 실패도 이번 시험의 관찰 결과로 남긴다. 성공이나 처리량 향상을 가정하지 않는다.

## 통과 기준과 실패 확인

- 6건이 중복 없이 등록되고 주문명 `TEST-...-01`부터 `06`까지 화면에 보인다.
- PENDING 주문이 배차 후 IN_PROGRESS가 되고, 가용 로봇이 생기면 다음 주문이 자동 할당된다.
- 같은 픽업대를 사용하는 주문은 WAITING_PICKUP이 될 수 있다. 주문의 IN_PROGRESS는 실제 이동 중이라는 뜻이 아니다.
- A/C와 B/D 주문은 노드 5→6을 방문한 뒤 패킹 작업대로 이동한다.
- 최종 6건 모두 status=COMPLETED, phase=COMPLETED이고 return_error가 없어야 한다.
- FAILED, CANCELLED, 복귀 오류, 300초 내 미완료는 화면과 로그에서 원인을 확인한다. 시간 초과만으로 교착을 확정하지 않는다.

결과와 등록된 주문 ID는 `logs/order-scenarios/TEST-*.json`에 기록한다.
조회 주기는 0.5초라 짧은 phase 전환은 로그에서 누락될 수 있다.
실행기를 Ctrl+C로 종료하거나 요청이 실패해도 이미 접수된 주문은 서버에서 계속 처리된다.
다시 실행하기 전에 관제를 확인한다. 실패 시 자동 취소·재시도·초기화는 하지 않는다.

이 시험은 주문 파이프라인의 동작 확인이다. 전체 tick의 충돌 검증이나 처리량 최적성 평가는 포함하지 않는다.
