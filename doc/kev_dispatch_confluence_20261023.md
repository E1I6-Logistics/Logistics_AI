# KEV 배차 적용 범위 및 비교 실험

작성일: 2026-10-23
관련 문서: `kev_dispatch_policy_decisions_20261021.md`

## 1. 목적

KEV로 코드 배차 전체를 대체하지 않습니다. KEV가 판단할 수 있는 부분에만 KEV를 쓰고, 그 부분에서 코드 규칙과 선택 품질을 비교합니다.

- 안전 조건과 계산할 수 있는 값은 코드가 보장합니다.
- KEV는 **픽업 ETA가 비슷해서 코드만으로 한 대가 확실히 우선이라고 보기 어려운 후보들** 사이에서만 선택합니다.
- KEV 결과가 코드보다 나쁘더라도 실패로 보지 않고, KEV 적용 범위와 한계를 정하는 근거로 기록합니다.

배차 우선순위는 2026-10-23에 **픽업 ETA 우선, 배터리는 최소 하한 조건**으로 확정했습니다.

## 2. 코드와 KEV의 역할

| 구분 | 담당 | 내용 | 구현 여부 |
|---|---|---|---|
| 안전 후보 필터 | 코드 | 연결 불가, 작업 중, 위치·점유 정보 이상, 오류 상태, 재시도 시 직전 실패 로봇 제외 | 구현됨 |
| 최소 배터리 | 코드 | 하한 미달 로봇 제외 | 임시 기준 구현됨. 최근 60초 최저 전압 11.2V 미만·전압 모름이면 제외(9절). 실측 하한은 미정 |
| 적재 용량 | 코드 | 주문 총수량 1~5개 제한 | 주문 접수 제한만 있음. 로봇별 적재 검사는 없음 |
| 거리·ETA 계산 | 코드 | route graph 최단 거리, 설정 속도로 ETA 계산 | 구현됨 |
| ETA가 확실히 앞서는 경우 | 코드 | 근소 ETA 범위 안에 한 대만 있으면 KEV 호출 없이 선택 | 구현됨 |
| **근소 ETA 후보 간 선택** | **KEV** | `KEV_DISPATCH_ETA_TIE_SECONDS` 범위 안 후보 중 한 대 선택. 현재 실험 기준 2초 | 구현됨 |
| KEV 오류·timeout·cooldown | 코드 | 같은 근소 ETA 후보군 안에서 임시 규칙 기준선으로 fallback | 구현됨 |
| 완전 동률 | 코드 | `robot_id` 오름차순 등 확정 규칙 | 일부 구현. 임시 기준선·fallback에서만 적용, KEV 선택 결과의 동률 판정은 미구현 |

안전 후보 전체를 KEV에 전달하는 방식은 사용하지 않습니다. ETA 범위를 벗어난 후보는 KEV에 전달하지 않습니다.

## 3. KEV 입력 정보

근소 ETA 후보군에 든 로봇만 전달합니다.

| 입력 | 의미 | 상태 |
|---|---|---|
| `state` | 현재 로봇 상태 | 입력됨 |
| `battery` | 현재 배터리 값 | 입력됨. 실제 로봇은 0~100 단위(robot1 확인, 2026-10-23) |
| `current_node`, `occupied_node`, `goal_node` | 현재·점유·목표 노드 | 입력됨 |
| `returning` | 이전 주문 완료 후 복귀 중인지 여부 | 입력됨 |
| `pickup_node` | 주문의 첫 픽업 노드 | 입력됨 |
| `pickup_distance_m` | route graph 기준 픽업 최단 거리 | 입력됨 |
| `pickup_eta_seconds` | 거리 ÷ `KEV_DISPATCH_ETA_SPEED_MPS`(기본 0.2 m/s) | 입력됨 |
| `eta_delta_seconds` | 최단 ETA와의 차이 | 입력됨 |
| `recent_dispatch_count` | 최근 배차 횟수 | 미입력. 작업량 기준 결정 후 추가 |
| `post_task_battery` | 주문 처리 후 예상 배터리 | 미입력. 소모율 측정 후 추가 |

거리와 ETA는 코드가 계산해 제공합니다. KEV가 계산하지 않습니다.

## 4. KEV 지시문 방향

- 전달된 후보는 코드 안전 조건과 근소 ETA 범위를 통과한 로봇입니다.
- 후보 목록 안에서 정확히 한 대를 선택하고, 로봇 ID 하나만 반환합니다.
- ETA로 다시 순위를 매기지 않습니다.
- 배터리를 안전 기준으로 판단하지 않습니다. 배터리 하한은 코드가 담당합니다.
- `IDLE` / `RETURNING`, 현재 배터리, 최근 작업량처럼 서로 충돌할 수 있는 보조 조건을 비교합니다.

현재 지시문은 상태와 현재 배터리만 보조 조건으로 사용합니다. 작업량과 예상 배터리는 입력이 추가된 뒤 지시문에 반영합니다.

## 5. 비교 구조

| 구간 | 처리 및 비교 대상 |
|---|---|
| ETA 차이가 큰 경우 | 코드가 즉시 선택. KEV 비교 대상 아님 |
| ETA가 근소한 경우 | 규칙 알고리즘 선택 vs KEV 선택 |
| KEV 오류·timeout·cooldown | 코드 fallback |
| 전체 운영 결과 | 기존 알고리즘, 규칙 알고리즘, 보호형 KEV의 완료 시간·편중·fallback 비율 비교 |

| 방식 | 내용 | 역할 |
|---|---|---|
| 기존 알고리즘 | 후보 목록 순서로 선택, 직전 로봇은 뒤로 미룸(`_select_robot_by_algorithm()`) | KEV 장애 시 fallback, 회귀 확인 |
| 규칙 알고리즘 | 정책 우선순위(ETA → 보조 조건 → 동률)를 코드로 구현 | 근소 ETA 구간에서 KEV와 비교할 기준선. 임시 기준선(`IDLE·비복귀 → 현재 배터리 높은 순 → robot_id 오름차순`) 구현됨. 작업량·예상 배터리 정책 확정 후 변경 |
| 보호형 KEV | 근소 ETA 후보군 안에서만 KEV가 선택 | 현재 구현된 KEV 배차 |

## 6. 평가 항목

| 평가 항목 | 확인 내용 |
|---|---|
| 근소 ETA 구간 선택 | 규칙 알고리즘과 KEV가 다른 로봇을 고른 비율과 이유 |
| 픽업 ETA | 선택된 로봇의 예상 픽업 도착 시간 |
| 주문 완료 시간 | 주문 생성부터 완료까지 걸린 시간 |
| 주문 성공률 | 완료, 실패, 취소 비율 |
| 배차 편중 | 특정 로봇에 주문이 몰리는지 여부 |
| 배터리 안전 | 하한 위반, Pi 저전압 발생 여부 |
| fallback 발생률 | KEV 오류·timeout·cooldown으로 코드가 선택한 비율 |
| KEV 응답 시간 | 호출부터 응답까지 걸린 시간 |

## 7. 범위에서 제외한 것

- 안전 후보 전체를 KEV에 전달하는 비교 실험
- 상황 요약, 모니터링 판단 등 배차 외 KEV 활용. 필요하면 별도 범위로 다룹니다.

## 8. 미결정 항목

- `KEV_DISPATCH_ETA_TIE_SECONDS` 운영값. 현재 코드와 KEV 비교 실험의 값은 `2초`이며, 실제 로봇 ETA 측정과 실험 결과를 확인한 뒤 재검토합니다.
- 실제 로봇의 ETA 속도(실측 평균 속도)
- 최소 배터리 기준(실측 후 확정)
- `RETURNING` 우선순위, 최근 작업량 기준, 완전 동률 규칙

## 9. 배터리

최소 배터리 기준은 아직 확정하지 않았습니다.

- 기존 실험의 `battery_percent`는 모두 빈 값이라 percentage 기준을 정할 근거가 없습니다.
- 전압이 기록된 정렬 런 105회는 10.97V~12.33V 범위였고, 그 안에서 정렬 성공 사례가 있습니다.
- robot3은 11.2V~11.7V, robot2는 12.15V에서도 Pi 저전압이 있었습니다. 배터리 잔량보다 전원 보드·케이블 문제 가능성이 큽니다.
- OpenCR 리셋·응답 끊김 사례는 문제 시점 전압이 기록되지 않았습니다.

**실측 전 임시 기준:** 주행 중 전압 11.2V 미만이면 배차에서 제외합니다. 기존 기록에서 표본이 있는 구간의 아랫선이며, 위험 지점을 예측한 값은 아닙니다. Pi 저전압은 전압과 별개로 `vcgencmd get_throttled`로 확인합니다. 이 기준은 구현되어 있습니다. 백엔드가 `battery_state.voltage`를 받아 최근 60초 최저 전압으로 판단하고(배터리 교체로 연결이 끊기면 기록을 지우고 새 전압으로 다시 판단), 전압을 모르는 로봇(`battery_unknown`)도 제외합니다. `/api/robots`의 `dispatch_block_reason`, `battery_voltage`, `battery_voltage_min`으로 확인할 수 있습니다. 실제 로봇이 전압을 보내지 않으면 모든 로봇이 배차되지 않으므로, 운행 전에 `battery_voltage` 값이 들어오는지 확인합니다.

실측 항목: `battery_state.voltage`, `battery_state.percentage`, 주행 중 최저 전압, Pi 저전압 여부, 로봇별 전원 보드·케이블 상태

**실제 로봇 확인 (2026-10-23, robot1 정지 상태):** 전압 12.26V, percentage 97.77(0~100 단위), `dispatch_available=true`. 주행 중 최저 전압과 robot2·robot3는 아직 확인하지 않았습니다. 로봇 연결 상태는 백엔드가 real 모드에서 2초마다 직접 갱신하므로 FMS 화면을 열지 않아도 됩니다(2026-10-24 robot3에서 화면 없이 확인). robot3: 10.99V 배터리는 경보음보다 먼저 `low_battery`로 차단, 교체 배터리로 주행 7회 동안 최저 11.36V, `get_throttled=0x0`. 실제 주행 시간은 코드 ETA(0.2 m/s)의 약 3.4배(N2→N5 평균 25.9초 vs 7.51초)여서 ETA 속도 보정이 먼저 필요합니다.

## 10. 다음 작업 순서

1. 배터리 voltage·percentage·주행 중 최저 전압·Pi 저전압 여부 수집
2. 실측 하한으로 전압 기준 갱신(임시 11.2V 구현됨), Pi 저전압 검사, 완전 동률 등 코드 규칙 구현
3. 실제 로봇 평균 속도 측정 후 ETA 속도 확정, `KEV_DISPATCH_ETA_TIE_SECONDS` 운영값 재검토
4. 작업량·예상 배터리 정책 확정 후 규칙 알고리즘 기준선 갱신
5. 로봇을 서로 다른 노드에 둔 ETA 실험으로 코드 즉시 선택 구간과 KEV 구간이 나뉘는지 확인
6. 근소 ETA 구간에서 상태·배터리·작업량을 한 항목씩 바꿔 규칙 알고리즘과 KEV 선택 비교
7. 전체 운영 결과로 세 방식 비교 후 KEV 적용 범위 결정
