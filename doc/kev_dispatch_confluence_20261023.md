# KEV 배차 적용 범위 및 비교 실험

작성일: 2026-10-23
관련 문서: `kev_dispatch_policy_decisions_20261021.md`

## 1. 목적

KEV로 코드 배차 전체를 대체하지 않습니다. KEV가 판단할 수 있는 부분에만 KEV를 쓰고, 그 부분에서 코드 규칙과 선택 품질을 비교합니다.

- 안전 조건과 계산할 수 있는 값은 코드가 보장합니다.
- 기본 `near_eta` 범위에서는 KEV가 **픽업 ETA가 비슷해서 코드만으로 한 대가 확실히 우선이라고 보기 어려운 후보들** 사이에서만 선택합니다.
- 비교 실험용 `all_eligible` 범위에서는 안전 검사를 통과한 후보 전체를 KEV에 전달하고, KEV가 ETA 우선 선택을 수행하는지 확인합니다.
- 대기 주문 우선순위 KEV는 기본적으로 꺼져 있습니다. 실험에서만 여러 대기 주문 중 다음에 배차할 주문 1건을 선택합니다.
- KEV 결과가 코드보다 나쁘더라도 실패로 보지 않고, KEV 적용 범위와 한계를 정하는 근거로 기록합니다.

배차 우선순위는 2026-10-23에 **픽업 ETA 우선, 배터리는 최소 하한 조건**으로 확정했습니다.

## 2. 코드와 KEV의 역할

| 구분 | 담당 | 내용 | 구현 여부 |
|---|---|---|---|
| 안전 후보 필터 | 코드 | 연결 불가, 작업 중, 위치·점유 정보 이상, 오류 상태 제외 | 구현됨 |
| 재시도 주문의 직전 로봇 | 코드 | AI 모드에서 다른 후보가 있으면 제외. algorithm 모드에서는 제외하지 않고 후보 순서만 뒤로 보냄 | 구현됨 |
| 최소 배터리 | 코드 | 하한 미달 로봇 제외 | 임시 기준 구현됨. 최근 60초 최저 전압 11.2V 미만·전압 모름이면 제외(9절). 실측 하한은 미정 |
| 적재 용량 | 코드 | 주문 총수량 1~5개 제한 | 주문 접수 제한만 있음. 로봇별 적재 검사는 없음 |
| 거리·ETA 계산 | 코드 | route graph 최단 거리, 설정 속도로 ETA 계산 | 구현됨 |
| ETA가 확실히 앞서는 경우 | 코드 | 근소 ETA 범위 안에 한 대만 있으면 KEV 호출 없이 선택 | 구현됨 |
| **근소 ETA 후보 간 선택** | **KEV** | `KEV_DISPATCH_ETA_TIE_SECONDS` 범위 안 후보 중 한 대 선택. 현재 실험 기준 2초 | 구현됨 |
| 전체 유효 후보 간 선택 | KEV | `KEV_DISPATCH_CANDIDATE_SCOPE=all_eligible`일 때 안전 통과 후보 전체 중 ETA 우선으로 한 대 선택 | 구현됨. 비교 실험용 |
| KEV 오류·timeout·cooldown | 코드 | 같은 근소 ETA 후보군 안에서 임시 규칙 기준선으로 fallback | 구현됨 |
| 대기 주문 우선순위 | KEV | 여러 `PENDING` 주문 중 다음에 배차할 주문 1건 선택 | 구현됨. 기본 비활성화, 실험용 |
| 주문 장기 대기 보호 | 코드 | 오래 기다린 주문은 KEV를 건너뛰고 FIFO로 먼저 배차 | 구현됨. 기본 120초 |
| 완전 동률 | 코드 | `robot_id` 오름차순 등 확정 규칙 | 일부 구현. 임시 기준선·fallback에서만 적용, KEV 선택 결과의 동률 판정은 미구현 |

기본값 `near_eta`에서는 ETA 범위를 벗어난 후보를 KEV에 전달하지 않습니다. `all_eligible`은 이를 풀어 안전 통과 후보 전체를 KEV에 전달하는 비교 실험용 범위입니다. 두 범위 모두 KEV 오류·timeout·cooldown 시에는 같은 근소 ETA 후보군의 코드 기준선으로 fallback합니다.

### 주문 우선순위 KEV 결론

주문 우선순위 KEV는 기본 비활성화 상태로 유지하고 연구 항목으로 둡니다. D-11~D-13에서 보호 규칙은 ETA가 명백히 긴 주문 선택을 코드가 교정했지만, KEV는 가장 오래된 주문을 반복해서 피했고 후보 라벨·나열 순서만 바꿔도 선택이 달라졌습니다. FIFO보다 짧은 처리 시간이 관찰된 회차는 있었지만 조건별 1회여서 재현성을 입증하지 못했습니다.

로봇 배차 KEV의 현재 운영 후보는 `near_eta` + 최근 작업량 + 코드 보호입니다. 실제 로봇 적용 전에는 보정한 ETA 속도(`0.06 m/s`)에서 선택 품질과 배차 편중을 별도로 검증합니다.

## 3. KEV 입력 정보

`near_eta`에서는 근소 ETA 후보군만, `all_eligible`에서는 안전 검사를 통과한 후보 전체를 전달합니다.

| 입력 | 의미 | 상태 |
|---|---|---|
| `state` | 현재 로봇 상태 | 입력됨 |
| `battery` | 현재 배터리 값 | 입력됨. 실제 로봇은 0~100 단위(robot1 확인, 2026-10-23) |
| `current_node`, `occupied_node`, `goal_node` | 현재·점유·목표 노드 | 입력됨 |
| `returning` | 이전 주문 완료 후 복귀 중인지 여부 | 입력됨 |
| `pickup_node` | 주문에서 실제로 첫 방문하는 픽업 노드(`pickup_nodes` 순서, A·B가 있으면 N5) | 입력됨 |
| `pickup_distance_m` | route graph 기준 픽업 최단 거리 | 입력됨 |
| `pickup_eta_seconds` | 거리 ÷ `KEV_DISPATCH_ETA_SPEED_MPS`(기본 0.2 m/s) | 입력됨 |
| `eta_delta_seconds` | 최단 ETA와의 차이 | 입력됨 |
| `recent_dispatch_count` | 최근 집계 기간 내 배차 횟수 | `KEV_DISPATCH_RECENT_WORKLOAD=1`일 때 입력됨 |
| `recent_pickup_distance_m` | 최근 배정 시점 픽업까지 예상 거리의 합 | `KEV_DISPATCH_RECENT_WORKLOAD=1`일 때 입력됨 |
| `post_task_battery` | 주문 처리 후 예상 배터리 | 미입력. 소모율 측정 후 추가 |

거리와 ETA는 코드가 계산해 제공합니다. KEV가 계산하지 않습니다.

ETA는 실제 주문 방문 순서의 첫 픽업 노드 기준입니다. 예를 들어 A와 C를 함께 주문하면 로봇이 N6에 더 가까워도 실제로 먼저 가는 N5까지의 거리와 ETA로 배차합니다. 이전에는 여러 픽업 노드 중 가장 가까운 노드 기준이었으며, 단일 품목 주문만 쓴 기존 실험(S0~S4, D-6~D-10) 결과에는 영향이 없습니다.

## 4. KEV 지시문 방향

- `near_eta`: 전달된 후보는 코드 안전 조건과 근소 ETA 범위를 통과한 로봇이며, ETA를 다시 순위를 매기지 않습니다.
- `all_eligible`: 전달된 후보는 코드 안전 조건만 통과한 로봇이며, KEV는 `pickup_eta_seconds`가 가장 짧은 로봇을 우선 선택합니다.
- 후보 목록 안에서 정확히 한 대를 선택하고, 로봇 ID 하나만 반환합니다.
- 배터리를 안전 기준으로 판단하지 않습니다. 배터리 하한은 코드가 담당합니다.
- `IDLE` / `RETURNING`, 현재 배터리, 최근 작업량처럼 서로 충돌할 수 있는 보조 조건을 비교합니다.

`KEV_DISPATCH_RECENT_WORKLOAD=1`이면 현재 지시문은 최근 배차 횟수와 최근 픽업 거리 합도 보조 조건으로 사용합니다. ETA와 상태가 비슷할 때만 작업량이 적은 로봇을 우선하며, 작업량 때문에 ETA가 확실히 짧은 로봇을 뒤집지 않도록 지시합니다. 기본값 `0`에서는 D-6~D-8과 동일한 입력을 유지하고, 기록도 남기지 않습니다. 작업 후 예상 배터리는 아직 입력하지 않습니다.

## 5. 대기 주문 우선순위 KEV

기존 대기열은 주문 등록 순서(FIFO)대로 순회합니다. 재시도 주문도 원래 FIFO 순서와 대기 시작 시각을 유지합니다. `KEV_ORDER_SCHEDULING_ENABLED=1`인 실험에서만 KEV가 여러 `PENDING` 주문 중 다음 주문 1건을 먼저 선택합니다. 선택된 주문을 먼저 배차한 뒤, 같은 주기에 남은 주문은 기존 순서로 처리합니다.

KEV에는 주문별 큐 순서, 대기 시간, 품목·수량, 픽업 노드, 현재 배차 가능한 로봇 수, 현재 후보 기준 최소 픽업 ETA를 전달합니다. 주문 UUID는 KEV 입력에 전달하지 않고 `order_1`, `order_2` 같은 큐 라벨만 후보 키로 사용하며, 코드가 선택 결과를 실제 주문 ID로 연결합니다. 지시문은 대기 시간이 충분히 다르면 오래 기다린 주문을 우선하고, 대기 시간이 비슷하면 최소 픽업 ETA가 짧은 주문을 우선하도록 합니다.

- KEV 오류·timeout·cooldown 시에는 가장 먼저 등록된 대기 주문부터 FIFO로 처리합니다.
- `KEV_ORDER_SCHEDULING_MAX_WAIT_SECONDS=120`이 지나면 KEV를 호출하지 않고 가장 오래 기다린 주문을 먼저 처리합니다. `0`이면 이 보호 규칙을 끕니다.
- 긴급도, 마감 시각, 적재 용량, 실제 작업대 혼잡도는 아직 주문 입력·정책에 없으므로 KEV가 추론해 판단하지 않습니다.
- 이 기능은 로봇을 고르는 기존 KEV 배차와 별개입니다. 순서는 “다음 주문 선택 → 해당 주문의 로봇 선택”입니다.

## 6. 비교 구조

| 구간 | 처리 및 비교 대상 |
|---|---|
| ETA 차이가 큰 경우 | 코드가 즉시 선택. KEV 비교 대상 아님 |
| ETA가 근소한 경우 | 규칙 알고리즘 선택 vs KEV 선택 |
| 전체 유효 후보 비교 | `all_eligible`에서 KEV가 ETA 최단 로봇을 고르는지, 선택과 `eta_winner`를 비교 |
| 대기 주문 우선순위 비교 | FIFO와 KEV 주문 선택의 주문 대기 시간, 완료 시간, 장기 대기 발생 여부를 비교 |
| KEV 오류·timeout·cooldown | 코드 fallback |
| 전체 운영 결과 | 기존 알고리즘, 규칙 알고리즘, 보호형 KEV의 완료 시간·편중·fallback 비율 비교 |

| 방식 | 내용 | 역할 |
|---|---|---|
| 기존 알고리즘 | 후보 목록 순서로 선택, 직전 로봇은 뒤로 미룸(`_select_robot_by_algorithm()`) | KEV 장애 시 fallback, 회귀 확인 |
| 규칙 알고리즘 | 정책 우선순위(ETA → 보조 조건 → 동률)를 코드로 구현 | 근소 ETA 구간에서 KEV와 비교할 기준선. 임시 기준선(`IDLE·비복귀 → 현재 배터리 높은 순 → robot_id 오름차순`) 구현됨. 작업량·예상 배터리 정책 확정 후 변경 |
| 보호형 KEV (`near_eta`) | 근소 ETA 후보군 안에서만 KEV가 선택 | 기본값 |
| 전체 후보 KEV (`all_eligible`) | 안전 통과 후보 전체에서 KEV가 ETA 우선으로 선택 | 비교 실험용 |

## 7. 평가 항목

| 평가 항목 | 확인 내용 |
|---|---|
| 근소 ETA 구간 선택 | 규칙 알고리즘과 KEV가 다른 로봇을 고른 비율과 이유 |
| 픽업 ETA | 선택된 로봇의 예상 픽업 도착 시간 |
| 주문 완료 시간 | 주문 생성부터 완료까지 걸린 시간 |
| 주문 성공률 | 완료, 실패, 취소 비율 |
| 배차 편중 | 특정 로봇에 주문이 몰리는지 여부 |
| 배터리 안전 | 하한 위반, Pi 저전압 발생 여부 |
| fallback 발생률 | KEV 오류·timeout·cooldown으로 코드가 선택한 비율 |
| KEV 응답 시간 | 호출부터 응답까지 걸린 시간 |
| 주문 장기 대기 | 설정한 최대 대기 시간을 넘긴 주문 수와 FIFO age guard 발생 횟수 |

## 8. 범위에서 제외한 것

- 상황 요약, 모니터링 판단 등 배차 외 KEV 활용. 필요하면 별도 범위로 다룹니다.

## 9. 미결정 항목

- `KEV_DISPATCH_ETA_TIE_SECONDS` 운영값. 현재 코드와 KEV 비교 실험의 값은 `2초`이며, 실제 로봇 ETA 측정과 실험 결과를 확인한 뒤 재검토합니다.
- `KEV_DISPATCH_CANDIDATE_SCOPE`: 기본은 `near_eta`이며, `all_eligible` 비교 실험 결과로 운영 적용 여부를 결정합니다.
- 실제 로봇의 ETA 속도(실측 평균 속도)
- 최소 배터리 기준(실측 후 확정)
- `RETURNING` 우선순위, 최근 작업량 기준, 완전 동률 규칙
- 주문 우선순위의 긴급도·마감 시각·적재량·작업대 혼잡도 정책

## 10. 배터리

최소 배터리 기준은 아직 확정하지 않았습니다.

- 기존 실험의 `battery_percent`는 모두 빈 값이라 percentage 기준을 정할 근거가 없습니다.
- 전압이 기록된 정렬 런 105회는 10.97V~12.33V 범위였고, 그 안에서 정렬 성공 사례가 있습니다.
- robot3은 11.2V~11.7V, robot2는 12.15V에서도 Pi 저전압이 있었습니다. 배터리 잔량보다 전원 보드·케이블 문제 가능성이 큽니다.
- OpenCR 리셋·응답 끊김 사례는 문제 시점 전압이 기록되지 않았습니다.

**실측 전 임시 기준:** 주행 중 전압 11.2V 미만이면 배차에서 제외합니다. 기존 기록에서 표본이 있는 구간의 아랫선이며, 위험 지점을 예측한 값은 아닙니다. Pi 저전압은 전압과 별개로 `vcgencmd get_throttled`로 확인합니다. 이 기준은 구현되어 있습니다. 백엔드가 `battery_state.voltage`를 받아 최근 60초 최저 전압으로 판단하고(배터리 교체로 연결이 끊기면 기록을 지우고 새 전압으로 다시 판단), 전압을 모르는 로봇(`battery_unknown`)도 제외합니다. `/api/robots`의 `dispatch_block_reason`, `battery_voltage`, `battery_voltage_min`으로 확인할 수 있습니다. 실제 로봇이 전압을 보내지 않으면 모든 로봇이 배차되지 않으므로, 운행 전에 `battery_voltage` 값이 들어오는지 확인합니다.

실측 항목: `battery_state.voltage`, `battery_state.percentage`, 주행 중 최저 전압, Pi 저전압 여부, 로봇별 전원 보드·케이블 상태

**실제 로봇 확인 (2026-10-23, robot1 정지 상태):** 전압 12.26V, percentage 97.77(0~100 단위), `dispatch_available=true`. 주행 중 최저 전압과 robot2·robot3는 아직 확인하지 않았습니다. 로봇 연결 상태는 백엔드가 real 모드에서 2초마다 직접 갱신하므로 FMS 화면을 열지 않아도 됩니다(2026-10-24 robot3에서 화면 없이 확인). robot3: 10.99V 배터리는 경보음보다 먼저 `low_battery`로 차단, 교체 배터리로 주행 7회 동안 최저 11.36V, `get_throttled=0x0`. 실제 주행 시간은 코드 ETA(0.2 m/s)의 약 3.4배(N2→N5 평균 25.9초 vs 7.51초)여서 ETA 속도 보정이 먼저 필요합니다.

## 11. 다음 작업 순서

1. FMS를 정상 설정으로 재시작합니다. 시뮬레이션 실험이면 `KEV_DISPATCH_ETA_SPEED_MPS=0.2 ./start_fms.sh`로 시작합니다.
2. 완료: 로봇 배차 KEV 질문 ID UUID 제거 후 S2를 재실행했습니다. 기존 확률(`robot1=0.4653`, `robot2=0.5347`)과 선택 결과가 완전히 같았습니다(D-8). 질문 ID 변경이 KEV 선택에 영향을 주지 않음을 확인한 뒤 비교 실험으로 넘어갑니다.
3. 로봇별 최근 작업량 입력을 추가하고, 배차 편중 비교에 사용할 집계 기준(최근 N건 또는 시간 범위)을 정합니다.
4. `near_eta`와 `all_eligible`을 같은 시나리오에서 비교합니다. ETA 최단 선택률, fallback 발생률, 로봇별 배차 편중을 우선 기록합니다.
5. 동일 픽업대 주문이 섞이는 상황을 기준으로 주문별 실제 배차 가능 로봇 수를 계산하도록 확장합니다.
6. 다품목 주문의 ETA 기준 노드: 실제 방문 순서의 첫 픽업 노드 기준으로 바꿨습니다(완료).
7. 완료: 주문 10건·로봇 3대 다중 주문에서 FIFO와 주문 우선순위 KEV를 비교했습니다(D-11~D-13). 보호 규칙은 ETA 위반을 막았지만 후보 표현 순서 편향과 오래된 주문 회피가 남아, 주문 우선순위 KEV는 기본 비활성화·연구 항목으로 유지합니다.

시뮬레이션은 회전 시간을 ETA와 완료 시간에 반영하지 않으므로, 시뮬레이션 비교에서는 ETA 최단 선택률·fallback·배차 편중을 중심으로 봅니다. 주문 완료 시간은 참고값으로만 기록합니다. 장기 대기 보호(기본 120초)는 주문을 한꺼번에 넣거나 `KEV_ORDER_SCHEDULING_MAX_WAIT_SECONDS`를 낮춘 조건에서 검증합니다.
