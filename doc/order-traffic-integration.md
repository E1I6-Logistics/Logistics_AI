# 일반 주문에 교통조정과 동적 우회 연결

초기 연결: 2026-10-19. 기능 공유 안내 갱신: 2026-10-24. 현재 연결은 **새로 출발하는 로봇 한 대의 경로를 조정하고, 다른 로봇의 주행과 예약은 유지하는 단계**다.
여러 로봇을 동시에 멈추거나 기존 주행 계획의 통과 순서를 바꾸지 않는다.

## 실제 흐름

```text
일반 주문 등록 → 기존 배차·픽업 순서 유지
  → 이번 목적지의 경로 생성
  → 다른 로봇의 점유·경로·예약·보호 자원 확인
  → 공유 자원을 피하는 우회 경로를 기존 생성기에 요청
  → 각 경로를 기존 TrafficManager 사본에서 예약 검사
      0개: 현재 노드에서 재검사 대기, 한도 초과 시 주문 실패
      1개: KEV 호출 없이 적용
      2개 이상: 설정한 방식에 따라 KEV 또는 코드가 최종 선택
  → 최신 점유·예약으로 다시 검사 → 새 요청만 예약 → 기존 주행기 실행
```

이 흐름은 일반 주문의 픽업 이동·작업대 이동·복귀에서 사용한다.

현재 비교에 사용하는 `KEV_STRATEGY_ORDER`는 **경로 후보를 만들기 전에 KEV가 전략 검토 순서를 제안하고, 코드는 생성·예약 검사한 경로 중 예상 시간이 짧은 것을 선택하는 방식**이다. 초기 `KEV` 정책은 후보 생성·검사를 마친 뒤 KEV가 최종 경로를 선택한다. `MIN_EXPECTED_TIME`은 검사한 후보 중 코드를 통해 예상 시간이 짧은 것을 고른다. 세 정책은 같은 역할이 아니며, 내부 코드 정책을 기존 관제의 알고리즘 모드와 혼동하지 않는다.

2026-10-20: 같은 픽업대를 쓰는 뒤 주문은 앞 주문 전체 완료를 기다리지 않는다.
`pickup_queue`가 이번 픽업대에 대한 선행 요청만 확인하고, 실제 점유가 풀리면 이동 요청을 허용한다.
예: R1이 N5를 떠나 작업대로 이동 중이면 R2는 N5로 이동을 요청할 수 있다. 통로·N5에 다른 예약이 있으면 그 예약 때문에 더 기다릴 수 있다.
각 픽업대의 차례는 방문마다 확인하며, 미래에 방문할 다른 픽업대를 미리 독점하지 않는다.
다른 로봇의 예약은 사전 검사와 적용 과정에서 해제하지 않는다.
상태가 바뀌어 선택한 경로를 예약할 수 없으면 다시 검사하며, 취소·출발 위치 변경·지도 변경·모드 변경 시 적용을 거부한다.
현재 준비 경로가 막힌 경우만 재검사한다. 이미 주행 중인 로봇을 계속 감시해 KEV로 우회시키는 기능은 아직 없다.

## 기존 경로 생성기와의 연결

`traffic_route_provider.generate_traffic_route()`가 다음 형식으로 기존 기능을 호출한다.

```python
generate_traffic_route(
    graph, "9", "11",
    source="EXISTING_SHORTEST_PATH",  # 또는 KEV
    blocked_nodes=["7"], blocked_edges=[],
)
# path, source, calls, blocked_nodes, blocked_edges
```

A*는 `plan_route()`, AI는 `preview_llm_route()`를 사용한다.
두 함수에 회피 인자를 선택 사항으로 추가해서 기존 호출은 유지했다.
물리 엣지 회피는 양방향을 함께 제외한다. 지도 원본·전역 예약표는 경로 생성 과정에서 바꾸지 않는다.
출발·목적지를 제외하는 우회는 거부한다. 별도 대기 장소나 목적지 변경은 이 기능의 범위 밖이다.
AI 생성이 실패하면 해당 우회 후보를 제외하고 이유를 남긴다. 같은 요청을 A* 성공으로 바꿔 기록하지 않는다.

## 켜는 방법과 직접 보기

공유 버전에서는 기존 런처의 기본 동작을 유지하고, 새 일반 주문 교통조정을 시험할 사람이 아래 환경 설정으로 명시적으로 활성화한다. 현재 PC의 자동 활성화용 런처 변경은 기능 공유에서 제외한다. 직접 uvicorn을 실행할 때도 같은 환경 설정을 사용한다.
이미 켜 둔 백엔드는 파일 변경만으로 바뀌지 않는다. 완료·취소 주문도 메모리에 있으므로 재시작하면 화면의 이력이 초기화된다.
현재 진행 중 주문·복귀를 끝낸 뒤 필요하면 이력을 보관하고 재시작한다.

```bash
cd ~/dev/Logistics_AI
export FMS_ORDER_TRAFFIC_ENABLED=1
# 이번 교통조정 검증은 A* 경로와 KEV 교통조정을 분리해서 사용한다.
export FMS_ORDER_ROUTE_SOURCE=EXISTING_SHORTEST_PATH
export FMS_TRAFFIC_SELECTION_POLICY=KEV_STRATEGY_ORDER
./start_fms.sh
```

시뮬·AI로 바꾸고 일반 주문을 등록한다. 처음에는 A 1개 주문 한 건으로 확인한다.
주문 목록에서 해당 주문을 누르면 **주문 상세 → 교통조정**에 검사 대기·선택 중·적용 결과와 경로를 표시한다.
다음으로 A 주문과 C 주문을 넣어 공유 통로와 픽업대가 다른 흐름을 확인한다.
경로가 하나뿐이면 KEV를 호출하지 않는 것이 정상이다.
화면의 일반 주문 공급 시나리오도 같은 일반 주문 처리기를 사용하므로 설정이 켜져 있으면 이 연결을 거친다.

`GET /api/mode`의 `order_traffic.enabled`·`route_source`·`selection_policy`로 실제 프로세스 설정을 확인한다.
`GET /api/orders`의 각 주문에는 `traffic_coordination`과 최근 12개 `traffic_coordination_history`가 있다.
적용 기록 파일은 `logs/order-traffic/decisions.jsonl`이다.
2026-10-20 선택 진단 후 요청·응답 원문 기록을 추가했다.
2026-10-20 10:18(KST) 백엔드 재시작으로 반영했다. 기존 주문 이력 42건·로봇 위치·운영 모드를 복원했고, 이후 KEV 선택 요청부터 `logs/order-traffic/selection-inferences.jsonl`에 REQUEST·RESPONSE·ERROR를 요청 ID별로 기록한다.
모델 응답 기록은 실행 승인이 아니다. 기존 최신 상태·예약 검사는 유지한다.
같은 날 일반 주문 6건·17개를 기존 관제에서 처리하며 KEV 호출 5회의 전송 요청·응답을 확인했다. [반영·원문 기록 확인 결과](experiments/selection-capture-live-20261020.md).
이전 시험은 원문이 없어 관측 상태로 재구성했으며, [진단 결과](experiments/order-traffic-selection-diagnosis-20261020.md)에 한계를 명시했다.

| 설정 | 기본과 의미 |
| --- | --- |
| `FMS_ORDER_TRAFFIC_ENABLED` | 코드 기본값 0. 위 실행 예시는 1로 명시하며 시뮬·AI에서만 적용 |
| `FMS_ORDER_ROUTE_SOURCE` | MODE: 기존 주문 경로 방식 유지. EXISTING_SHORTEST_PATH: A*. KEV: 기존 AI 생성기 사용 |
| `FMS_TRAFFIC_MODEL` | kev-08b. 교통조정용 모델을 경로 생성 모델과 별도 설정 |
| `FMS_TRAFFIC_SELECTION_POLICY` | 코드 기본값 KEV. 위 실행 예시는 KEV_STRATEGY_ORDER로 전략 순서를 제안받고 코드가 최종 선택한다. MIN_EXPECTED_TIME은 검사 완료 후보 중 예상 시간이 최소인 후보를 코드로 선택하며 모델 오류의 자동 대체 기능은 아님 |
| `FMS_TRAFFIC_REROUTE_LIMIT` | 2. 한 이동 요청에서 우회 경로 생성 요청 상한. 0~8 |
| `FMS_TRAFFIC_WAIT_SECONDS` | 60초. 예약 가능한 경로가 없을 때 대기 상한 |
| `FMS_TRAFFIC_SELECTION_SECONDS` | 10초. 선택·개별 우회 생성 응답 한도 |

기존 흐름으로 시험하려면 `FMS_ORDER_TRAFFIC_ENABLED=0`으로 시작한다.
운영 목표를 바꾸는 설정은 주문 중간에 변경하지 않는다.
계산 방식도 시뮬·AI 모드에서 일반 주문 교통조정을 거친다. 경로가 여러 개이면 주문 상세에 ‘코드가 예상 시간이 가장 짧은 경로를 선택’으로 표시한다. 후보가 하나면 기존처럼 KEV를 호출하지 않는다.
2026-10-20: 같은 주문표 2종을 두 방식으로 비교해 32건·112개를 완료했다. 실행 후 원래 KEV 설정으로 복원했다. [일반 주문 비교 결과와 한계](experiments/order-traffic-policy-comparison-20261020.md).

## 비교 기준과 현재 한계

2026-10-21에는 같은 주문 18건·57개를 두 방식으로 각각 처리해 **총 36건·114개 완료**를 확인했다.
앞 로봇이 작업대로 가는 동안 다음 로봇이 같은 픽업대로 이동했고, 홈 복귀 전 새 주문을 받는 사례도 관측했다.
KEV 출고 완료 185.64초·코드 182.29초이며 한 쌍 비교만으로 우열을 확정하지 않는다.
[연속 처리 결과·대기 분석·원래 설정과 위치 복원](experiments/continuous-order-validation-20261021.md).

지금은 다른 로봇의 계획을 고정하고, 새 요청의 **예약 대기를 포함한 예상 목적지 도착 시간**을 비교한다.
여러 로봇의 통과 순서를 다시 정하는 기존 정지 상태 JointAction 시험과 다른 범위다.
초기 `KEV` 정책에서는 코드가 후보 경로를 만들고 검사한 뒤 KEV가 선택한다. 위 실행 예시의 `KEV_STRATEGY_ORDER`는 생성 전 전략 순서 제안과 코드의 최종 선택을 사용한다.
모델의 다음 검토 동작 제안·분기 보관·한도 뒤 코드 보완은 [별도 정지 상태 시험](experiments/deferred-recovery-20261020.md)으로 구현했다.
현재 평균 도착 예상이 좋다고 전체 주문 처리량이 개선됐다고 해석하지 않는다.
계산은 기존 예약기의 속도와 안전 여유를 사용하며 회전·실기체 정지 거리의 정밀 예측은 아니다.

공유 자원은 겹침의 단서이며 그 자체가 동시 충돌을 뜻하지 않는다. 실제 채택은 예약 검사를 통과해야 한다.
후보 생성은 제한된 회피 노드 묶음·통로를 사용한다. 모든 MAPF 해나 양보 이동을 탐색하지 않는다.
새 요청끼리의 완전한 공동 최적화, 이동 중 로봇의 강제 정지·경로 교체, 동적 양보 생성, 장기 대기 보호는 이후 작업이다.

### 2026-10-20 같은 픽업대의 다음 로봇 출발 수정

기존 `_wait_for_pickup_turn()`은 같은 픽업대가 주문에 포함되어 있고 앞 주문이 `IN_PROGRESS`이면 계속 기다렸다.
픽업을 마치고 작업대로 이동하는 중에도 막는 과도한 조건이었다.
이제 이번 방문 노드·픽업 단계·실제 점유를 확인한다. 앞 로봇이 해당 노드를 떠나면 뒤 로봇의 이동 요청을 허용하고, 실제 통행은 예약기로 검사한다.
동일 주문의 두 번째 픽업대도 접근할 때 별도로 차례를 확인한다.
