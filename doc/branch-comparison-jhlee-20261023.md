# 우리 교통조정과 최신 jhlee 비교·push 전 점검

2026-10-23. 사용자가 지정한 원격 `jhlee`의 최신 커밋을 조회·받아 비교했다. 작업 브랜치를 바꾸거나 병합·커밋·push하지 않았다. 관제·모델·실기체 명령도 보내지 않았다.

## 한 문장으로 비교

**우리 일반 주문은 예약 검사된 경로 후보 중 하나를 고르는 방식이고, jhlee는 충돌 구간·로봇 우선순위·대기 또는 우회를 KEV가 단계별로 판단하는 방식이다.**

`jhlee`는 이제 충돌 노드나 대기 노드만 우리에게 전달하는 전처리 코드가 아니다. 경로 생성뿐 아니라 교통조정과 시뮬 실행 연결까지 구현돼 있어 우리 모듈과 책임이 겹친다. 아래 비교에서 ‘우리 방식’은 실제 일반 주문에 연결된 `order_traffic_service`를 뜻한다. 별도 정지 상태 조정안·다중 양보 탐색 실험은 구분한다.

## 흐름을 쉽게 보면

### 우리 일반 주문

```text
이번에 새로 출발할 로봇 한 대
 → 기본 경로 생성: 최근 검증은 A*
 → 다른 로봇 점유·남은 경로·예약 확인
 → 기존 생성기로 제한된 우회 경로 준비
 → 후보별 예약 가능성·예상 도착 시간 계산
 → 0개면 한도 내 대기 / 1개면 바로 적용 / 여러 개면 KEV 또는 코드가 선택
 → 최신 상태로 예약 재검사·확정
 → 기존 FMS 주행
```

이미 움직이는 다른 로봇의 계획·예약을 유지한다. KEV에는 전체 그래프 대신 로봇 상태·남은 경로와 후보별 거리·예약 대기·전체 예상 시간 등을 준다. 목표는 **다른 계획을 고정했을 때 새 요청의 예상 도착 시간 최소**다.

### jhlee의 시뮬 MAPF 연결

```text
다른 로봇 점유·경로 정보를 참고해 AI 경로 생성
 → 출발 전 경로를 Pending으로 등록
 → 이미 주행 중인 Active 경로와 Pending 경로 수집
 → 코드가 겹치는 노드·물리 엣지를 묶음
 → KEV: 어느 공유 구간부터 해결할까?
 → KEV: 누구를 먼저 보낼까? (choice 또는 score)
 → KEV: 기다릴까, 우회할까, 보류할까?
 → 필요하면 대기 노드 선택 / 기존 AI 생성기로 우회 경로 요청
 → 제안 결과를 FMS 상태와 대조
 → 기존 예약·주행기로 실행 요청
```

선택지가 하나면 API를 생략하고, 우선순위 score 모드는 여러 로봇 질문을 한 API 요청으로 묶는다. 따라서 ‘항상 4회 호출’처럼 고정된 횟수가 아니다. 초기 경로·우회 생성도 분기마다 모델 호출이 생길 수 있다.

## 핵심 차이

| 항목 | 우리 일반 주문 | 최신 jhlee |
| --- | --- | --- |
| KEV의 주요 역할 | 검사된 경로 중 선택 | 해결할 구간·우선 로봇·행동·대기 위치 판단 |
| 입력의 지도 정보 | 후보 경로·거리 중심, 전체 인접 그래프 없음 | compact 그래프·인접 엣지·로봇 경로 포함 |
| 시간 기준 | 예약 대기를 포함한 후보별 도착 예상 제공 | MAPF 엔진은 `eta_available=false`, `time_prediction_used=false` |
| 후보 생성·검사 | 경로 후보를 먼저 만들고 예약 사전 검사 | 공간 중복·우선순위 순환·대기 위치 제약으로 선택지를 제한하고, 우회는 선택 뒤 생성·검증 |
| 결과 | 선택 경로 적용 또는 대기·실패 기록 | 우선순위 관계, WAIT/REROUTE/HOLD 제안, 최종 경로 |
| 기존 주행 변경 | 다른 로봇 계획을 유지하고 새 요청만 적용 | 실행 게이트는 Active 로봇을 대기·우회시켜야 하는 제안을 거부하고 Pending만 검토 |
| 실행 연결 | `FMS_ORDER_TRAFFIC_ENABLED`, 시뮬·AI. 런처 기본 1 | `FMS_SIM_MAPF_ENABLED=1`일 때 시뮬·AI 게이트 사용. 코드 기본 0 |
| 최근 확인 범위 | 실제 KEV 일반 주문 완료·연속 흐름·코드 예외 시험, 성능 이점 미입증 | 이번에는 코드 읽기·대체 모델 응답을 쓰는 검사 33개. 실제 KEV 처리량 우열은 이번에 시험하지 않음 |

**jhlee가 시간표를 전혀 쓰지 않는다는 뜻은 아니다.** KEV-MAPF 판단 엔진이 ETA를 쓰지 않는 것이고, 최종 FMS는 양쪽 모두 기존 시간 예약·실제 점유 검사를 사용한다. 우리 방식도 시각만 믿고 점유 검사를 건너뛰는 구조가 아니다.

`jhlee`의 Active+Pending 수집은 모든 순간의 주행 상태를 그대로 해결하는 범용 연결은 아니다. 엣지 중간이면 `MID_EDGE`로 보류하고, 수집 전후 상태가 바뀌거나 기존 Active를 다시 대기·우회시켜야 하면 실행 승인을 하지 않는다. 현재 게이트에서 WAIT는 새 로봇이 현재 노드에서 기다리는 형태만 허용하고 다른 대기 노드까지의 이동은 별도 검토 대상으로 거부한다.

## 둘을 그대로 연결하면 안 되는 이유

현재는 ‘jhlee가 입력만 만들고 우리 부분이 MAPF를 완성하는’ 분업이 자동으로 성립하지 않는다. 두 가지 완성 교통조정 흐름을 연달아 호출하면 같은 상황의 우선순위·우회·출발 허가를 중복 결정할 수 있다.

팀이 먼저 정할 것은 **교통 전략을 고르는 계층과 최종 예약·실행을 맡는 계층의 주인**이다. 예를 들어 jhlee의 전략 제안을 활용하더라도 최종 FMS 예약·상태 검사는 한 경계에서 수행하도록 설계해야 한다. 이는 통합 제안이며 이번에 코드를 바꾼 것은 아니다. KEV가 맡는 판단이 더 넓다고 자동으로 더 빠르거나 안전하다고 결론 내리지 않는다.

양쪽에서 동시에 수정한 파일은 네 개다.

- `backend/app/services/order_route_dispatcher.py`: 두 교통조정 흐름 중 어디로 보낼지 결정하는 지점.
- `backend/app/services/llm_route_preview.py`: 우리는 회피 노드·엣지 인자를 추가했고 jhlee는 `traffic`·방향 정보를 추가했다.
- `backend/app/services/route_service.py`: 우리 회피 인자와 jhlee의 특수 노드 우회 정책·지도 캐시 변경을 함께 검토해야 한다.
- `backend/app/services/traffic_manager.py`: 우리 사본 예약 검사·확정 기능과 jhlee의 진입 점유 판정 변경을 함께 검토해야 한다.

파일 하나를 다른 쪽 버전으로 통째로 바꾸면 새 인자나 실행 연결이 사라질 수 있다. 우리 연속 주문·픽업 차례 개선·원문 기록·비교 도구는 재사용 후보지만 양쪽 KEV 판단기의 우열은 동일 입력·동작·검사·한도로 따로 확인해야 한다. 과거 우리 다중 양보 확장 실패를 이번 jhlee 엔진의 실패로 계산하지 않는다.

## 지금 push할지에 대한 판단

**개인 `woozoo` 브랜치에 백업·팀 공유용으로 push할 시점은 맞다. main 병합이나 최종 성능 완료 선언과는 구분한다.**

이번 비교 문서를 쓰기 전 상태는 기존 수정 17개·새 파일 92개로 총 109개였다. 대부분 핵심 개발이 미커밋이므로 `git push`만 하면 기존 환경 설치 관련 커밋 5개만 올라가고 새 교통조정은 올라가지 않는다. 비교 문서·인수인계 보완도 이후 커밋 대상에 포함해야 한다.

추천 순서:

1. 현재 기능·검사·화면 연결에 필요한 파일과, 중단 실험·분석·문서를 구분한다. 서로 참조하는 새 모듈을 빠뜨리지 않는다.
2. 예를 들어 ‘교통조정·연속 주문·검사’와 ‘실험 분석·검증·인수인계’처럼 설명 가능한 커밋으로 나눈다. 별도 실험을 실제 일반 주문 기본 기능인 것처럼 설명하지 않는다.
3. 확인한 개인 브랜치 `woozoo`에 push한다. 현재 `main`이나 `jhlee`로 직접 push하거나 자동 병합하지 않는다.
4. 팀과 책임을 맞춘 뒤 네 공통 파일을 포함한 병합·통합을 별도 수행한다.

사용자는 현재 비교와 push 여부를 물었으므로 이번에는 커밋·staging·push를 실행하지 않았다. 과거 실험과 원본 로그를 지우거나 무관한 파일을 정리하지도 않았다.
