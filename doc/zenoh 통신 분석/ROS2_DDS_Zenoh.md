# ROS2 DDS / Zenoh 60초 통신 성능 정밀 분석 보고서
**실험 식별자:** `bench_20261019_183111`  |  **분석 기준:** 2026-10-19  |  **범위:** 원본 48개 조건 및 ACK 패킷 30,637건
> 측정 사실, 통계적 관측, 원인 가설을 구분했습니다. 실제 ROS2 표준 메시지 타입을 사용하지만 센서 데이터는 합성이며, FMS와 Nav2의 실제 처리시간을 측정한 실험은 아닙니다.
## 1. 요약 및 핵심 결론
- **전체 48/48 조건 완료:** 3 방식 × 8 메시지 × 2 방향. 각 조건 60초, 1회. 송신 계획 30,960건, 스케줄 누락 0건.
- **저전압 이벤트 0건:** 48조건 로봇 자원 샘플의 현재 undervoltage/throttle 이벤트 0건. 이전 OpenCR 전원 환경에서 0x50005가 발생했고 USB-C 독립 전원 후 이번 실험은 중단 없이 완료했으나, 인과관계를 단일 실험으로 확정하지 않는다.
- **RTT 경향:** CycloneDDS가 대부분의 LaserScan/PointCloud2/이미지 조건에서 낮은 평균 RTT. Zenoh는 소형 상태 메시지에서 경쟁력 있으나 일부 로봇→PC 조건에서 수초 지연.
- **로봇 CPU:** 앱 프로세스 평균 FastDDS 56.14%, CycloneDDS 58.45%, Zenoh 58.94% (1 코어=100%). 이전 약 100%보다 개선되었으나 프로그램 자체의 실행비용이 포함되어 있다.
- **수신≠ACK:** Zenoh Odometry robot→PC에서 수신 1,166건, ACK 1,095건. Zenoh 전체 수신 확인률 99.30%, ACK 확인률 98.61%.
- **누락은 군집형:** 연속 37~40 메시지 누락 구간이 DDS 직접통신에도 나타난다. 네트워크 패킷 손실이라고 단정할 수 없으며, 송신 스케줄/프로세스/발견과 재연결/응답 큐 단계별 계측이 필요하다.
## 2. 실험 목적, 장비와 통신 아키텍처
이 실험의 목적은 동일한 ROS2 인터페이스로 FastDDS 직접, CycloneDDS 직접, CycloneDDS+Zenoh Bridge/Router의 종단 간 동작을 비교하는 것이다. 메인 PC `192.168.0.16`, Robot2 `192.168.0.102`, Zenoh Router `192.168.0.16`을 사용했다. 로봇은 Raspberry Pi4 기반 TurtleBot3이며 이전 OpenCR 경유 전원에서 저전압이 관찰돼 USB-C 독립 전원으로 변경한 뒤 진행했다. 실제 물리 링크(유선/Wi-Fi), 라우터 버전/명령행, 커널, 펌웨어, RMW 상세 파라미터, NTP/Chrony 오프셋 수치는 이 ZIP에 없어 독립 검증할 수 없다.

| 방식 | ROS2 RMW / 통신 경로 | 메인 Domain | 로봇 Domain |
|---|---|---|---|
| FastDDS | FastDDS 직접 DDS | 67 | 67 |
| CycloneDDS | CycloneDDS 직접 DDS | 67 | 67 |
| Zenoh | CycloneDDS → zenoh-bridge-ros2dds → Router → Bridge → CycloneDDS | 67 | 68 |


**통제 조건:** 60초/조건, 반복 1회, 프로파일별 고정 Hz/페이로드, 동일 방향을 테스트. **비통제 조건:** 실행 순서 FastDDS→CycloneDDS→Zenoh, 단일 반복, 배경 OS 프로세스 및 네트워크 상태. 절대적인 미들웨어 우열이나 통계적 유의성은 입증하지 못한다.

## 12. 실제 FMS 적용 판단
**현재 단계의 권고:** Robot 내부 센서/Nav2/제어는 로컬 DDS로 유지하고, 관제에 필요한 저용량 상태/명령/이벤트만 필터링해 Zenoh Router로 중계하는 기존 아키텍처를 유지하는 것이 합리적이다. Python 통신 테스트의 평균 RTT는 실제 로봇 작업 반응시간과 동일하지 않으며 아래 분리가 필요하다.
- **명령/상태:** Twist 20Hz, Odometry 20Hz 수준의 소형 메시지는 일반 상황에서 10ms 내외 RTT. Zenoh odom 한 조건의 6.5초 지연 사례는 상태 최신성 감시와 timeout/failsafe 필요성을 보여준다.
- **LaserScan:** 로봇 내부 Navigation의 10Hz sensor path는 Zenoh 외부 Router를 꼭 통과시킬 필요가 없다. 필요 시 대시보드용 스캔 다운샘플/낮은 주기 전송.
- **영상/PointCloud:** 원본 이미지/포인트를 Zenoh로 장시간 전송하는 것에는 누락과 지연이 존재. 관제용 썸네일/JPEG 압축/별도 스트리밍 후보. 압축의 처리 비용도 재검증.
- **Nav2 Action/Service:** 이번 데이터는 Action 요청/피드백/결과의 신뢰성을 직접 검증하지 않는다. 별도 시나리오에서 3대 로봇 동시 주행과 작업 수행 상태를 계측해야 한다.

## 14. 데이터 품질 / 해석 제한 / 누락된 증거
1. **반복 1회:** 조건별 평균의 분산 및 신뢰구간을 산출할 수 없다. `rtt_run_avg_std_ms`가 NaN인 것은 정상이다.
2. **합성 메시지:** 메시지 타입과 페이로드 근사는 실제이나 센서 프레임 획득, 이미지 인코딩, 로봇 제어 및 FMS 기능은 빠져 있다.
3. **서로 다른 RMW 경로:** FastDDS vs CycloneDDS vs CycloneDDS+Zenoh는 브리지와 Router를 추가로 포함. 순수 Zenoh 단독 전송 성능 비교가 아니다.
4. **시계 오프셋:** 파일의 `raw_one_way_ms_unverified_*`는 검증 없이 인용하면 안 된다. RTT는 monotonic 기준.
5. **전원 샘플링:** 샘플된 현재 이벤트 0과 완전한 전압 안정은 다르다. USB-C 어댑터 모델과 실제 입력전압 계측값 미제공.
6. **ACK 기록 제한:** `packet_traces.csv`는 ACK 성공분만 포함. 영구 미도착인지 타임아웃/정리로 빠진 것인지 파일만으로 결론 불가.
7. **실행 시각:** wall clock으로 기록된 ACK 시각은 관측 순서를 나타내는 용도로 사용. 각 호스트 단방향 시각 차이는 Chrony offset을 검증하지 않았음.
8. **통계 가중치:** 방식별 전체 평균 RTT를 개별 조건 평균의 단순 평균으로 결합하면 작은 메시지와 큰 메시지가 동일하게 취급된다. 목적에 따라 조건별 비교가 우선이다.
9. **물리망 상태:** NIC 링크속도/에러카운터, RSSI, iperf3 결과가 없어 패킷 손실/지연 원인을 네트워크 구간으로 특정 불가.

## 16. 종합 판정
**측정 성과:** USB-C 분리 전원 상태에서 정해진 48개 조건을 모두 마쳤고, 저전압 감지 이벤트 0, 송신 스케줄 누락 0, 총 30,637개 ACK RTT 표본을 확보했다. CycloneDDS는 평균 RTT에서 특히 대용량 메시지에 우세했고, Zenoh는 평상시 소형 메시지를 처리할 수 있지만 일부 방향에서 응답 지연/미ACK 군집의 리스크가 남았다.**
**원인 판정:** 이전 테스트의 안전 중단은 측정된 저전압/Throttling 때문이라는 것은 확실하다. 이번 Zenoh ACK 지연과 연속 미수신의 구체 원인을 특정할 프로세스 내부 단계별 로그, 네트워크 상태, 시계 동기 검증 자료는 부족하다.**
**권고:** 현재 FMS용 Zenoh 아키텍처는 유지하되 제어와 안전 기능은 로봇 로컬에서 처리하고, 관제 수신 데이터에 freshness/timeout를 두며, 발견된 대규모 누락·장시간 지연에 대해 3회 반복 및 단계별 로그로 재검증한다.

### A.3 해석상 한계

- ACK가 없는 메시지는 `packet_traces.csv`에 개별 발송 시각이 없다. 따라서 해당 SEQ에 대응하는 실제 수신 실패 시각은 식별할 수 없다. 누락 구간의 시간은 목표 Hz로 근사할 수 있을 뿐이다.
- `resource_samples.timestamp_ns`도 벽시계 시각으로 기록되어 있으므로 CPU, 메모리, 전원 샘플을 ACK 이벤트 시간대와 연결할 수 있다. 다만 1초 샘플링으로 수 ms~수백 ms 순간적인 CPU 스파이크를 배제할 수 없다.
- 주요 지연이 발신 앱, DDS, Bridge, Router, 수신 콜백 중 어디서 발생했는지는 구간별 monotonic 계측 없이는 확인할 수 없다.
- Python 벤치마크에서 ACK 전송과 실제 ROS2 토픽 송신의 완료 의미가 다를 수 있으므로 ACK 누락을 IP 패킷 손실로 단정하지 않는다.
