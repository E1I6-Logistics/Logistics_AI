## KEV 추천 후 코드가 보완하는 새 시험 (2026-10-20)

**전략 탐색 비교 → KEV 추천 + 코드 보완 · 두 대가 비켜주고 R1 통과**를 추가했다.
미룬 검토 순서를 보관하고, 모델 제안 8회 뒤에는 남은 한도 안에서 코드가 검토를 이어받는다.
관제에서 5단계 이동·복귀를 약 21.29초에 완료했다. 완료 주문 102건 보존, 위치 관측 177회에서 중복 점유 0회.

## 현재 다중 양보 배치와 입력 진단 (2026-10-20)

같은 네 다중 양보 항목을 **R1이 작업대 N3에서 N0로 복귀**하는 상황으로 바꿨다.
R2는 출구 N11을 막고 N6로, R3는 입구 N10을 막고 N8로 양보한다.
N11·N10 모두 비워야 하는 구조이며, N6·N8 정차는 가상 시험의 허용 설정이다.

이전 요청의 원본·점유 관계 추가·짧은 설명을 대조했지만 검사 수 개선은 없었다.
후보 표시 순서에 따라 선택이 바뀌는 사례는 확인했다. 기본 입력은 기존 표현을 유지한다.
[현재 배치·이전 기록의 분석·실제 모델 대조 결과](experiments/workstation-return-input-diagnosis-20261020.md).

## KEV가 다음 검사 동작을 제안하는 시험 (2026-10-20)

**전략 탐색 비교 → KEV 제안 · 두 대가 비켜주고 R1 통과**를 추가했다.
아직 예약 검사 전인 이동 동작에서 KEV가 하나를 제안하고, 코드가 검사한 실패 이유를 다음 요청에 전달한다.
최대 8회 제안·128회 예약 검사·8단계·10초이며, 완성된 계획을 찾기 전에는 로봇을 움직이지 않는다.

공정한 대조는 같은 DFS 실행기의 **코드 순서** 항목이다. 첫 격리 비교에서 둘 다 13회 검사로 해결했고,
KEV는 제안 8회로 계획 시간이 늘었다. 관제에서는 KEV 제안 8회·코드 검사 13회 후 5단계를 약 19.42초에 완료했다.
전체 자동 검사 233개 통과. [새 역할·한도·실제 요청·비교 결과](experiments/kev-guided-recovery-20261020.md).

## 두 로봇의 양보 순서를 자동으로 찾는 시험 (2026-10-20)

**기본 동작 확인 → 자동 찾기 · 두 대가 비켜주고 R1 통과**를 추가했다.
고정된 5단계를 주지 않고 로봇별 진행·양보·복귀 경로만 제공한다. 코드는 중간 순서를
예약 검사하면서 완성된 이동 순서를 찾고, 기존 실행기로 이동시킨다. KEV 호출은 없다.

탐색은 최대 128회 검사·8단계·1초로 제한한다. 한도에 걸리면 찾다 만 순서는 실행하지 않는다.
관제에서 예약 검사 20회·탐색 약 0.007초로 5단계를 찾았고, 복귀까지 약 18.58초에 완료했다.
현재는 평균 시간 최적화가 아닌 실행 가능한 순서 찾기다. 전체 자동 검사 225개 통과.
[입력 차이·검사 횟수의 뜻·확인 결과](experiments/two-yield-search-20261020.md).

## 두 로봇이 양보하는 고정 계획 시험 (2026-10-20)

기존 관제의 **기본 동작 확인 → 두 대가 비켜주고 R1 통과**를 추가했다.
R2가 N9→N2, R3가 N10→N8로 비켜준 뒤 R1이 N1→N9→N10→N0을 통과하고,
R2·R3가 원래 자리로 돌아오는 5단계다. 전체 계획을 기존 예약 검사로 확인하고 이전 단계의 도착 후 다음 단계를 실행한다.

시뮬·AI에서도 **KEV 호출은 0회**다. `fixed_plan`에 직접 적은 계획의 실행 확인이며,
KEV가 이 순서를 자동으로 찾았다는 뜻이 아니다. 일반 주문의 후보 생성 방식은 바꾸지 않았다.
관제 실행은 18.31초에 완료했고, 167회 위치 관측에서 중복 점유는 없었다.
이번 변경 후 전체 자동 검사 215개와 프런트 타입 검사·빌드가 통과했다.

배치·설정·직접 실행 방법·결과·남은 작업은 [두 로봇 양보 시험 상세](experiments/two-yield-real-map-scenario-20261020.md)에 정리했다.

## 느린 후보를 고른 원인 진단 (2026-10-19)

‘R2도 목적지로 이동해야 할 때’의 저장된 실패 요청으로 입력 표현을 바꿔 시험했다.
**후보와 지시문을 유지해도 상태 입력에 따라 선택이 바뀌는 것을 확인했다.**
각 조건은 원래·반대 후보 순서로 2회씩, 총 4회 요청했다. 모델 가중치·런타임 설정은 동일하다.

| 바꾼 부분 | 예상 평균이 짧은 후보 선택 |
| --- | --- |
| 기존 전체 입력 그대로 | 0/4 |
| 지시문만 짧게 | 0/4 |
| 상태에서 지도만 제거 | 0/4 |
| 상태를 경로 요청 목록만으로 축약, 후보·지시문 동일 | 4/4 |
| 상태를 빈 객체로 변경, 후보·지시문 동일 | 4/4 |
| 상태·후보 설명·지시문 모두 간단하게 | 4/4 |

원본 입력은 5,695토큰이고, 지도만 뺀 경우는 2,209토큰, 경로 요청만 남긴 경우는 2,071토큰이었다.
비슷하게 짧은 입력에서도 결과가 달랐으므로 단순히 길이만이 원인이라고 결론내리지 않는다.
**상태에 포함된 설정·부가정보와 표현 방식의 영향이 유력하다. 어느 개별 필드가 원인인지는 아직 분리하지 않았다.**
간단한 작은 수 선택은 수치·표시 순서를 교환한 대조에서 8/8회 맞았다. 큰 수 선택 대조에서는 순서에 따라 틀리기도 했다.
따라서 모든 숫자 비교를 못한다거나, 반대로 항상 정확하다고 결론내리지 않는다.

설치된 KEV의 API 변환 코드에서 지시문이 모델 입력으로 전달되고, 모델 점수가 가장 높은 후보를 반환하는 것을 확인했다.
선택은 무작위 샘플링이 아니다. 런타임의 상태 자르기 설정은 꺼져 있었고 모든 진단 요청은 정상 응답했다.
파인튜닝·모델 교체·운영 선택기 변경은 하지 않았다. 입력 표현 진단 48회와 상태 대조 24회는 앞선 54회 비교와 별개이며 로봇을 실행하지 않았다.

결과: 표현 방식 진단 (`logs/traffic-joint-actions/selection-diagnosis-20261019.md`, 로컬 보관),
상태 정보 대조 (`logs/traffic-joint-actions/selection-diagnosis-state-controls-20261019.md`, 로컬 보관).
실행 도구: traffic_selection_diagnosis.py (`backend/simulation/traffic_selection_diagnosis.py`, 로컬 보관).

### 이전 횟수의 정확한 의미

이전의 45회 이동은 다음 다섯 상황을 **3가지 선택 방식 × 각 3회** 실행한 것이다.

1. R2가 먼저 움직여 길을 비울지, R1을 우회시킬지.
2. 정차한 R2가 비켜줄지, R1을 우회시킬지.
3. 기존 지도의 3대 통과 순서.
4. 같은 3대의 요청 순서를 반대로 바꾼 경우.
5. 별도 작은 교차로에서 이동 거리 차이가 있는 3대의 순서.

무작위 실제 주문 45건이 아니다. 선택 분기와 비용 차이를 비교하도록 직접 구성한 작은 상황들이다.
기존 관제에 제공 경로와 초기 위치를 넣는 시험 정의를 재사용하고, 네 번째 상황은 요청 순서를 뒤집어 만든 변형이다.

이전의 9회 대기는 한 막힘 상황을 **3방식 × 3회** 실행한 것이다.
R1은 9→7→11로 가야 하는데 R2가 7번에 정차하고, 이 시험에는 우회·양보 경로를 제공하지 않았다.
준비된 이동 후보가 검사에서 제외되어 `HOLD_ALL`만 남았고, 새 이동 요청을 보내지 않아 현재 위치를 유지했다.
이동 단계 0개·시뮬 경과 0초로 `UNRESOLVED`를 반환하는 **즉시 보류 결정 검사**다.
일정 시간 기다렸다가 통로가 비면 다시 출발하는 동작이나 모든 우회 가능성을 시험한 것은 아니다. 이 9회에서 KEV 호출도 0회다.

계산 방식의 15/15는 ‘이동 가능한 5상황 × 3회’에서 코드가 제공 후보의 예상 평균 중 최솟값을 고른 횟수다.
예상 값이 5.03초와 10.59초라면 `min()`으로 5.03초 후보를 고른다. 계산 방식이 같은 정의와 일치한 것은 당연하다.
KEV도 같은 기준을 지키는지 비교하기 위한 기준이며, 실제 시간의 예측 오차·전체 최적 경로·물류 처리량을 검증한 수치는 아니다.

## 선택 방식 세 가지 비교 (2026-10-19)

**이번 결과: 현재의 작은 시험에서는 KEV가 계산값 비교보다 좋은 선택을 한다는 근거를 얻지 못했다.**

세 방식 모두 같은 입력, 후보, 사전 검사, 격리 가상 이동기를 사용한다.
경로는 미리 제공해서 경로 생성 성능의 영향을 빼고, 선택만 비교했다.
일반 주문·켜져 있는 관제 상태를 바꾸지 않는 CLI 시험이다. 관제 화면의 선택기는 계속 KEV다.

| 선택 방식 | 정확한 규칙 |
| --- | --- |
| 요청 순서 | 원래 이동 요청의 완료 순서가 접수 순서에 가까운 후보 우선. 양보 준비 동작은 건너뜀. 동률은 경로 유지, 총 거리 순 |
| 계산상 빠른 방법 | 예상 평균 이동 완료 시간(실행 기준) 최소. 같은 값이면 최장 차례 대기, 총 거리, 요청 순서로 결정 |
| KEV | 같은 실행 기준 평균 최소를 최우선으로 명시. 총 거리나 양보 후 복귀 완료를 먼저 최적화하지 말라고 전달 |

KEV가 계산상 느린 방법을 골라도 응답을 바꾸지 않고 그 후보로 실행했다.
제공 후보에서 **예상 평균 이동 완료 시간(실행 기준)**이 가장 작은 값과 같은 것을 고른 횟수만 센다.
이것은 예측 시간 기준의 일치이며, 관측 시간이 가장 짧다는 증명이나 모든 가능한 경로의 최적해를 의미하지 않는다.

### 1차 결과

- 6상황 × 3방식 × 3회 = **54회 실행**.
- 이동 가능한 5상황은 45회 모두 완료. 진행 불가 대조 상황 9회는 전원 대기·미해결로 유지.
- 중복 점유 0건, 실행 실패 0건.
- 여러 후보 중 실제 KEV 선택은 **15회**. 전원 대기는 후보가 하나여서 KEV를 호출하지 않음.
- KEV는 제공 후보 중 예상 평균 최소와 **7/15회 일치**. 계산값 비교는 정의상 15/15회 일치.
- KEV 선택 요청 지연은 평균 약 **0.447초**. 일반 코드 방식은 이 시험에서 약 0.0002~0.0003초.
- 관련 자동 검사 **110개 통과**. 이 숫자는 실제 모델의 선택 횟수·정확도와 별개.

이 표의 값은 **관측 평균 이동 완료 시간(실행 기준·가상 시계)**의 반복 3회 평균이다.

| 대표 상황 | 요청 순서 | 계산상 빠른 방법 | KEV |
| --- | --- | --- | --- |
| R2도 목적지로 이동해야 할 때 | 10.85초 | 5.30초 | 10.85초 |
| R2가 길을 막고 서 있을 때 | 9.65초 | 8.70초 | 9.02초 |
| 기존 지도의 3대 통과 | 23.63초 | 22.50초 | 23.34초 |

위 완료 시간은 **가상 시계**다. 실제 모델 선택 지연과 합쳐 실측 완료 시간이라고 하지 않는다.
격리 이동기는 단계 사이에 0.5초의 가상 간격을 두므로 이전 경과 시간 시험과 절대값을 섞어 비교하지 않는다.
각 방식끼리는 같은 실행기를 사용한다.

반복 1·3회는 원래 후보 표시 순서, 2회는 반대 순서다. 반대로 보여줬을 때 선택이 달라진 상황이 있다.
표시 순서의 영향을 의심할 관측이며, 반복 수가 작고 다른 입력도 함께 바꾸어 시험하지 않았으므로 원인을 단정하지 않는다.
같은 몇 상황을 반복한 결과이므로 7/15를 실제 물류 전체에서의 정확도로 해석하지 않는다.
장기 대기 보호는 아직 동률 참고 기준뿐이다. 연속 요청에서 특정 로봇이 계속 밀리지 않는지도 별도로 검증해야 한다.

## 추가한 기능: 예상 시간과 실제 시간 보기 (2026-10-19)

교통조정 시험 결과 아래의 **‘예상 시간과 실제 시간 보기’**를 펼치면 다음을 본다.

- 각 방법의 **예상 평균 이동 완료 시간(실행 기준)**과 총 경로 거리. 선택한 방법에는 체크 표시.
- 선택한 방법의 **관측 평균 이동 완료 시간(실행 기준)**과 **평균 요청 처리 시간(판단 포함)**.
- 준비 시간, 선택 요청에 걸린 시간, 가장 오래 출발 차례를 기다린 시간.
- 아직 도착하지 않은 로봇. 전원 대기·중단·미완료는 0초 성공으로 계산하지 않는다.

새 API 응답을 만들려면 이 변경 이후의 백엔드가 실행되어야 한다. 기존에 켜둔 서버는 재시작 후 반영된다.
진행 중인 주문을 지우는 재시작은 이번 작업에서 하지 않았다.

### 숫자는 어떻게 계산하나

예상 값은 **경로의 노드 사이 거리 합계÷현재 시뮬 속도 0.2m/s**다.
한 단계씩 이동하므로 앞 로봇이 걸리는 시간이 다음 로봇의 차례 대기가 된다.
회전·추론·추가 예약 정지·도착 확인 지연까지 예측하는 정밀한 값은 아니다.

| 값 | 기준 |
| --- | --- |
| 예상 평균 이동 완료 시간(실행 기준) | 실행 시작을 0초로 둔, 원래 이동 요청 로봇들의 목적지 도착 예상 시각 평균 |
| 관측 평균 이동 완료 시간(실행 기준) | 같은 실행 시작 기준으로 도착을 확인한 시각 평균. 전원이 도착해야 확정 |
| 평균 요청 처리 시간(판단 포함) | 이동 요청 접수부터 이번 목적지 도착까지의 평균. 현재 기록은 요청 수집 후 관측 시간 + 입력에 명시된 이전 대기 |
| 준비 시간 | 경로 준비·후보 만들기·검사·선택 요청·실행 전 확인. 선택 시간은 이 안에 포함 |
| 선택 시간 | 선택 함수에 요청한 뒤 결과를 받을 때까지. 모델 호출 외 검사·통신 시간도 포함 |
| 출발 차례 대기 | 실행 시작부터 해당 로봇에 첫 이동 단계를 요청할 때까지. 실제 움직이기 시작한 시각과는 다를 수 있음 |
| 단계 시간 | 이동 요청부터 도착 확인까지. 예약 정지·확인 지연도 포함 |

물리적으로 바퀴가 움직인 시간과 예약 때문에 멈춘 시간을 아직 따로 나누지 않는다.
이미 정차 중인 로봇은 이동 요청 평균에서 제외하지만, 양보 후 복귀의 단계 시간과 경로 거리는 남긴다.
원래 이동 요청 중 미완료가 있으면 평균은 `null`로 유지한다. 미완료 로봇을 빼고 완료 로봇만의 평균으로 성공을 표시하지 않는다.
이전 대기 시간은 시나리오에서는 0초, 일부 격리 입력에서는 30초 등으로 공급한 시험값이다. 실제 과거 대기를 측정했다는 뜻은 아니다.
준비 시간에는 선택 시간이 포함되므로 두 값을 다시 더하지 않는다. 모든 동작 완료 시간은 양보 지원 로봇의 복귀까지 포함하며 이동 요청 평균과 다르다.
경로 거리는 그래프 경로 기준이며 실기체가 실제로 주행한 궤적의 측정값은 아니다.
관제 실행의 `actual_metrics.clock`은 `WALL_MONOTONIC`, 빠르게 돌리는 격리 CLI는 `VIRTUAL_SIMULATION`이다.
가상 시계의 완료 시간을 실제 경과 시간으로 해석하지 않는다. CLI의 실제 선택 지연은 `decision_wall_seconds`로 따로 남긴다.

## 먼저 해볼 테스트: FMS 입력 연결

선택하고 **경로 생성: A*** 또는 **경로 생성: KEV**를 고른 뒤 테스트 실행을 누른다.
기본값은 A*이며 **교통조정: KEV**는 두 경우 모두 동일하다.
진행 중 주문이 있으면 완료·취소·복귀 후 실행한다.
일반 AI 주문 등록 버튼은 이 테스트의 진입점이 아니다.

```text
시나리오 목적지: R1=11, R2=8 (R3는 0에 정차)
  → 별도로 선택한 방식으로 경로 생성 (기본 A*, 선택 KEV)
  → order/current_node/node/result.path 형태의 경로 DTO
  + 같은 잠금에서 수집한 전체 로봇 상태·예약·보호 자원
  → build_traffic_situation_input
  → 코드가 조정안 생성·검사
  → 여러 후보면 KEV가 한 번 선택, 후보 하나면 호출 생략
  → 기존 FMS가 선택한 순서로 가상 주행
```

이 테스트의 경로 생성 방식은 관제 operation_mode와 독립적이다. 시뮬·알고리즘과
시뮬·AI 모두 A* 경로 + KEV 교통조정 또는 KEV 경로 + KEV 교통조정을 선택할 수 있다.
A*는 plan_route, KEV는 preview_llm_route(selector=kev, model=kev-08b)를 호출한다.
KEV 경로 생성 실패는
실패로 표시하며 A*로 대체하지 않는다. jhlee의 DTO 형식은 사용하지만 해당 브랜치의
이 정지 상태 시험은 팀원 수집기나 일반 주문 흐름을 직접 받지 않는다. 일반 주문은 별도의 [새 출발 요청 연결](order-traffic-integration.md)을 사용한다. 목적지와 시작 배치는 시나리오가
정하고, 실제 수집한 현재 노드로 경로를 생성한다. `paths` 설정은 없다.

| 검사 | 관찰/통과 기준 |
| --- | --- |
| 자동 입력 | A* 경로 R1=9→7→11, R2=5→7→8. KEV 선택 시 모델이 생성한 유효 경로를 사용. 입력 로그의 route_source는 선택에 따라 EXISTING_SHORTEST_PATH 또는 KEV, traffic_selector는 kev |
| 정적 점유 | 요청 없는 R3도 node:0 점유로 입력되며 주행하지 않음 |
| 조정안 선택 | 생성 경로의 사전 검사를 통과한 후보 중 선택. A1이면 R1, A2이면 R2가 먼저 이동. 특정 ID를 모델의 정답으로 고정하지 않음 |
| 대기/진행 | 첫 로봇이 목적지에 도착한 뒤 두 번째 출발. 노드 7이나 물리 엣지를 함께 점유하지 않음 |
| 완료 | R1=11, R2=8, R3=0. 상태 메시지에 모든 단계 완료 |
| 모델 호출 | route_generation_calls는 KEV 경로 생성 호출 합계(A* 선택 시 0), joint_action_choice_requests는 조정안 선택 0~1회. 총 호출은 둘의 합계이며 단일 후보 단계는 생략 가능 |

API에서도 `POST /api/scenarios/run`에 다음과 같이 경로 출처를 명시할 수 있다.
생략하면 이 시나리오의 기본값 A*를 사용한다. 다른 지도 시험·고정 경로 시험·연속 주문에는
이 옵션을 적용할 수 없고, 일반 주문 경로 생성 정책을 바꾸지 않는다.

## 1. 지금 검증하는 것

교통 상황 → 코드가 교통조정안 생성·사전 검사 → KEV가 조정안 ID 하나 선택
→ 기존 TrafficManager의 예약·구간 허가 → 격리된 MockFmsStore 이동·도착 확인.

- 정지한 가상 로봇 3대, 노드·양방향 공유 물리 엣지당 최대 1대.
- 경로 유지형 A1/A2/A3, 경로 변경형 B_REROUTE/B_YIELD_robot2, 전원 진입 대기 HOLD_ALL.
- 한 조정안의 steps는 순차 실행한다. 우선 단계가 목적지에 도착한 뒤 다음 단계를 시작한다.
  충돌 노드 이탈 직후 다음 로봇을 보내는 최적화는 아직 하지 않는다.
- YIELD는 대기 노드 이동 → 다른 로봇 통과 → 원래 목적지 재개의 세 단계를 포함한다.
- UNRESOLVED는 실행 가능한 이동 조정안을 못 찾은 결과 상태다. 별도 행동이 아니다.
- HOLD_ALL을 선택하면 정지 상태와 노드 점유를 그대로 유지한다.
- 기본 테스트 정책은 검사에 통과한 이동 조정안이 있으면 그중에서 선택한다.
  HOLD_ALL은 이동 조정안이 없을 때만 제공한다. 임의로 진행시키는 것이 아니라,
  기존 FMS 사전 검사와 실행 직전 구간 검사는 그대로 유지한다.

테스트 전용 지도다. 노드 13이나 대기 노드 8은 실제 지도에서 검증한 공간을 뜻하지 않는다.
터미널 실행기는 실제 관제 주문, ROS/Nav2, 실기체에는 명령하지 않는다.
아래의 관제 시나리오 연결은 실제 지도와 기존 가상 로봇을 사용한다.
일반 주문·배차·주행 흐름과 프런트 화면 코드는 수정하지 않았다.

## 2. TrafficSituation 입력

앞 담당자의 기존 요청 형식인 order/current_node/node/result.path를 재사용한다.
다음 한 묶음을 TrafficSituation에 전달한다. 테스트 파일은 지도 중복을 줄이기 위해
공통 graph와 cases를 나누어 저장하고, 실행기가 각 case에 graph를 합쳐 입력한다.

| 필드 | 의미 |
| --- | --- |
| schema_version | traffic-situation/0.1 |
| snapshot_id | 입력 상황 식별자 |
| mode | simulation만 지원 |
| graph | 유향 Route Graph GeoJSON |
| route_requests | 아래 형식의 로봇별 요청 목록. 움직이지 않는 로봇도 포함 |
| config.wait_allowed_nodes | 정지·대기를 허용한 노드 목록 |
| config.zone_occupancy | 기존 jhlee 명칭 재사용. node:0 → robot1 같은 실제 점유 입력 |
| config.reservations | v0.1은 빈 목록만 지원. 승인된 예약이 있으면 거부 |
| config.blocked_nodes / blocked_edges | 사용할 수 없는 노드·물리 엣지. 엣지 방향은 함께 검사 |
| config.reroute_paths | 선택 사항. 미리 생성한 우회 경로 |
| config.yield_paths | 선택 사항. 양보 이동 out 경로와 원래 목적지로의 resume 경로 |
| config.allow_proactive_hold | 기본 false. true인 명시적 실험에서만 이동 가능 상태의 전원 대기 선택도 허용 |

로봇별 요청 예:

```json
{
  "order": {"robot_id": "robot1", "selector": "kev", "model": "kev-08b"},
  "current_node": "0",
  "node": "3",
  "result": {"path": ["0", "13", "3"]},
  "status": "IDLE",
  "occupied_edge": null,
  "request_order": 1,
  "waiting_seconds": 30
}
```

모든 로봇은 노드에 정지해 있고 경로는 생성됐으나 아직 주행을 요청하지 않은 상태다.
진행 중인 로봇·엣지 위 로봇·기존 예약이 있는 입력은 지원하는 척하지 않고 거부한다.
각 로봇의 초기 노드와 zone_occupancy는 정확하게 일치해야 하고 중복 점유는 거부한다.
정차 로봇은 current_node == node, result.path는 노드 하나로 나타낸다.

우회·양보 경로는 이번 테스트에서 입력으로 공급한다. 추가된 FMS 입력 시나리오는
경로 생성 선택에 따라 기존 A* 또는 KEV로 최초 경로를 생성한다. 실행 중에 새 우회 경로를 요청하는
② 연동은 아직 하지 않는다. 제공 경로의 유향 엣지·끝점·차단 구간·예약 가능성은 검사한다.
YIELD의 resume 경로가 원래 목적지로 돌아오는지도 검사한다.

## 3. 조정안과 교통조정 결정

상황·전략·후보·선택 방식은 [설계의 공통 용어](continuous-order-traffic-design.md#traffic-decision-terms)를 따른다.
현재 구현은 완성된 교통조정안 중 하나를 선택한다. 전략부터 제안하는 확장안은 아직 설계 단계다.

| 코드 표현 | 뜻 |
| --- | --- |
| Action | `PROCEED` 이동 / `WAIT` 차례 대기 / `YIELD` 비켜주기 / `REROUTE` 원래 목적지로 다른 길 사용 |
| JointAction | 초기 대기와 순서가 있는 이동 단계들의 묶음. 현재는 앞 단계가 목적지까지 끝난 뒤 다음 단계를 시작 |
| TrafficDecision | 입력 스냅샷 해시와 선택된 조정안 ID. 선택 자체가 실행 승인은 아님 |
| `HOLD_ALL` | 이동 단계를 요청하지 않는 조정안. 몇 초 기다리라는 시간 값이나 성공 결과가 아님 |
| `COMPLETED` | 교통 시험의 원래 목적지·필수 복귀 단계 완료. 일반 주문의 완료와 구분 |
| `HELD` / `UNRESOLVED` | 진행 후보가 있어도 대기를 고른 경우 / 현재 후보로 진행을 찾지 못한 경우 |

오류·중단 표시는 [실행 결과 정의](continuous-order-traffic-design.md#traffic-decision-outcomes)에서 구분한다.
현재 `UNRESOLVED` 대조 시험은 즉시 보류 결정을 검사하며 대기 후 자동 재개까지 검증하지 않는다.

경로 유지형은 첫 진행 대상을 바꾼 N개 조정안을 만들고, 이후 로봇은 FIFO로 배치한다.
모든 N! 통과 순열을 열거하는 설계는 아니다. 실제 점유 때문에 실행 불가능한 조정안은
복사한 상태에서 기존 TrafficManager의 예약·진입 검사를 거쳐 제거한다.

초기 테스트의 선택 기준은 작업 진행·경로 유지·통행 요청 순서·대기 시간을 참고하는 것이었다.
선택 방식 비교부터는 `MIN_MEAN_GOAL_COMPLETION_V1`로 예상 평균 이동 완료 시간(실행 기준) 최소를 최우선으로 명시했다.
같은 값일 때 최장 차례 대기·총 거리·요청 순서를 참고한다. 실제 장기 대기 보호와 전체 물류 처리량은 아직 검증하지 않았다.

모델이 선택한 후보 ID를 받고 로봇 행동·경로는 코드에 등록된 조정안에서 가져온다. 유효한 ID를 받았다는 것만으로 목표에 맞는 좋은 선택이라고 보지는 않는다.
알 수 없는 선택, 입력 변경, 다른 스냅샷의 결정, 실행 직전 새 예약, 중복 적용은 거부한다.
KEV 결정의 fms_execution_approved는 false다. 실제 시뮬레이션 이동은 FMS가 구간별로 검사한다.

## 5. 실행 명령

아래는 Logistics_AI 루트에서 실행한다. 패키지 설치나 전체 FMS 시작은 필요 없다.

### 오프라인: 입력·조정안·실행 연결 확인

```bash
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python -m unittest \
  tests.test_traffic_joint_actions tests.test_fixed_route_reservation -v

PYTHONNOUSERSITE=1 ~/venv/robot/bin/python -m backend.simulation.traffic_joint_actions \
  --selector test --output logs/traffic-joint-actions/test-results.json
```

TEST_DOUBLE은 코드가 선택을 고정한 테스트다. KEV 추론 성공으로 해석하지 않는다.
A2를 강제로 선택해 출발 순서가 실제 바뀌는지 보려면:

```bash
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python -m backend.simulation.traffic_joint_actions \
  --selector test --case three_robot_node --choice A2
```

### 실제 KEV 선택 + 격리 시뮬레이션

KEV 서버가 127.0.0.1:8011에서 0.8B로 준비되어 있어야 한다.

```bash
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python -m backend.simulation.traffic_joint_actions \
  --selector kev --model kev-08b \
  --output logs/traffic-joint-actions/kev-results.json
```

기본 정책에서는 이동 가능한 조정안이 있을 때 HOLD_ALL을 모델에 제공하지 않는다.
allow_proactive_hold=true인 실험에서는 KEV가 HOLD_ALL을 선택해 HELD가 나올 수 있다.
모델 응답을 받은 뒤 다른 ID로 덮어쓰지 않는다. 유효한 ID 반환과 목적지 도착은 따로 확인한다.
우회/양보처럼 유효 조정안이 하나뿐이면 SINGLE_OPTION으로 모델 호출을 생략한다.
all_wait는 단일 조정안이므로 모델 호출 없이 SINGLE_OPTION으로 처리된다.

결과는 logs/traffic-joint-actions 아래 JSON에 선택 출처, 조정안, 단계 이벤트,
최종 노드와 매 tick의 용량 검사 횟수를 저장한다. 이 경로는 Git에서 제외된다.
