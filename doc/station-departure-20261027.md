## 확정한 운영 방식

- robot1/2/3은 각각 N0/N1/N2를 앞 노드로 사용한다. 물리 Station 1/2/3과 노드 번호는 별개다.
- 연결만으로 로봇을 움직이지 않는다. 일반 위치의 로봇은 기존 위치·점유 판정을 거쳐 대기하며, 시작 시 CHARGING이나 재도킹을 요구하지 않는다.
- 일반 IDLE·복귀 로봇의 이동/배차는 현재 위치에서 기존 경로·정지·예약 절차를 사용한다. 담당 앞 노드 점유만을 이유로 직진 이탈을 적용하거나 스위치 OFF/과거 도킹 성공을 요구하지 않는다.
- 정지한 담당 로봇이 담당 앞 노드 주변에 있고 신뢰된 ON이 안정되면, 과거 도킹 성공 기록 없이 CHARGING을 인식한다. 초기 미수신·retained를 ON/OFF로 추정하지 않고 센서 UNKNOWN으로 표시하되, 일반 출발을 센서 때문에 보류하지 않는다.
- 센서는 진행 중인 주문·주행·이탈·DOCKING·PAUSE·비상정지를 덮어쓰지 않는다. 작업이 없는 CHARGING의 안정된 OFF는 자동 이동 없이 IDLE로 전환한다. 충전 접촉을 확인할 수 없으면 CHARGING의 새 배차는 대기하지만 일반 로봇의 배차는 막지 않는다.
- 주문 완료·취소 후 자동 복귀는 앞 노드까지이며 IDLE로 끝난다. 정밀 도킹을 자동으로 호출하지 않는다.
- `/api/command/charging`으로 충전 이동을 명시적으로 요청했을 때만 앞 노드 이동 → 정밀 도킹을 호출한다. 이 명령으로 시작한 정밀 도킹은 기존 Action 성공·새 접촉 검증을 유지하며, 실패를 센서 ON으로 성공 처리하지 않는다.
- CHARGING 중 배차는 주문을 유지하면서 앞 노드까지 직진 이탈한다. 속도 기본값 0.09m/s, 제한 시간 20초. Action 성공과 새 실제 Pose 도착을 확인한 뒤 일반 경로로 진행한다. 스위치 OFF 수신과 MQTT 연결 상태는 승인된 이탈의 완료 조건이 아니다.
- 주문 배정으로 CHARGING이 TASK_ASSIGNED/WAITING으로 바뀌어도 충전 출발 문맥을 보존한다. 출발에 사용한 ON이 그대로 남거나 반복 수신되어도 이탈 후 다시 CHARGING으로 전환하지 않는다. 새로운 OFF→ON 접촉은 다시 인식한다.
- 사용자가 확인한 물리 조건: 도킹 완료 자세에서 앞으로 직진하면 담당 앞 노드로 나온다.
- CHARGING 중 WASD 수동 속도 명령을 허용한다. 수동 조작은 DriveOnHeading이나 앞 노드 도착 검사를 실행하지 않고, 배차 전압 필터도 적용하지 않는다. 자동 주행·이탈·정밀 도킹·정렬·주문·취소 대기 중에는 먼저 정지를 완료해야 수동 속도를 보낼 수 있다.
- 정상 수동 조작은 MOVING, 키를 놓으면 속도 0을 보낸다. 충전 접촉 문맥은 보존하므로 접촉 ON이 남아 있으면 CHARGING으로 돌아가고 안정된 OFF가 확인되면 IDLE로 전환한다. 잠깐 수동 조작한 사실을 자동 이탈 완료로 간주하지 않는다.
- 이탈 실패 PAUSED는 기존 직진 Action과 Nav2의 실제 종료 콜백을 받은 뒤 WASD 수동 복구를 허용한다. 취소 수락·시간 초과만으로 허용하지 않는다. 위치·점유가 미확정이면 기존 예약 보호는 남긴 채 수동 복구하며, 복구 조작 중과 키 해제 후 모두 PAUSED를 유지하여 주문을 자동 재개하지 않는다. 정밀 도킹 실패에는 이 예외를 적용하지 않는다. 비상정지 요청은 PAUSED에서도 가능하며 EMERGENCY_STOP 중에는 수동 이동을 차단한다.

주문 후 자동 복귀가 정밀 도킹까지 이어진 원인은 ESP32 통합 커밋 `fde5d01`의 `charging_return=True`, 복귀 목적 변환 및 CHARGING 종료 조건이었다. 이번 수정에서 일반 복귀와 명시적 충전 요청을 다시 분리했다. heeyeon 배차 방식 때문에 생긴 변경은 아니다.

## 이동 제어와 실행 경계

FMS가 시간만 정해 raw cmd_vel을 반복 발행하지 않는다. 기존 로봇 Nav2에 등록된 `/{robot_id}/drive_on_heading` (`nav2_msgs/action/DriveOnHeading`)으로 제한된 저속 직진을 요청한다. 로봇의 Nav2가 로컬 위치 기반 이동 거리·충돌 검사·시간 제한을 처리한다. 일반 NavigateThroughPoses와 이 Action을 동시에 실행하지 않는다.

- 출발 목표는 담당 앞 노드의 **실제 map 좌표**이다. 계획용 점유 노드 좌표로 실제 도착을 가정하지 않는다.
- 도킹 자세가 앞 노드를 향한다는 운영 전제로, 출발 전 횡오차 3cm·방향차 15도 문턱은 적용하지 않는다. 실제 위치의 최신성·목표의 전방 여부·거리 상한은 확인한다. 자동 제자리 회전이나 방향 반전은 하지 않는다. 공통 MAPF 위치·점유 검사는 유지한다.
- 이탈 중에는 앞 노드를 보호하고 기존 경로의 시간 예약을 보류한다. 이탈 후 같은 required_path를 현재 시각으로 다시 예약한다. AI 경로 선택·MAPF 정책은 교체하지 않는다.
- 이탈 여부는 CHARGING 출발 문맥으로 결정하며 시작 위치·근접 노드만으로 결정하지 않는다. 이미 앞 노드 허용 오차 이내라면 추가 이동 없이 보호를 정리하고 일반 경로를 진행한다.
- Action 성공만으로 완료하지 않는다. Action 종료 시각 이후 수신한 최신 실제 Pose가 앞 노드 허용 범위에 도달했는지도 확인한다. 결과와 Pose 도착의 시차는 기존 도착 확인 제한 안에서 기다린다.
- Action 거절/실패, 로봇 연결 해제, 위치 미갱신, 제한 시간 초과, 앞 노드 미도착, 비상정지 때는 일반 주행을 이어가지 않는다. 이탈 중 스위치 ON 유지·OFF 수신·MQTT 단절/재접속은 이 조건에 포함하지 않는다.
- 취소 응답의 수락만으로 점유를 해제하지 않는다. 직진 Action의 terminal result를 확인한 뒤 기존 Nav2 정지 처리를 완료한다. 늦은 이전 결과는 새 작업을 완료시키지 못한다.
- Action Server를 확인할 수 없을 때 raw cmd_vel로 우회하지 않는다.

일반 시작 위치 때문에 `dock_startup_sensor_wait`나 `dock_restart_unverified`를 만들지 않는다. 실제 도킹/이탈 실패와 취소 미완료는 계속 보류한다. 이탈 실패는 위 조건을 통과한 WASD 수동 복구 또는 명시적 충전소 복귀 명령으로 대응한다. 실패 후 비상정지만 해제하거나 센서 ON을 받아도 주문을 자동 재개하지 않는다.

## 설정과 전압 필터

백엔드 시작 환경변수로 설정하고 변경 후 재시작한다. 아래 값은 초기 보수적 설정이며 장비 실측 검증을 끝낸 값은 아니다.

```dotenv
FMS_STATION_EXIT_SPEED_MPS=0.09
FMS_STATION_EXIT_TIMEOUT_S=20
FMS_STATION_EXIT_TOLERANCE_M=0.03
FMS_STATION_EXIT_MAX_DISTANCE_M=0.25
FMS_REAL_ARRIVAL_CONFIRM_TIMEOUT_S=1.0
```

속도는 m/s, 거리·도착 허용 오차는 m이다. `FMS_STATION_EXIT_TOLERANCE_M=0.03`은 이미 앞 노드 근처인지와 직진 후 실제 도착을 확인할 때 사용하는 값이다. 출발 전 횡오차 검사에는 쓰지 않는다. 최대 직진 거리보다 멀거나 노드가 전방에 없으면 움직이지 않는다. 기존 점유 판정의 `FMS_REAL_DOCK_OCCUPANCY_TOLERANCE_M`도 기본 0.25m이므로, 임의로 이탈 거리만 키워도 모든 시작 위치가 지원되는 것은 아니다. 실측 후 두 범위와 노드 좌표를 함께 확인해야 한다.

실기체 시험에서 전압으로 배차가 막히지 않게 하려면 백엔드 실행 터미널에서 다음처럼 설정한다.

```bash
export FMS_MIN_DISPATCH_BATTERY_VOLTAGE=0     # 전압 검사 OFF
# 원래 기준으로 되돌릴 때:
export FMS_MIN_DISPATCH_BATTERY_VOLTAGE=11.2  # 최근 60초 유효 전압의 최저값 검사
```

전압 조건 OFF는 미수신·낮은 전압으로 새 배차를 제외하는 조건만 해제한다. 도킹·연결·비상정지·위치 검사는 그대로다. 기존 CHARGING 출발 시 잔량(%) 유효성 검사도 유지한다. 실제 `.env`, 실행 중 서버 및 실제 장비 설정은 이번 코드 작업에서 변경하지 않았다.

검증은 ROS/장비 호출 대역으로 수행한다. 현재 실행 중인 서버를 재시작하거나 실제 로봇을 구동하지 않는다. 이번 재설계로 프런트 코드와 AMR 코드는 변경하지 않았다.

ROS 도메인 93/로컬 탐색 및 격리된 시뮬레이션 MQTT 1885를 사용했다. simulation-algorithm에서 HTTP 주문 1건이 N5 픽업 → N3 하역 → N0 복귀 → COMPLETED까지 완료됐다. 이 검사는 이동 속도 1.0m/s로 가속한 모의 실행이며 실제 CHARGING 이탈이나 KEV 서버 연결 검증을 뜻하지 않는다. 검증 서버는 종료하고 기존 8002 서버와 5175 화면은 재시작하지 않았다.

CHARGING 수동 조작 추가 검증: 전후진·좌우회전, ON 유지 중 반복 명령, 키 해제와 OFF 수신의 순서, 수동 정지 후 자동 이탈 유지, 실행 중 Action·대기 요청·취소·주문과의 중복 차단, 비상정지·실패·오프라인 보류, 발행 실패 시 충전 문맥 보존을 ROS 대역으로 검사했다. 관련 검사 111개 통과, 전체 검사 420개 통과·기존 경로 벤치마크 6개 실패. 실제 서버·장비를 재시작하거나 원격 push하지 않았다. 보고된 실기체 WASD 끊김·비상정지 불능의 원인이 해결되었다고 검증한 결과는 아니다.

이탈 실패 수동 복구와 출발 문턱 제거 후 검증: 관련 검사 119개 통과, 전체 검사 428개 통과·기존 경로 벤치마크 6개 실패. 직진 Action과 Nav2 종료 전 차단, 시간 초과만으로 복구 금지, 늦은 실제 종료 후 복구, 경로 정리 불가 시 예약 보호 보존, PAUSED 주문 자동 재개 방지, PAUSED에서 비상정지 요청 및 명시적 해제 전 수동 이동 차단을 확인했다. 횡오차 3cm·방향차 15도 출발 검사는 제거했지만 직진 후 도착 허용 오차 3cm와 미도착 시 PAUSED 처리는 유지한다. 위 검증은 모의 ROS로 수행했으며 변경 코드를 서버·실기체에 적용하지 않았다.

추가로 FastAPI 웹소켓 경로를 통한 CHARGING 속도·정지, 자동 이탈 중 수동 이동 차단, 실제 종료 후 수동 복구 3건이 통과했다. 기존 실기체 WASD 끊김·비상정지 불능은 별도 tester 중복 실행이 원인이었고 해결됐다는 사용자 보고를 받았다. 이는 이번 변경 코드의 실기체 검증 결과와는 별개다.
