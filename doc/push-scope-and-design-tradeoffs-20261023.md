# GitHub에 올릴 범위와 두 교통조정 방식의 장단점

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-23. 현재 변경 110개를 대상으로 참조 관계를 확인했다. 이 보고서 자체는 그 이후 추가한 파일이다. **분류 제안만 작성했으며 파일 삭제·이동, Git 제외 설정, staging·commit·push는 하지 않았다.**

## 먼저 정할 기준

실행에 필요 없다는 이유만으로 검사·실험 자료를 모두 빼지는 않는다. 팀이 같은 결과를 확인할 수 있는 검사와 검증 결론은 공유할 가치가 있다. 반대로 현재 PC의 상태와 개인 대화 지시를 담은 문서는 프로젝트 실행에 필요하지 않다.

현재 시나리오와 자동 검사 구성을 유지하는 최소 기준으로 분류했다. 중단한 연구 코드를 프로젝트에서 완전히 제거하는 일은 별도 변경이다. 파일만 커밋에서 누락시키는 것으로 대신하지 않는다.

## 로컬 보관을 우선 추천하는 문서 3개

| 파일 | 이유 |
| --- | --- |
| `doc/handoffs/KEV_MAPF_CHATGPT_HANDOFF_20261022.md` | 개인 ChatGPT 대화용 지시·현재 PC 상태가 중심. 프로젝트 사용자 설명서와 목적이 다름 |
| `doc/handoffs/KEV_MAPF_HANDOFF_20261022.md` | 로컬 경로·주소·가상 주문 이력·프로세스 복원·개인 작업 지시가 포함된 인수인계 |
| `doc/continuous-order-traffic-design-v0.1.md` | 현재 설계 문서로 대체된 이전 검토안. 별도 초기 설계 이력 공유가 필요할 때만 포함 |

이 파일을 버리자는 뜻은 아니다. 로컬 원본을 보존하고 GitHub 공유 범위에서 제외하자는 제안이다. 팀원에게 초기 설계 이력이 필요하면 v0.1은 보관 문서임을 표시해 올려도 된다.

현재 `continuous-order-traffic-design.md`, `kev-mapf-implementation-map.md` 등은 이 문서들을 링크한다. **제외하기 전에 공유 문서의 연결과 ‘먼저 읽을 문서’ 안내를 바꿔야 한다.** 지금 파일만 빼면 설명 링크가 끊긴다. GitHub용 문서의 로컬 절대경로 링크도 저장소 상대 링크로 정리할 필요가 있다. 이번에는 링크를 일괄 변경하지 않았다.

## 별도 실험 자료로 공유할지 선택할 도구 6개

아래는 현재 앱·시나리오 실행과 전체 자동 검사의 필수 import에서 참조되지 않는 독립 실행 도구다. 일반 주문 기능을 공유하는 데 필수는 아니지만 실험 재현을 원하면 별도 커밋으로 보관할 수 있다.

```text
backend/simulation/order_traffic_exact_replay.py
backend/simulation/order_traffic_saved_choice_review.py
backend/simulation/order_traffic_selection_diagnosis.py
backend/simulation/traffic_recovery_deferred_comparison.py
backend/simulation/traffic_recovery_dependency_comparison.py
backend/simulation/traffic_selection_diagnosis.py
```

이 중 `order_traffic_saved_choice_review.py`는 최근 세 선택 분석의 재현 도구이고, 다른 파일들도 기존 실험 문서에서 링크한다. ‘쓸모없는 파일’로 단정해 삭제하지 않는다. 제외를 선택한다면 문서에 도구·원본 기록을 별도 보관했다고 표시해야 한다. 당시 `logs/`가 없는 저장소 복제본만으로는 과거 결과의 완전한 재분석이 되지 않는다.

## 특정 시점의 수동 확인 도구 3개

```text
tests/blocked_return_live.py
tests/blocked_return_reuse_live.py
tests/verify_blocked_return.py
```

복귀 차단·복귀 후 재사용을 직접 확인한 도구다. pytest가 자동 수집하는 검사 파일은 아니다. 특히 재사용 도구는 고정된 과거 기록 폴더를 선행 조건으로 읽는다. 팀이 그 시험을 그대로 재현할 필요가 없으면 로컬 또는 별도 실험 자료로 보관할 수 있다. 공유한다면 실행 조건·고정 경로를 명시하고 기능 검사와 구분한다.

다음 두 도구는 자동 실행 필수는 아니지만 팀에서 연결 확인에 쓰기 좋아 공유를 추천한다.

- `tests/order_traffic_live_smoke.py`: 별도 가상 로봇과 실제 KEV 연결 확인. 기본 실행이 모델을 호출할 수 있으므로 수동 검사임을 유지한다.
- `tests/random_order_observer.py`: 기존 관제에 제한된 주문을 공급하고 관측. `--run`에서 관제를 조작한다.

## 이름에 실험이 들어 있어도 지금 빼면 안 되는 코드

정적 import를 함수 내부까지 추적한 결과 새 Python 55개 중 13개는 앱·현재 시나리오에서 직접·간접 참조되고, 31개는 자동 검사 자체 또는 검사 의존 모듈이다. 나머지 11개가 위의 독립 실행 도구다. 여기서 31은 검사 통과 건수가 아니라 파일 수다.

주요 참조 예:

```text
일반 주문 order_traffic_service
 → traffic_joint_actions의 공통 식별값 생성 기능
 → traffic_metrics 등 공통 기능

현재 시나리오 화면
 → scenario_service
 → traffic_joint_action_scenario
 → traffic_joint_actions
 → traffic_recovery_search
 → guidance / dependencies / input / motion

자동 검사
 → traffic_recovery_comparison / candidate_diagnosis / benchmark 등 보조 모듈
```

따라서 `traffic_recovery_*.py`를 중단한 실험이라는 이유로 전부 빼면 현재 화면의 양보 비교나 자동 검사 실행이 깨질 수 있다. 현재 화면·검사를 그대로 공유하려면 관련 모듈도 함께 올려야 한다. 정말 줄이려면 시나리오·검사·공통 함수의 참조를 함께 정리하는 별도 변경과 재검증이 필요하다.

다음 데이터도 유지해야 한다.

- `tests/traffic_scenarios.json`: 앱이 직접 읽는 시나리오 설정이다. tests 폴더에 있다고 모두 검사 전용인 것은 아니다.
- `tests/order_scenarios.json`: 주문 시나리오 검사 도구의 입력.
- `tests/traffic_situation_cases.json`: 조정안·지표·비교 검사 입력.
- `tests/traffic_recovery_benchmark_cases.json`: 기존 대표 상황 준비 도구의 입력.

현재 설계·실행 방법·성공과 실패의 검증 결론은 공유를 추천한다. 세부 실험 기록을 덜 올리더라도 KEV의 효과가 입증되지 않았다는 결론이나 중단 이유를 숨기지 않는다.

## 저장소에 넣지 않을 생성물·환경

`.env`, `logs/`, 가상환경, `frontend/node_modules/`, `frontend/dist/`, Python·pytest 캐시는 소스 공유에 필요하지 않다. `.env`, logs, node_modules, dist, pytest 캐시의 Git 제외 상태를 확인했다. `.env.example`은 제외하지 않고 팀 공통 설정 예시로 유지한다.

모델 가중치·ROS 빌드 결과·실행 PID·복원 스냅샷도 소스 커밋에 넣을 대상이 아니다. 과거 근거를 팀에 전달해야 하면 로그를 따로 보관·전달할 수 있고, 필요한 작은 시험 입력은 검토해 fixtures로 구성할 수 있다. 원본 로그를 전부 강제 추가하지 않는다.

## 두 방식의 장단점

아래 ‘우리 방식’은 일반 주문에 연결된 경로 후보 선택을 뜻한다. [최신 jhlee 코드와의 상세 비교](branch-comparison-jhlee-20261023.md)와 분리된 다중 양보 실험을 혼동하지 않는다.

| 관점 | 우리 방식 | jhlee 방식 |
| --- | --- | --- |
| 비유 | 검사가 끝난 길들의 예상 시간을 보고 하나를 고름 | 교통 담당자가 해결 구간·통행 순서·대기/우회 방침부터 정함 |
| 구현·운용 장점 | 새 요청 한 대만 조정하고 기존 계획을 유지해 연결 범위와 영향이 비교적 명확 | KEV가 실제 통행 우선순위와 행동 선택에 참여해 AI가 맡는 역할이 더 직접적 |
| 판단 근거 | 후보별 거리·예약 대기·합계가 있어 선택을 수치로 설명·비교하기 쉬움 | 지도 연결·점유·경로·우선 관계를 바탕으로 공간적 조정 전략을 제안할 수 있음 |
| 호출 비용 | 일반 주문은 단일 후보면 0회, 여러 후보면 선택마다 호출. 상태 변경 시 재검사는 별도 | 구간·우선순위·행동·대기 위치·우회 생성에서 호출이 생길 수 있어 상황에 따라 지연이 늘 수 있음 |
| 주요 한계 | 만든 후보에 없는 해법은 고를 수 없고 전체 로봇의 공동 최적화를 하지 않음 | 여러 모델 판단의 오류·상태 변화·보류를 함께 관리해야 해 구현과 검증이 더 복잡 |
| AI의 현재 가치 | 이미 계산한 최솟값만 고르는 목표에서는 코드보다 나은 점을 입증하지 못함 | 역할은 넓지만 실제 처리량·완료 시간의 개선은 같은 조건의 비교로 입증해야 함 |
| 시간 기준 | 후보별 예상 시간 계산의 정확성에 의존 | MAPF 판단 엔진에는 ETA가 없어 어느 제안이 더 빠른지 직접 비교하기 어려움 |
| 실제 실행 경계 | 코드의 최종 예약·점유 재검사 필요 | 똑같이 최종 FMS 검사가 필요. 현재 게이트는 Active 변경이나 엣지 중간 상태를 보류 |

‘jhlee는 AI, 우리는 코드’라고 나눌 수는 없다. 둘 다 코드로 경로·상태를 검사하며 KEV를 판단 일부에 쓴다. 차이는 **모델에게 판단을 맡기는 위치와 범위**다. jhlee가 ETA 없이 판단한다고 FMS 시간 예약까지 없는 것은 아니고, 우리도 예약 시각만 믿고 실제 점유를 무시하는 방식이 아니다.

현재 목표가 검증 가능한 일반 주문 운영이라면 우리 코드 선택을 기준선으로 유지하기 쉽다. AI가 통행 전략을 정하는 연구 목적에는 jhlee의 구조가 더 가깝다. 그러나 실기체 안전이나 처리량에서 어느 쪽이 더 낫다고 결론 낼 새 비교는 하지 않았다. 두 전체 판단기를 연달아 실행하는 대신 전략 제안과 최종 실행의 책임을 한 번씩 정해야 한다.

## 추천하는 이번 업로드 범위

1. 기능 실행·현재 시나리오·자동 검사·필수 데이터와 팀용 설계·검증 결론은 포함한다.
2. 개인 인수인계 2개와 이전 설계 보관본은 로컬 보관을 우선 제안한다. 제외하기 전에 공유 문서의 링크를 정리한다.
3. 독립 실험 CLI 6개·특정 수동 도구 3개는 팀이 재현 자료까지 원하는지에 따라 별도 묶음으로 선택한다. 불필요하다고 삭제하지 않는다.
4. 기록 생성물은 계속 제외하고 `git add -A`로 전부 넣지 않는다. 실제 커밋은 검토한 명시적 파일 목록으로 준비한다.

전체 110개 파일별 분류는 `logs/push-audits/20261023/publication-plan.json`과 같은 폴더의 `publication-plan.md`에 있다. 의존성 근거는 `python-dependencies.json`이다. 이 로그들은 현재 Git 제외 영역이고 실제 커밋 목록이 아니다.
