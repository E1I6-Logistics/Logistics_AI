# KEV 후보 이름·표시 순서 분리 시험

2026-10-20, 한국 시간. [직전 입력 진단](workstation-return-input-diagnosis-20261020.md)에서 확인한 표시 순서 영향을 후보 ID 영향과 분리했다. **표시 순서를 바꾸면 이동 선택이 달라졌지만, 전체 계획 탐색이 좋아지지는 않았다.** 일반 주문·관제 설정·실행 중인 로봇 위치는 변경하지 않았다.

## 무엇을 유지하고 바꿨나

모델은 실행 중인 `jaredpalmer/kev-0.8b@v1.0`, CUDA, torch, bfloat16이다. 지시문, 로봇 위치·목표·경로, 최근 검사 기록과 허용 동작은 유지했다. 후보를 검사 결과에 따라 미리 제거하거나 정답을 모델에 주지 않았다.

| 조건 | 후보 이름 | 이동 내용을 나열하는 순서 |
| --- | --- | --- |
| 기존 이름·기존 순서 | 그대로 | 그대로 |
| 변경 이름·기존 순서 | 한 칸씩 변경 | 그대로 |
| 기존 이름·반대 순서 | 그대로 | 뒤집음 |
| 변경 이름·반대 순서 | 한 칸씩 변경 | 뒤집음 |

전체 동작이 5개인 상황에서는 `M1→M2, M2→M3, M3→M4, M4→M5, M5→M1`로 이름만 바꿨다. 실제 이동은 동일하다. 모델이 고른 변경 이름은 시험용 변환기에서 원래 동작 ID로 되돌린다. 반환 확률도 같은 대응으로 되돌리고, 서버에 보낸 요청·응답 원본과 대응표를 별도로 보존한다. 모델 응답이 후보에 없으면 오류로 처리하며 다른 선택으로 대체하지 않는다.

이 대응은 한 상황의 모든 탐색 상태에서 동일하다. 동작을 3개만 제공한 미해결 상황에서는 그 3개의 ID를 한 칸씩 변경했다. **모든 이름이나 모든 순열을 비교한 시험은 아니다.**

## 같은 질문 재현: 이름보다 순서 영향이 컸다

원본은 현재 N3 복귀 배치의 실행 기록 (`logs/traffic-joint-actions/run-82971e17a43a4d90b0086bd9b97ee8f9.json`, 로컬 보관)에 저장된 모델 요청 8개다. 각 요청의 가상 위치·선택 전 상태를 그대로 재현했다. 두 번 반복하므로 **8개 질문 × 4조건 × 2회 = 실제 KEV 요청 64회**다. 조건별 실행 순서는 회전·반전했다.

평가용 예약 검사 결과는 모델에 전달하지 않았다. 다음 표는 모델이 제안한 **그 한 단계까지의 이동을 검사했을 때 통과한 횟수**이며, 전체 막힘 해결이나 시간 최적화 성공률이 아니다.

| 조건 | 한 단계 검사 통과 |
| --- | ---: |
| 기존 이름·기존 순서 | 8/16 |
| 변경 이름·기존 순서 | 8/16 |
| 기존 이름·반대 순서 | 12/16 |
| 변경 이름·반대 순서 | 12/16 |

같은 질문끼리 비교하면 다음과 같다. 여기서 다른 선택은 **이름을 원래대로 돌려서 비교한 실제 이동 내용의 차이**다.

| 바꾼 요소 | 유지한 요소 | 선택한 이동이 달라진 쌍 |
| --- | --- | ---: |
| 이름만 | 기존 표시 순서 | 0/16 |
| 이름만 | 반대 표시 순서 | 2/16 |
| 표시 순서만 | 기존 이름 | 8/16 |
| 표시 순서만 | 변경 이름 | 10/16 |

각 16쌍은 8개 질문을 두 번 반복한 수다. 독립적인 새 상황 16개가 아니다. 네 조건 각각에서 동일 요청의 두 번 선택은 모두 일치했다. 따라서 이번 표의 차이를 반복 시 무작위 응답으로만 설명할 수는 없다. 다만 표본이 작고 이름 변경도 한 종류라, 모든 입력에서의 영향을 확정하지 않는다.

이름 변경 영향이 나타난 것은 반대 순서의 7번 질문 한 종류였다. 이름 영향을 완전히 없다고 단정할 수 없고, **이 표본에서는 순서 영향이 더 자주 나타났다.**

## 전체 계획 탐색: 순서를 뒤집어도 개선되지 않았다

저장 질문 재현과 별도로, 아래 세 상황을 처음부터 탐색했다. 코드 DFS는 상황별 한 번, KEV DFS는 네 조건을 각각 두 번 실행했다. 코드 3회와 KEV 탐색 24회, 합계 **격리 탐색·실행 27회**다.

| 상황 | R1 이동 | R2 양보·복귀 | R3 양보·복귀 |
| --- | --- | --- | --- |
| 작업대 N3 복귀 | N3→N11→N7→N9→N10→N0 | N11↔N6 | N10↔N8 |
| 새 작업대 N4 복귀 | N4→N12→N8→N10→N0 | N12↔N11 | N10↔N9 |
| 해결 동작 누락 | N3 복귀와 동일 | 제공 | R3 양보 경로 미제공 |

새 N4 배치에서도 N4의 유일한 출구 N12와 N0의 유일한 입구 N10을 모두 비워야 한다. 둘 중 하나를 차단하면 A* 경로 생성이 실패하는지 자동 검사했다. 대기 노드는 이 격리 시험에만 허용한 위치다. 일반 주문의 양보 노드 규칙이나 실제 주문 상태를 변경한 것은 아니다.

모두 **검사 128회·이동 8단계·탐색 10초** 한도다. KEV는 추가로 **제안 8회·개별 응답 2초** 한도이며, 같은 동작·검사기·코드 DFS 실행기에서 다음 동작 선택만 바꿨다. 각 상황의 공통 입력 해시와 한도, 검사·요청 원본은 결과 JSON에 기록했다.

| 방식 | N3 복귀 검사 수 | N4 복귀 검사 수 | 해결 동작 누락 검사 수 |
| --- | ---: | ---: | ---: |
| 코드 DFS | 13 | 13 | 5, 미해결 |
| KEV 기존 이름·기존 순서 | 13 / 13 | 13 / 13 | 5 / 5, 미해결 |
| KEV 변경 이름·기존 순서 | 13 / 13 | 13 / 13 | 5 / 5, 미해결 |
| KEV 기존 이름·반대 순서 | 13 / 13 | 15 / 15 | 5 / 5, 미해결 |
| KEV 변경 이름·반대 순서 | 13 / 13 | 15 / 15 | 5 / 5, 미해결 |

`13 / 13`은 두 번의 별도 탐색 결과다. 해결 가능한 두 배치의 KEV 시험 16회는 모두 최종 통과·복귀까지 완료했고, 매번 모델 제안 8회가 필요했다. 코드 DFS의 계획 시간은 약 0.005초, KEV 방식은 약 0.820~0.892초였다. 모델 호출이 포함된 실제 경과 시간이며 가상 로봇 이동 시간과 다르다. 작은 표본이므로 조건별 수십 밀리초 차이는 개선으로 해석하지 않는다.

동작 누락 상황은 코드와 KEV 모두 미해결이었다. KEV는 매번 2회 요청했고, **새 이동을 실행하지 않았다.** 길이 비면 나중에 다시 출발하는 연속 대기를 시험한 것은 아니다.

격리 가상 이동에서 노드·물리 엣지 중복 점유 위반은 0회였다. 실기체·일반 주문의 연속 실행 검증은 아니다.

## 결론과 다음 판단

후속 [저장 답변의 해결 가능성 분석](recovery-answer-analysis-20261020.md)에서 ‘지금 이동 가능하지만 이후 통과를 막는 선택’을 따로 구분했다. 순서를 바꿨을 때 늘어난 한 단계 통과가 실제 해결 능력 개선이 아니었던 이유를 확인할 수 있다.

- 이름·순서 변경만으로 KEV가 교통 상황을 더 잘 판단하게 됐다는 근거는 얻지 못했다.
- 다음 한 단계 검사 통과가 늘어도 전체 탐색의 검사 수가 줄지는 않았다. 일찍 복귀하는 이동은 당장 가능해도 뒤의 통과를 다시 막을 수 있다.
- 순서를 뒤집는 설정은 채택하지 않았다. 기존 ID·순서·입력 표현을 유지한다.
- 현재 예제에서는 코드 DFS보다 KEV가 검사를 줄이지 못했고 모델 요청 시간이 추가됐다. KEV 효과를 입증한 결과로 사용하지 않는다.
- 같은 모델의 이름·표현 변경 시험을 계속 늘리기보다, 다음 설계 검토에서 **해결 성능·검사 비용을 줄일 구체적인 판단을 맡길 수 있는지**를 먼저 판단한다. 일반 주문 연결이나 파인튜닝 필요성을 이번 결과만으로 결정하지 않는다.

총 모델 요청은 **재현 64회 + 전체 탐색 중 144회 = 208회**다. 자동 검사 244개 통과는 이 요청 횟수와 별개이며, ID 변환의 정확성·알 수 없는 응답 거부·상태 보존·평가 결과 미전달·새 배치의 실행 및 기존 회귀 검사를 포함한다. 기존 경고 4개는 그대로다.
