# 두 로봇 양보 순서를 자동으로 찾는 시험

**현재 배치 변경:** 같은 시나리오 항목의 시작점·경로는 R1=N3→N0, R2=N11, R3=N10으로 바꿨다. [현재 배치·새 비교](workstation-return-input-diagnosis-20261020.md). 아래 N1 배치의 입력·관측 값은 당시 기록이다.

2026-10-20. 기존 관제의 **기본 동작 확인 → 자동 찾기 · 두 대가 비켜주고 R1 통과**에 추가했다. 일반 주문·배차·실기체 주행에는 자동 연결하지 않았다. KEV 호출은 없다.

## 이전 시험과 달라진 점

| 구분 | 이전 고정 계획 | 이번 코드 자동 탐색 |
| --- | --- | --- |
| 입력 | 실행할 5단계를 순서대로 지정 | 로봇별 진행·양보·복귀 경로와 탐색 한도 |
| 누가 먼저 움직이는가 | 사람이 지정 | 코드가 가능한 순서를 찾아 결정 |
| 사전 검사·실행 | 기존 예약 검사·가상 이동기 | 같은 검사·이동기 |
| KEV 호출 | 0회 | 0회 |

시작 배치는 R1=N1(목적지 N0), R2=N9(정차), R3=N10(정차)이다. N1 출구인 N9와 N0 입구인 N10을 모두 비워야 한다. 대기 위치 N2·N8은 이번 가상 시험에서 허용한 위치다.

이번 입력에 `fixed_plan.steps`는 없다. 다음처럼 움직일 수 있는 경로를 주되, 전체 실행 순서는 주지 않는다.

```json
{
  "paths": {"robot1": ["1", "9", "10", "0"]},
  "yield_paths": {
    "robot2": {"out": ["9", "2"], "resume": ["2", "9"]},
    "robot3": {"out": ["10", "8"], "resume": ["8", "10"]}
  },
  "recovery_search": {"max_checks": 128, "max_steps": 8, "max_seconds": 1.0}
}
```

**양보 위치·경로를 지도 전체에서 자동으로 찾은 것은 아니다.** 이번에는 허용한 이동들을 안전한 순서로 묶는 기능을 확인한다. 우회 경로를 새로 만드는 기존 경로 생성 기능도 바꾸지 않았다. 공급한 `reroute_paths`가 있으면 같은 탐색의 선택 동작으로 사용할 수 있다.

## 어떻게 찾는가

1. 각 로봇에 대해 가능한 동작을 만든다. 원래 경로로 진행, 제공된 우회 경로로 진행, 양보 위치로 이동, 양보 후 원래 목적지로 이동이다.
2. 현재 상태에서 한 로봇을 움직인 순서를 구성한다.
3. 실제 로봇 대신 복사본에서 기존 `TrafficManager`로 예약·진입을 검사한다. 다른 로봇이 막고 있으면 그 시도를 제외한다.
4. 통과한 중간 상태에 다음 이동을 붙여 본다. 같은 로봇별 상태에 도달한 중복 순서는 다시 살피지 않는다.
5. 이동 요청이 있던 로봇의 도착과 양보한 로봇의 복귀까지 검사한 완성 계획만 반환한다.
6. 실행 직전 원래 입력과 현재 관제 상태를 다시 확인하고, 같은 전체 계획을 재검사한다. 이전 로봇 도착을 확인한 뒤 다음 단계로 넘어간다.

이 방법은 **너비 우선 탐색(BFS)**이다. 1단계짜리, 2단계짜리 순으로 검사한다. 이번 목표는 허용 동작 안에서 실행 단계가 적은 해결 순서를 먼저 찾는 것이다. 평균 도착 시간이나 물류 처리량을 최적화한 결과로 해석하지 않는다.

탐색 중에는 아직 복귀를 붙이지 않은 양보 상태도 살펴야 한다. 따라서 중간 상태 검사에서만 최종 복귀 확인을 보류한다. **실행할 완성 계획과 실행 직전 검사는 복귀 확인을 생략하지 않는다.**

## 한도의 의미

| 설정 | 기본 시험 값 | 뜻 |
| --- | --- | --- |
| `max_checks` | 128회 | 탐색 중 중간·완성 순서에 대한 예약 검사 횟수 합계 |
| `max_steps` | 8단계 | 한 계획에 붙일 수 있는 순차 이동 수 |
| `max_seconds` | 1초 | 탐색의 경과 시간 한도 |

검사 횟수는 로봇 이동 횟수나 KEV 호출 횟수가 아니다. 실행 직전 재검사는 탐색 횟수와 별개다. 시간은 검사 사이와 검사 직후에 확인한다. 실행 중인 동기 검사 하나를 강제로 끊지는 않지만, 늦게 끝난 검사 결과로는 출발하지 않는다.

| 탐색 결과 | 처리 |
| --- | --- |
| `FOUND` | 전체 검사에 통과한 계획을 실행 직전 다시 검사 |
| `CHECK_LIMIT`, `TIME_LIMIT`, `STEP_LIMIT` | 완성되지 않은 계획을 실행하지 않고 대기 |
| `EXHAUSTED` | 이번에 제공한 움직임으로 해결 순서를 못 찾음. 이동 없이 대기 |

실패는 모든 경로나 모든 방법으로 해결할 수 없다는 증명이 아니다. 현재 범위는 **정차한 로봇, 활성 예약 없음, 제공한 경로, 로봇별 양보 최대 1회, 한 단계씩 순차 이동**이다. 반복 양보, 이동 중 계획 교체, 자동 대기 위치 탐색은 아직 없다. 대기 후 운영자 요청으로 전환하는 전용 상태도 이번 변경에 포함하지 않았다.

## 확인 결과

정답 순서를 제공하지 않은 검사에서 다음 계획을 찾았다.

**R2 양보 → R3 양보 → R1 통과 → R2 복귀 → R3 복귀**

예약 검사 20회 중 통과 12회, 예약 불가 8회였다. 통과한 중간 순서를 포함한 숫자이며, 완성 계획 20개를 찾았다는 뜻이 아니다. 찾은 완성 계획은 5단계다. 종전의 한 로봇만 양보시키는 생성기는 같은 입력에서 전원 대기만 남았다.

전체 자동 검사 **225개 통과**, 프런트 타입 검사·빌드 통과. 추가 검사는 두 로봇 양보·복귀, 양보 경로 누락, 차단 엣지, 대기 불허 노드, 탐색 한도, 탐색 중 정지 후 출발 차단, 실제 모드 실행 거부를 포함한다. 네 번째 정차 로봇과 서로 다른 로봇 번호를 넣은 검사도 통과했다. 다수 로봇의 처리 속도·해결률을 검증한 결과는 아니다.

기존 관제의 시뮬·AI에서 자동 탐색을 실행한 결과는 다음과 같다.

| 항목 | 관측 결과 |
| --- | --- |
| 탐색 시간 | 약 0.007초 |
| 탐색 중 예약 검사 | 20회: 통과 12회, 예약 불가 8회 |
| R1 도착 | 준비·탐색 포함 약 12.73초 |
| 두 로봇 복귀까지 전체 완료 | 약 18.58초 |
| 최종 위치 | R1=N0, R2=N9, R3=N10 |
| 위치 관측 | 168회, 노드·물리 엣지 중복 점유 0회 |
| KEV 경로 생성 / 조정안 선택 | 0회 / 0회 |
| 기존 주문 | 완료 이력 102건 보존, 시험 전후 주문 API 내용 일치 |

자료: 관측 결과 (`logs/traffic-joint-actions/recovery-search-live-20261020-172538.json`, 로컬 보관), 실행 상세 (`logs/traffic-joint-actions/run-c470ee43f8e24d829af7ad904a87913c.json`, 로컬 보관), 완료 화면 (`logs/traffic-joint-actions/recovery-search-completed-20261020.jpg`, 로컬 보관).

고정 계획 시험보다 빠르거나 느린지 비교하도록 통제한 실험은 아니다. 이번에는 정답 순서를 주지 않아도 찾아서 실행하는지를 확인했다. 노드·엣지 점유 검사는 실기체의 연속 물리 공간 충돌 검증을 대신하지 않는다.

직접 보려면 [관제](http://100.81.82.30:5173/)에서 **시뮬 · AI → 기본 동작 확인 → 자동 찾기 · 두 대가 비켜주고 R1 통과 → 테스트 실행**을 선택한다. 화면에 `탐색 검사 20회 / 최대 128회 · 5단계 계획 발견`과 현재 이동 단계가 표시된다. 이전 고정 계획 항목도 그대로 남겼다. 실행 후 홈 복귀를 추가하지 않으므로 최종 위치는 N0·N9·N10이다.

## 파일과 연결

| 파일 | 역할 |

| `backend/app/services/traffic_recovery_search.py` | 허용 동작, 탐색 한도, 상태 중복 제거, 검사 기록 |
| `backend/app/services/traffic_joint_actions.py` | 자동 탐색 선택, 기존 예약 검사·실행 직전 전체 검사 |

`traffic_selector: search`와 `recovery_search`를 함께 지정한다. `fixed_plan`과 동시에 지정하지 않는다. 일반 시나리오의 KEV 선택 기본값은 유지한다. 탐색 보고서는 시나리오 결과의 `coordination.recovery_search`와 `traffic_preview.recovery_search`에 저장한다.
