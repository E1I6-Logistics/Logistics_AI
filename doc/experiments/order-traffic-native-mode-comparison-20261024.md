# 기존 시뮬·알고리즘과 우리 시뮬·AI 비교

## 비교 목적

사용자가 확정한 순서는 **시뮬·알고리즘 ↔ 시뮬·AI 비교 → 검증 → 실기체 비교**다. 이전 시험은 주로 추가 교통조정 내부에서 선택기를 바꾼 비교였다. 특히 `MIN_EXPECTED_TIME`은 기존 화면의 알고리즘 모드가 아니다. 이 문서는 두 모드 전체 흐름의 비교를 따로 기록한다.

| 조건 | 경로·교통 처리 | KEV |
| --- | --- | --- |
| 시뮬·알고리즘 | 기존 관제의 경로 계산·예약·점유 제어 | 사용하지 않음 |
| 시뮬·AI: 우리 방식 | A* 기본 경로 → KEV 전략 순서 → 코드의 제한된 우회 생성·검사 → 유효 경로 중 코드의 예상 시간 비교 → 기존 주행기에 적용 | 전략 순서 제안 |

기존 알고리즘에도 교통 제어가 있다. 우리 AI는 경로 생성용 KEV를 쓰는 설정과 구분한다. 모드 외에도 `FMS_ORDER_ROUTE_SOURCE=EXISTING_SHORTEST_PATH`, `FMS_TRAFFIC_SELECTION_POLICY=KEV_STRATEGY_ORDER`를 명시한다. 따라서 이번 비교는 **전체 방식의 차이**이며 AI 판단 하나의 인과 효과를 분리한 시험은 아니다.

## 고정 조건과 실행 방법

- 같은 지도, 로봇 3대, 초기 위치 N0·N1·N2, 같은 배터리 상태.
- 두 픽업대 모두 방문하는 혼합 주문 12건·41개. seed 137, 최초 3건 동시 접수 뒤 5초마다 공급.
- 속도 0.2m/s, 예약 여유 0.2초, 작업 시간 1.5초, 기존 시뮬 갱신 0.1초. 관측 약 0.2초.
- 각 조건 한 번, 조건당 300초 한도. 실패 시 기록을 보존하고 중단하며 유리한 결과를 얻기 위한 자동 재시험은 하지 않는다.
- 별도 시험 서버 8035를 차례로 사용한다. 기존 화면 서버 8000은 조회만 한다. ROS/MQTT 시작 함수·실기체 명령은 실행하지 않는다.
- 모델은 이미 실행 중인 8012의 `jaredpalmer/kev-0.8b@v1.0`. 공통 준비 요청 1회는 주문 판단에서 제외한다.

실행 도구: [order_traffic_native_mode_comparison.py](../../tests/order_traffic_native_mode_comparison.py). 기본은 주문표와 실행 조건 준비만 하며 `--run`이 실행한다. `--case`로 A/B 집중·혼합·빠른 공급을 선택할 수 있다. 이번에는 혼합 한 쌍부터 확인한다.

기존 알고리즘 분기는 `order_route_dispatcher.py`에서 추가 교통조정을 건너뛰고 `navigate_to_node(..., required_path=None)`를 호출한다. 그 뒤 기존 주행기에서 경로·예약을 처리한다. 공통 시험 진입점은 시작 모드를 고르는 옵션만 추가했고 기본 AI 모드는 유지했다. 실제 주문의 `operation_mode`, `driving_mode`, 모델·선택기 필드와 모델 서버 카운터도 확인한다.

두 조건 모두 작업·복귀가 끝났고 세 로봇이 홈에서 IDLE 상태였다. 같은 지도·초기 상태·주문표·주행 설정, 실제 저장 주문의 모드, 알고리즘의 추가 교통조정 미호출, AI의 전략 판단 연결을 확인했다. AI의 추가 교통조정 결정은 48회이며 29회는 단일 경로, 19회는 모델 전략 제안 후 코드 시간 비교였다. 기존 알고리즘에 해당 로그가 0개인 것은 실제 이동이 0번이라는 뜻이 아니다.

모델 서버 요청 카운터는 569→589다. 공통 준비 1회＋AI 주문 판단 19회와 맞으며 기존 알고리즘 조건에서는 0회였다. 모델 오류는 없었다. 관련 자동 검사 301개 통과·기존 경고 4개는 이 운행 2회·주문 24건과 별개다.

### 전체 실행 상태를 완전 통과로 표시하지 않은 이유

`comparison.json`은 **STOPPED_REVIEW_REQUIRED**를 유지한다. 16개 확인 항목 중 `visible_unchanged` 한 항목이 불일치했다. 별도 시험은 모두 완료됐지만, 시험 전후 기존 화면 서버의 선택 모드가 **AI→알고리즘**으로 달라졌다. 기존 주문 6건·로봇 위치/상태/배터리·시나리오 상태는 동일했다. 시험 도구는 화면 서버에 조회만 하며 모드 변경 요청을 보내지 않는다. 조회 전후 자료만으로 변경 주체는 판단할 수 없다. 현재 화면 모드는 되돌리지 않았다.

`verify_raw.py`와 `independent-verification.json`에서 저장 원문만으로 주문 완료·평균 시간·점유 표본·모델 호출과 화면 차이를 재확인했다. 원문은 바꾸지 않았고 전체 상태를 성공으로 덮어쓰거나 자동 재시험하지 않았다. 별도 시뮬 시험 서버는 모두 종료했다.

**후속 사용자 확인(2026-10-24):** 사용자가 시험 중 화면을 보며 직접 모드를 바꿨다고 확인했다. 따라서 이 모드 차이는 설명된 사용자 조작이며, 시험 도구의 관제 상태 훼손이나 주문 처리 실패로 해석하지 않는다. 별도 시험 서버 두 개는 각각 지정한 모드에서 끝까지 실행됐다. 당시의 자동 검사 불일치와 원본 `STOPPED_REVIEW_REQUIRED` 상태는 이력으로 유지하며 추가 재시험은 하지 않았다.

### 이번 결과가 뜻하는 범위

이번 혼합 주문 한 쌍에서는 우리 방식의 평균 주문 시간이 약 3.86초 짧고 홈 복귀까지 약 12.46초 빨랐다. 이는 **현재 브랜치의 두 모드 전체 흐름을 한 번씩 실행한 결과**다. KEV 판단 자체의 독립적인 성능 이점을 입증한 것은 아니다. 이전 응답 대기 대조에서 모델 없이도 비슷한 차이를 재현한 결과는 그대로 유효하다.

다음은 같은 기준으로 A/B 집중·빠른 공급과 다른 주문표도 비교해 실패·장기 정지·점유 문제 및 시간 변화가 반복되는지 확인하는 것이다. 아직 일반적인 우열이나 실기체 전환 준비 완료를 선언하지 않는다.

## 해석 기준

1. 주문 실패·복귀 실패·시험 한도 초과·관측 중복 점유가 없는지 먼저 확인한다.
2. 평균 주문 시간은 **접수 응답부터 작업대 작업 완료까지**이며 배차 대기·이동·작업을 포함한다. 홈 복귀는 별도 지표다.
3. 전체 작업 종료 시간, 최종 홈 복귀 시간, 최장 주문 시간, 최대 대기 주문, 모델 요청·응답 수를 함께 기록한다.
4. 제한된 주문표 한 번으로 장시간 처리량·일반적인 성능 우위·실기체 안전을 입증하지 않는다. 점유 관측도 표본 사이 모든 순간의 증명은 아니다.

## 변경과 복원

일반 관제 서비스·화면·실기체 실행 코드는 이번 비교 준비에서 바꾸지 않았다. 시뮬 전용 진입점과 시험 관측기를 확장하고 별도 비교 도구·검사를 추가했다. 기존 미커밋 작업을 포함해 변경 전 파일을 `logs/change-snapshots/20261024-before-native-mode-comparison/`에 보존했다. 복원 도구는 이번 변경 이후의 추가 수정이 있으면 중단하며 기본은 복원 예정 목록만 보여준다. 시험 기록은 지우지 않는다.
