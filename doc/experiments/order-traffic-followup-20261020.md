# KEV 후보 판정 역할 검토와 비교 후속 진단

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-20. **확장 방식을 구현하라는 요청이 아니므로 운영의 후보 생성·검사·선택 로직은 바꾸지 않았다.** 실제 입력 재질문 도구와 진단 기록만 추가하고, 기존 비교 실행기로 같은 주문표를 한 쌍 더 실행했다.

## 먼저 구분할 세 가지 역할

현재 일반 주문 연결에서는 여러 로봇 전체의 행동을 다시 정하지 않고, 다른 로봇의 계획을 유지하며 새 이동 요청의 경로 후보를 선택한다.

| 방식 | KEV에게 묻는 것 | 코드가 할 일 | 줄일 가능성이 있는 일 |
| --- | --- | --- | --- |
| 현재: 완성 후보 선택 | 검사 통과한 경로 중 어느 것을 실행할까? | 모든 후보 생성·검사·시간 계산 후 선택 경로 재검사 | 현재는 후보 생성·검사 일을 줄이지 않음 |
| 제안된 후보 판정 | 이미 만든 경로가 가능한가, 불가능한가? | 판정 결과 확인과 실행 직전 검사. 검증 없이 판정을 신뢰하는 방식은 권하지 않음 | 판정이 정확하고 기존 검사가 비쌀 때 검사 비용 절약 가능성 |
| 전략부터 제안 | 어느 로봇을 우선하고 어떤 통과·우회·양보 계획을 먼저 만들까? | 선택 전략의 경로를 만들고 검사, 실패 피드백·시도 한도 관리 | 만들고 검사할 계획의 수를 줄일 가능성 |

**후보 판정과 전략 제안은 같은 변경이 아니다.** 하나는 이미 만든 계획의 가능 여부, 다른 하나는 만들 계획의 방향과 순서를 정한다. 둘을 함께 사용하는 설계도 가능하다.

설명용 정지 상황에서 R2가 N7에 계속 서 있다고 하자.

- 기존 후보가 ‘R2는 그대로 있고 R1이 N7을 통과’라면, 현재 점유 규칙상 실행할 수 없다. KEV가 가능하다고 답해도 그 후보의 내용은 바뀌지 않는다.
- KEV가 ‘허용된 N5로 R2가 비킨 다음 R1을 통과시키자’는 전략을 고르면, 코드는 다른 후보를 만들어 검사할 수 있다. 이는 유효한 해결 방법을 추가하는 시도다.
- 현재 일반 주문 연결은 다른 로봇의 계획을 고정한다. 이 예의 R2 양보까지 실행하려면 별도 실행 연결이 필요하다. KEV 호출 위치만 바꿔 완성되는 기능이 아니다.

## 후보 검사를 KEV에 맡기는 제안에 대한 판단

### 지금 검사를 완전히 대체하는 것은 추천하지 않는다

1. **현재 입력이 독자적인 검사에 충분하지 않다.** 모델에는 `reservation_count`와 남은 경로 등이 전달되지만 상세 예약표의 자원별 시간 구간은 없다. 예약이 14개라는 정보만으로 어떤 노드가 언제 비는지 알 수 없다. 후보별 대기 예상은 코드가 예약표로 계산한 결과다.
2. **잘못된 판정은 두 종류다.** 불가능한 후보를 가능하다고 하면 잘못된 실행 요청이 된다. 가능한 후보를 불가능하다고 버리면 갈 수 있는 길을 잃고 불필요하게 기다릴 수 있다. 실행 전 코드 검사만 유지해도 앞의 오류는 막을 수 있지만, 이미 버린 유효 후보를 자동으로 되살려 주지는 않는다.
3. **모델의 판정 정확도는 아직 측정하지 않았다.** 지금 시험은 가능한 후보 중 숫자 목표를 따르는지 측정했다. 이 결과만으로 모델의 실행 가능성 판정 능력이 없다고 증명할 수는 없지만, 그 권한을 넘길 근거도 없다. 가능/불가 정답과 오류 유형을 따로 평가해야 한다.
4. **현재 검사 비용이 병목이라는 근거가 없다.** 이전 시험에서 입력 경로를 받은 뒤 우회 생성·검사·선택까지의 중앙값은 계산 방식 약 2.4~12.5ms, KEV 방식 약 99~105ms였다. 사전 검사만 따로 잰 값도, 동일 상태에서 통제한 속도 비교도 아니다. 적어도 현재 작은 사례에서 코드 검사를 모델 호출로 대체해 빨라질 것이라고 가정할 수 없다.

모델 판정을 실험한다면 실제 실행과 분리된 데이터에서 ‘불가능을 가능이라고 한 비율’, ‘가능을 버린 비율’, 검사·추론 비용을 확인하는 단계부터 필요하다. 최종 검사는 현재 점유·예약 모델에 대한 검사이며 실기체 안전 전체를 증명하는 것도 아니다.

### 검사 시점을 뒤로 미루는 방식은 검토할 수 있다

```text
코드가 구체적인 후보 경로들을 만듦
  → KEV가 먼저 검사할 후보를 고름
  → 코드가 그 후보만 검사
      실패: 다른 후보 검토
      통과: 실행 가능한 후보로 보관
  → 횟수·시간 한도 안에서 검토한 유효 후보 중 채택
  → 최신 점유·예약 재검사 후 실행
```

이것은 **후보 검사 순서 제안**이다. 모든 후보를 먼저 검사하지 않아도 되지만, 처음 통과한 후보만 실행하면 더 좋은 후보를 놓칠 수 있다. 검사 수가 줄었는지, 모델 호출까지 포함해 빨라졌는지, 좋은 계획을 얼마나 놓쳤는지를 함께 봐야 한다. 전략 제안은 여기서 더 앞서 경로 생성 순서까지 바꾸는 방식이다. 둘 다 설계 검토이며 구현하지 않았다.

학습 모델로 기존 MAPF 탐색을 안내하는 방향에는 연구 근거가 있다. [Neural Neighborhood Search for MAPF](https://proceedings.iclr.cc/paper_files/paper/2024/hash/d41f8403e9bb5141bc2c81fad7658185-Abstract-Conference.html)는 학습 모델로 LNS 탐색을 안내한다. 해당 전용 학습 모델의 결과가 우리 KEV의 성능을 증명하는 것은 아니다.
또 [SayCan](https://say-can.github.io/)은 언어 모델의 유용성 판단과 스킬의 실행 가능성 추정을 결합한다. 이 역시 코드 검사 제거의 근거가 아니라 판단 역할을 나누는 연구 사례다.

## 왜 비교를 추가했나

앞선 전체 주행 시험에서는 실행 중 상태·예약·담당 로봇이 달라졌다. 전체 시간 차이와, 같은 입력에서 KEV가 목표를 제대로 따르는지를 분리할 필요가 있었다.

### 1. 실제 입력 원문을 그대로 재질문

실제 전송 JSON 14개를 각각 3번, 총 42회 재질문했다. 상태·지시문·후보 이름·순서·숫자를 바꾸지 않았고, 전송 JSON 일치와 같은 checkpoint를 확인했다. 관제 이동 명령은 보내지 않았다.

- 42/42회 원래와 같은 후보를 선택했다.
- 원래 맞았던 12개 입력은 각각 3회 모두 예상 최소 후보를 선택했다.
- 원래 틀렸던 2개 입력은 각각 3회 모두 같은 느린 후보를 선택했다.
- 따라서 36/42회 예상 최소와 일치했다. 42개의 서로 다른 상황을 시험한 숫자가 아니다.

이 자료에서는 오류가 반복된다. 입력 표현·목표 해석·학습된 선호 등이 원인 후보이며, 모델 내부 원인을 하나로 확정한 결과는 아니다. 숫자 최소 선택을 고치려고 같은 원문만 계속 반복할 필요는 낮다.

도구: order_traffic_exact_replay.py (`backend/simulation/order_traffic_exact_replay.py`, 로컬 보관).
원문과 응답: 재질문 결과 (`logs/order-traffic-exact-replays/20261020-104638/report.json`, 로컬 보관).

### 2. 같은 주문표의 실제 주행을 한 쌍 추가

seed 42의 8건·22개를 KEV와 계산 방식으로 한 번씩 더 실행했다. 앞선 시험과 주문표·지도·로봇 시작 상태 일치를 확인했다.

| 시험 | KEV 작업 완료 | 계산 방식 작업 완료 | 해석 |
| --- | ---: | ---: | --- |
| 첫 비교 | 75.47초 | 83.33초 | 이 실행에서는 KEV가 약 7.86초 빠름 |
| 후속 반복 | 75.75초 | 75.71초 | 약 0.05초 차이. 현재 관측 간격으로 우열 판단 불가 |

후속 16건·44개는 모두 처리·복귀 완료했다. 실패·취소·복귀 오류는 없었다. 점유를 856회 관측하는 동안 중복은 없었지만 모든 순간의 안전 증명은 아니다. 후속 KEV 선택은 7회 중 6회, 계산 선택은 7회 중 7회 예상 최소와 일치했다.

첫 비교의 8초 차이는 반복에서 유지되지 않았다. 조건당 두 번이라 변동 분포나 평균 개선을 확정할 수 없다. 그러나 최초의 한 실행만으로 KEV가 우수하다고 말하면 안 된다는 근거는 분명해졌다.

## 발견한 구체적인 배차·복귀 분기

첫 비교에서 같은 7번 주문의 R2 복귀를 대조했다.

| 항목 | 첫 KEV 실행 | 첫 계산 실행 | 후속 계산 실행 |
| --- | --- | --- | --- |
| 기존 경로의 예상 | 11.908초 | 11.567초 | 11.322초 |
| 우회의 예상 | 11.324초 | 11.324초 | 11.324초 |
| 선택 | 기존 경로: 예상 최소 위반 | 우회: 예상 최소 | 기존 경로: 예상 최소 |
| 복귀 경로가 N7을 지남 | 예 | 아니오 | 예 |
| 뒤의 5번 주문 담당 | R2, N7에서 출발 | R3, N2에서 출발 | R2, N7에서 출발 |

첫 KEV 실행에서는 약 42.69초에 R2가 N7에서 WAITING, 약 42.87초에 새 목적지 N5로 이동하는 상태가 관측됐다. 첫 계산 실행에서는 R2가 다른 복귀 통로를 이동했고, 뒤 주문은 R3에게 배정됐다.

현재 배차기는 **복귀 중인 로봇이 노드 위에 있고 엣지를 점유하지 않을 때** 새 주문 후보로 삼는다. 따라서 경로·예약·갱신 시점에 따라 다음 주문을 맡을 기회가 달라질 수 있다. 확인 위치: [order_dispatcher.py](../../backend/app/services/order_dispatcher.py), [order_manager.py](../../backend/app/services/order_manager.py).

이 관측으로 말할 수 있는 것:

- 단일 복귀 목적지 도착 시간을 줄이는 것과, 다음 주문까지 포함해 전체 흐름을 개선하는 것은 다르다.
- 같은 주문표라도 실제 예약 시점과 이후 후보가 같지는 않다. 후속 계산 실행에서는 두 예상값 차이가 약 0.002초에 불과해 기존 경로가 선택됐다.
- KEV 입력에는 대기 주문 목록과 다음 배차의 이득이 없다. N7을 거친 선택을 ‘다음 주문을 예측한 의도적인 물류 최적화’라고 해석할 근거는 없다.
- 왜 정확히 각 예약 시점이 달라졌는지까지 통제한 원인 실험은 하지 않았다. 모든 시간 차이를 특정 코드 한 줄이나 추론 지연 하나로 단정하지 않는다.

첫 비교의 경로·로봇 차이 원본: trajectory-differences.json (`logs/order-traffic-comparisons/20261020-102657/trajectory-differences.json`, 로컬 보관).

## 다음에 결정할 사항

현재 검사는 유지하는 것이 권고다. ‘AI가 더 많은 단계를 맡는가’ 대신 어떤 판단이 더 좋은 유효 계획이나 적은 계산량으로 이어지는지를 목표로 정한다.

1. 현재 단순 예상 최소 선택은 코드 기준을 유지해 모델 평가의 정답으로 쓸 수 있다. KEV가 못 고른 답을 몰래 덮어써 성능으로 보고하지 않는다.
2. 복귀 중 재배차의 허용 시점과, 이번 이동 시간·다음 주문·전체 처리량 중 무엇을 최적화하는지를 팀과 명시한다. 이는 기존 배차 담당과도 관련된다. 이번에는 바꾸지 않았다.
3. KEV 역할을 확장한다면 ‘전략 제안 또는 검사 순서 제안 → 코드로 구체화·검사’를 별도 실험으로 검토한다. 같은 탐색 한도에서 일반 규칙 대비 계획 수·총 시간·완료 시간을 비교한다.
4. 이미 틀린 원문을 재전송하거나 같은 주문표의 전체 완료 시간만 더 모으는 일보다, 역할과 목표를 확정하고 필요한 실험을 정하는 것이 우선이다. 이후 성능 주장에는 반복·새 상황 평가가 필요하다.

추가 주행 원본: 비교 결과 (`logs/order-traffic-comparisons/20261020-104730/comparison.json`, 로컬 보관), 기존 시험과의 대조 (`logs/order-traffic-comparisons/20261020-104730/followup-verification.json`, 로컬 보관), 종료 상태 (`logs/order-traffic-comparisons/20261020-104730/final-server-state.json`, 로컬 보관).

종료 후 원래 KEV 선택으로 복원했고 로봇 3대는 대기 위치에 있다. 기존 이력 86건과 새 16건을 보존해 총 102건이다. 확장 방식·검사 제거·배차 정책 변경은 적용하지 않았다.
