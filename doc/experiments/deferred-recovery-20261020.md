# 미룬 순서 보관과 KEV 제안 한도 뒤 코드 보완

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-20. 해결 가능한 순서까지 KEV가 포기하던 문제를 보완했다. **관제의 별도 가상 로봇 시험에서 이동·복귀를 완료했다.** 일반 주문의 교통조정 기본 방식은 변경하지 않았다.

## 바뀐 흐름

```text
로봇 위치·공급 경로·길을 막는 관계 수집
  ↓
KEV가 다음에 검토할 이동 또는 ‘다른 순서 먼저 보기’를 추천
  ├─ 이동: 코드가 기존 예약 검사 수행
  └─ 다른 순서: 남은 후보를 보관하고 다른 분기 검토
  ↓
다른 분기를 다 보면 보관한 분기를 다시 꺼냄
같은 분기는 두 번 미루지 않음
  ↓
KEV 제안 8회를 다 쓰면 남은 전체 한도 안에서 관계 코드가 검토를 이어받음
  ↓
완성 계획을 다시 검사한 뒤에만 가상 로봇 이동
```

과거 방식은 되돌아갈 때 남은 후보가 있는 분기를 버렸다. 새 `DEFER` 설정은 그 프레임의 가상 상태·선택 전 이동 기록·아직 검사하지 않은 후보를 보관한다. 나중에 원래 후보를 그대로 재개하며, 실제 로봇을 되돌리는 명령이 아니다. 계획 하나를 찾으면 나머지 보관 분기는 더 검사할 필요가 없다.

새 설정은 다음과 같다. 기존 기본값 `DISCARD`와 `STOP`은 유지했다.

```json
{
  "recovery_strategy": "KEV_DEPENDENCY",
  "recovery_branch_policy": "DEFER",
  "recovery_guidance_budget_policy": "CODE_CONTINUE",
  "recovery_guidance": {"max_calls": 8, "request_seconds": 2.0},
  "recovery_search": {"max_checks": 128, "max_steps": 8, "max_seconds": 10.0}
}
```

`CODE_CONTINUE`는 정상적인 제안 횟수 한도 소진 뒤에만 동작한다. 모델 오류·잘못된 응답·개별 응답 시간 초과·취소에는 이동을 실행하지 않는다. 코드가 이어받아도 전체 128회 검사·8단계·10초 한도는 그대로다. 시간·검사 한도 안에 완성 계획을 찾지 못하면 현재 위치를 유지한다.

코드가 이어받은 선택은 `CODE_AFTER_MODEL_BUDGET`, 함께 찾은 결과는 `HYBRID_KEV_CODE_SEARCH`로 기록한다. **KEV 단독으로 해결한 결과로 집계하지 않는다.**

## 효과를 나눠 본 결과

N3→N0와 N4→N0 두 복귀 배치를 각각 두 번 시험했다. 같은 공급 동작·관계 정보·예약 검사·전체 한도를 사용했다. ‘필요한 양보 동작 하나를 주지 않은 상황’도 별도로 두 번씩 검사했다.

| 방식 | 해결 가능한 시험 완료 | 예약 검사 | 모델 제안 |
| --- | ---: | ---: | ---: |
| 관계 코드 + 분기 보관 | 4/4 | 5회씩 | 0회 |
| KEV + 분기 포기 + 제안 한도에서 중단 | 0/4 | N3 7회, N4 6회씩 | 8회씩 |
| KEV + 분기 보관 + 제안 한도에서 중단 | 0/4 | 6회씩 | 8회씩 |
| KEV + 분기 보관 + 한도 뒤 코드 보완 | 4/4 | 10회씩 | 8회씩 |

**보관만으로 제안 8회 안에 해결되지는 않았다.** 미검사 후보를 남겨두었기 때문에 코드가 이어받아 완성할 수 있었다. 이번 표본에서는 코드만 쓴 방식보다 검사·계획 시간이 더 들었다. 개선한 것은 모델의 판단 정확도가 아니라 **모델이 잘못 추천해도 해결 기회를 보존하고 한도 안에서 검토를 이어가는 구조**다. 어떤 지도에서도 반드시 해결한다는 보장은 아니다.

필요한 양보 동작이 없는 상황은 보관 방식에서 모든 남은 후보를 검사한 뒤 미해결이었다. 보관 코드·보관 KEV는 각 5회 검사했으며, 완성 계획이 없어 이동 0단계였다. 분기 포기 방식은 완전 탐색 결과로 해석하지 않는다.

전체 격리 실행은 24회, 실제 모델 요청은 118회다. 위치와 남은 시간 등 입력은 실행에 따라 달라질 수 있어 반복 요청이 바이트 단위로 같다는 뜻은 아니다.

자료: 입력·제안·분기 보관·코드 이어받기·실행 결과 (`logs/traffic-recovery/deferred-20261020-200712/report.json`, 로컬 보관).

## 관제에서 직접 보기

1. [관제](http://100.81.82.30:5173/)에서 **시뮬 · AI**를 선택한다.
2. **전략 탐색 비교 → KEV 추천 + 코드 보완 · 두 대가 비켜주고 R1 통과**를 선택한다.
3. **테스트 실행**을 누른다.

이번 시험은 가상 로봇 위치를 **R1=N3, R2=N11, R3=N10**으로 맞춘 뒤 시작한다. 진행 주문이 있거나 로봇이 이동 중인 상태에서는 실행하지 않는다. 경로는 시험용 고정 경로이며, KEV 경로 생성 시험이나 실제 주문의 복귀 상태를 재현하는 시험은 아니다.

화면에는 다음을 표시한다.

- KEV 제안 횟수와 예약 검사 횟수.
- 제안 한도 뒤 코드가 판단한 횟수.
- 나중에 검토하도록 보관한 분기 수와 다시 검토한 수.
- ‘KEV가 제안한 동작 보기’에서 진행·양보·복귀·다른 순서 먼저 검토 기록.

‘코드 보완 4회’는 모델 호출 4회나 실제 로봇 이동 4회가 아니다. 모델 한도를 다 쓴 뒤 코드가 다음 검토 동작을 선택한 횟수다. 예약 검사와 자동으로 결정되는 단일 후보 검토는 별도다.
