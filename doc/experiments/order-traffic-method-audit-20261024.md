# 시뮬·알고리즘과 우리 시뮬·AI 비교 방법 검토

2026-10-24. 코드와 저장된 [보통 접수·폭증 8회 결과](order-traffic-ordinary-burst-20261024.md)를 검토했다. 새 운행·모델 요청·사용자 관제 명령은 실행하지 않았다.

## 결론과 12건의 사용 범위

**현재 방법은 기존 관제와 우리 전체 방식의 초기 기능·운영 비교로는 타당하다. 확정적인 성능 우위나 KEV 판단 하나의 효과를 입증하는 시험으로는 보완이 필요하다.**

새 상황의 대기·우회·재개·완료를 확인하는 짧은 시험은 12건으로 유지해도 된다. 다만 모든 검증을 12건으로 끝내지는 않는다. 장기 대기·지속 처리량에는 긴 연속 운행이 필요하고, 작은 시간 차이의 반복성에는 같은 조건의 반복 실행이 필요하다. 다음 케이스의 우선순위는 한 픽업대 집중 → 작업 지연/일시 점유 → 긴 연속 운행이다. 실제 실행 승인은 이번 검토와 별개이며 여기서는 시험 계획·결과를 바꾸지 않았다.

저장된 네 쌍의 `same_schedule`·`same_start`·`same_map`·`same_settings`와 분기·카운터 검사는 모두 참이었다. 현재 검토한 주요 코드도 실제 운행 사본과 같았다. 기존 운행 원문의 해시가 유지되는지도 확인했다.

기존 알고리즘도 예약 시간을 고려하는 `DistanceAStar.plan_timed()`와 `TrafficManager._resolve_deadlock()`를 사용한다. 단순히 거리만 계산하고 다른 로봇을 무시하는 약한 비교군을 새로 만든 것은 아니다. 여기서 기존은 현재 브랜치의 알고리즘 모드이며 과거 main 전체를 복원한 서버라는 뜻은 아니다.

## 보완할 점과 결과 해석에 미치는 영향

### 1. 같은 접수 계획이 실제 접수 순간까지 완전히 같은 것은 아니다

클라이언트가 약 0.2초마다 공급 시각을 확인하고 HTTP로 순차 등록한다. 각 모드의 최대 요청 지연은 0.126~0.229초였다. 같은 번째 주문이 등록 완료된 시각의 두 모드 차이는 쌍별 최대 0.192·0.079·0.153·0.043초였다.

초기 부하 시험으로는 기록된 허용 범위 0.5초 안이다. 그러나 작은 시각 차이가 복귀 로봇의 배차 가능 여부에 영향을 줄 수 있어 완전히 같은 사건 순서를 재현한 시험이라고 부르면 안 된다. 같은 입력을 반복하고 실제 등록·배차·이동 시각을 함께 기록해야 한다. 큰 결과 차이가 모두 이 접수 오차 때문이라고 확정하는 것도 아니다.

### 2. 완료 시간은 서버의 실제 완료 사건 시각이 아니라 조회로 확인한 시각이다

현재 관측기는 주문 목록을 조회한 뒤 로봇 목록을 조회하고, 두 응답을 받은 뒤 시각을 기록한다. 실제 관측 간격 중앙값은 약 0.222~0.230초, 최대 간격은 약 0.276초였다. 두 조회는 동시에 읽은 하나의 상태가 아니다. 이 값이 정확한 측정 오차의 상한이라는 뜻도 아니다.

따라서 약 0.3초 차이를 안정적인 성능 차이라고 설명하면 안 된다. 그렇다고 그 차이가 전부 조회 오차라는 뜻도 아니다. 최종 성능 비교에는 두 모드에 같은 서버 측 접수·배차·이동 시작·작업 완료·복귀 완료 사건 시각 기록을 넣는 것이 적절하다. 기존 기록의 시간을 사후에 실제 사건 시각으로 바꾸지는 않는다.

주문 등록 요청의 최대 왕복 시간은 운행별 약 0.001~0.028초였다. 현재 평균 주문 시간은 두 모드 모두 **등록 응답부터 작업 완료 관측까지**로 같은 정의를 쓴다. 등록 응답 전 시간까지 포함하는 지표가 필요하면 별도로 정의하고 양쪽에 같이 적용한다.

### 3. 조회하는 자료의 양도 완전히 같지 않다

AI 주문에는 전략·검사 이력이 붙는다. 관측 원문을 JSON으로 다시 인코딩했을 때 평균 주문 상태 자료는 기존 약 3~4KB, AI 약 51~55KB였다. 이는 실제 네트워크 전송 바이트를 직접 계측한 값은 아니다.

같은 API를 같은 방식으로 조회했지만 응답을 만드는 비용과 기록량은 다르다. 최종 비교에서는 공통의 가벼운 상태·사건 기록을 주 측정에 쓰고, 상세 AI 진단 로그는 따로 보존하는 것이 좋다. 이를 위해 일반 관제 구조를 대폭 변경할 필요는 없다.

### 4. CPU·GPU 부하는 통제하지 않았다

코드·지도·주문·예약은 분리했지만 컴퓨터는 사용자의 다른 기능 시험과 공유했다. 사용자 관제의 재시작·모드 변경도 관측 정보로만 남겼다. CPU/GPU 부하를 운행 내내 계측하지 않았으므로 시각별 다른 부하의 영향을 사후에 보정할 수 없다.

현재 결과는 병행 작업 중의 초기 관측으로 유지한다. 최종 속도 비교는 다른 부하가 적은 조건에서 반복하고 실행 순서도 계속 균형을 맞춘다. 사후에 유리한 운행만 선택하지 않는다.

### 5. WAITING 상태 시간만으로 전체 통행 대기를 비교하면 안 된다

기존 알고리즘은 예약을 기다리는 로봇을 WAITING으로 표시할 수 있다. 우리 AI는 이동 계획을 적용하기 전에 KEV 응답·경로 검사를 기다리므로 로봇이 IDLE인 시간이 생길 수 있다. IDLE로 보인다고 대기나 판단 비용이 없는 것이 아니다.

기존 `sampled_robot_waiting_seconds`는 상태 표본의 누적 시간일 뿐, 두 방식의 전체 통행 대기를 같은 의미로 비교하는 지표가 아니다. AI의 대기 감소를 입증하는 근거로 쓰지 않는다. 주 지표인 주문 접수→작업 완료 시간은 이 대기도 포함한다. 별도 대기 지표가 필요하면 양쪽 모두 이동 요청→실제 출발을 기준으로 잡고 계획 시간·예약 대기를 나눠 기록한다.

### 6. 내부 판단·대기 정책은 서로 다르다

우리 AI에는 우회 생성 한도·KEV 호출 한도·검토 주기 한도와 적용 전 교통조정 대기 60초가 있다. 기존 알고리즘의 예약 대기에는 같은 추가 60초 판정이 없다. 공통 관측 종료는 300초지만 내부 종료 조건까지 동일한 것은 아니다.

이번 8회에는 한도에 걸린 실패가 없어 완료 결과가 무효가 되는 것은 아니다. 향후 장기 차단·응답 실패 시험에서는 정해진 시간 안의 완료, 안전한 정지·실패 처리를 어떤 결과로 볼지 미리 정하고 내부 정책 차이도 표시해야 한다. 단순히 실패 표시가 먼저 떴다는 이유만으로 방법의 해결 능력을 판단하지 않는다. 이번 검토에서 기존 알고리즘이나 운영 한도를 임의로 바꾸지는 않았다.

### 7. 시뮬의 모든 순간을 검증한 안전 증명은 아니다

두 방식은 같은 노드·물리 엣지 단일 점유 규칙과 주행기를 사용한다. 저장된 5,103회 점유 표본에서 중복이 없었다. 하지만 조회 사이의 모든 갱신을 검사한 것은 아니다. 후속 케이스에는 시험용 시뮬 루프의 매 갱신마다 공통 점유 불변 조건 검사를 추가하면 검출 범위를 넓힐 수 있다. 실기체의 도착·정지·통신 오차 검증은 여전히 별도다.

### 8. 전체 방식 비교와 AI 기여 비교는 다른 질문이다

주 비교는 계속 **기존 시뮬·알고리즘 ↔ 우리 시뮬·AI**로 유지한다. 초기 조건을 맞춘 두 시스템 전체의 비교이므로 내부 구현이 다르다는 이유만으로 무의미하지 않다.

반면 우리 AI에는 KEV 외에 우회 생성·예약 검사·최소 예상 시간 선택도 들어간다. 현재 자료에서 160회 이동 결정의 190회 전략 검사 묶음은 준비 전략을 모두 시도했다. 전체 방식이 빨랐던 한 장면만으로 KEV가 더 좋은 검사 순서를 제안했다고 결론내리지 않는다. 필요할 때 우리 흐름에서 KEV 제안만 제거한 대조를 진단용으로 덧붙이고, 그것을 기존 알고리즘과의 주 비교로 바꿔 부르지 않는다.

### 9. 입력 다양성·반복·장시간 운행은 아직 부족하다

두 주문표·접수 조건 두 개·모드 두 개를 한 번씩 실행한 초기 자료다. 96건을 독립적인 비교 96회로 계산하지 않는다. 같은 입력을 초기 상태부터 반복해 결과 변동을 먼저 확인하고, 구별하려는 성능 차이와 허용 오차에 따라 필요한 횟수를 정한다. [FHWA 2019 시뮬레이션 비교 지침](https://ops.fhwa.dot.gov/publications/fhwahop18036/chapter6.htm)은 이 원칙을 참고할 수 있는 자료이며 AMR용 12건 기준을 제공하는 것은 아니다.

## 다음 시험에 적용할 구분

1. **케이스 동작 확인:** 12건 유지. 한 픽업대 집중·작업 지연·일시 점유 등에서 기대한 완료/대기/중지가 나오는지 확인한다. 통계적 속도 우위는 선언하지 않는다.
2. **시간 측정 보완:** 같은 서버 사건 기록, 가벼운 공통 측정, 실제 접수 시각 기록, 매 갱신 점유 검사를 시험용 범위에서 설계한다. 두 방식에 함께 적용한다.
3. **성능 비교:** 다른 부하가 적을 때 동일 조건을 반복한다. 모든 결과와 실패를 남기고 입력·순서를 미리 정한다. 케이스가 달라지면 기대 결과도 미리 정의한다.
4. **연속 운영:** 공급 시간을 정해 그 안의 완료량·대기열·가장 오래 밀린 주문, 공급 종료 후 해소·복귀를 별도 확인한다. 12건의 완료 비교만으로 대체하지 않는다.

3·4단계의 반복 수와 운행 길이는 아직 확정하지 않았다. 이번 검토는 새 시험·코드 수정을 시작하라는 결정을 대신하지 않는다.
