# 일반 주문: 코드·기존 KEV·새 전략 순서 비교

2026-10-23. 사용자 승인으로 [일반 주문 연결 확인](order-traffic-strategy-integration-20261023.md) 다음에 수행하는 전체 흐름 비교다. 아래 조건을 실제 모델 시험 전에 고정한다.

## 무엇을 비교하나

동일한 6건·8개 주문을 같은 시각표로 공급하고 코드 선택·기존 KEV 선택·새 KEV 전략 순서를 각각 한 번 실행한다. 모델 호출 수뿐 아니라 주문 완료·대기·복귀까지의 결과를 확인한다.

세 방식은 판단 책임이 다르다. 코드는 생성·검사한 경로의 예상 완료 시간으로 고르고, 기존 KEV는 검사 뒤 최종 경로를 고른다. 새 방식은 생성 전 전략 순서를 KEV가 제안하고 코드가 검사한 경로 중 최종 선택한다. 따라서 **전체 방식의 비교이며 AI 모델 단독 효과 비교가 아니다.** 판단 결과에 따라 이후 로봇 상태와 경로 후보도 달라질 수 있다.

## 고정 조건과 중단 기준

- 현재 사용자 화면의 8000 서버와 주문은 유지한다. 비교는 **127.0.0.1:8030**에 도구가 시작한 별도 시뮬 전용 서버를 사용한다.
- 방식마다 새 프로세스·가상 저장소·주문 관리자·예약표를 사용한다. 시작은 R1=N0, R2=N1, R3=N2이며 초기 위치·지도·시뮬 속도·작업 시간 일치를 검사한다.
- 경로 생성·우회는 공통 A*, 시뮬 속도 0.2m/s, 예약 마진 0.2초, 작업 시간 1.5초. 배차·가상 이동 확인 주기는 기존 약 0.1초다.
- 입력 순서: 0초 A1과 C1을 별도 주문으로 등록, 2초 B1, 4초 D1, 6초 A1+C1, 8초 B1+D1. 모두 최대 적재량 5개 이하다.
- 기존 일반 주문 설정인 전체 대기 60초, 개별 선택 10초, 우회 생성 최대 2개를 유지한다. 새 방식만 전략 호출 상한 8회를 추가로 사용한다. 세 방식이 같은 모델 호출 수를 보장하는 조건은 아니다.
- 실행 순서는 코드 → 기존 KEV → 새 전략으로 고정하고 각각 한 번만 시험한다. 공통 준비 모델 호출 1회는 별도로 기록한다.
- 주문 등록 요청 지연이 계획보다 0.5초 넘게 생기면 비교 조건 문제로 표시한다. 누락·실패·미완료를 0초나 성공으로 채우지 않는다. 모델 오류·등록 조건·소스 변경도 기록한다.
- 모델 서버는 표시 중인 화면과 공유한다. 전후 요청 카운터가 준비 1회+이 비교의 호출 합계와 맞지 않으면 다른 요청의 영향 가능성을 표시한다. 사용자 작업을 막지 않는다.
- 실제 비교는 각 방식 최대 180초, 도구 실행 상한 200초. 시험이 끝나면 도구가 시작한 자식 서버만 종료한다. 관측·주문 결과·소스를 파일에 보존한다.
- 모델 지시문·모델·입력을 결과에 맞춰 수정하거나 좋은 결과를 얻을 때까지 반복하지 않는다. 일반 관제의 기본 설정도 바꾸지 않는다.

이전 연결 시험의 64.12초·9회를 그대로 새 방식의 비교 결과로 재사용하지 않고, 이번에 세 방식 모두 새로 실행한다.

## 지표 정의

| 지표 | 의미 |
| --- | --- |
| 전체 작업 끝 | 시작부터 여섯 주문의 작업대 작업 완료를 모두 관측할 때까지 |
| 평균 주문 시간 | 각 주문의 등록 응답부터 작업대 작업 완료 관측까지의 평균 |
| 평균 배차 대기 | 주문 등록 응답부터 로봇 할당을 처음 관측할 때까지의 평균 |
| 홈 복귀까지 | 여섯 주문의 작업과 홈 복귀가 모두 끝날 때까지 |
| 로봇 대기 합계 | 약 0.2초 관측 사이 WAITING 상태로 추정한 누적 시간. 픽업·작업대의 모든 대기를 뜻하지 않음 |
| 모델 호출 | 해당 방식의 실제 REQUEST 기록 수. 단일 전략·후보로 생략된 경우는 제외 |
| 모델 응답 시간 합계 | 응답 로그의 요청 소요 시간을 더함. 동시에 실행된 요청이 있어 전체 판단 지연이나 실행 시간과 다름 |
| 묶음 처리 속도 | 이번 8개를 전체 작업 끝 시간으로 나눈 값. 지속 주문의 정상 상태 처리량이 아님 |

API 관측은 약 0.2초 간격이므로 완료·배차 시간에는 관측 오차가 있다. 작고 한 번씩인 시험에서 근소한 차이로 일반적인 우열을 주장하지 않는다.

## 실행·기록

[비교 도구](../../tests/order_traffic_policy_comparison.py), [공통 주문 공급·관측](../../tests/order_traffic_strategy_smoke.py), [지표 검사](../../tests/test_order_traffic_policy_comparison.py)를 사용한다. 기본 실행은 준비만 하고 실제 시험은 `--run`을 명시한다.

```bash
cd ~/dev/Logistics_AI
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python tests/order_traffic_policy_comparison.py \
  --run --model-host http://127.0.0.1:8012 \

```

실행 당시 소스 사본·해시, 모델 설정, 정책별 API 관측·완성 주문·판단 기록, 공통 시작 조건과 최종 요약을 보관한다. 기존 결과 폴더는 덮어쓰지 않는다. 관제의 실행 정책 코드에는 이번 비교를 위한 변경을 하지 않는다. 시뮬 전용 API에 실행 식별자와 실제 속도·작업 시간 메타데이터만 추가한다.

## 결과

각 방식 한 번씩, 총 18건·24개를 작업과 홈 복귀까지 완료했다. 실제 모델은 `jaredpalmer/kev-0.8b@v1.0`, CUDA·torch·bfloat16, temperature 2.3510958125672174, prefix cache 0이다. 이번의 ‘기존 KEV’는 **우리 일반 주문의 최종 경로 선택 방식**이다. 별도 배치 시험의 jhlee 방식과 다르며, 이번 일반 주문 비교에 jhlee를 연결하지 않았다.

| 방식 | 작업 완료 | 전체 작업 끝 | 평균 주문 시간 | 평균 배차 대기 | 홈 복귀까지 | KEV 호출 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 코드로 예상 시간이 짧은 경로 선택 | 6/6 | 53.41초 | 28.27초 | 9.56초 | 62.90초 | 0회 |
| 검사 후 KEV가 최종 경로 선택 | 6/6 | 53.33초 | 28.15초 | 9.52초 | 63.00초 | 1회 |
| KEV가 전략 순서 제안 → 코드가 최종 경로 선택 | 6/6 | 54.14초 | 28.73초 | 9.70초 | 63.99초 | 9회 |

모델 응답 시간 합계는 기존 선택 약 0.123초, 새 전략 순서 약 1.773초다. 다른 작업과 겹칠 수 있는 시간의 합계이므로 두 방식의 전체 완료 시간 차이와 같지 않다. 준비 호출 1회는 표에서 제외했다. 모델 서버 요청 수는 9→20으로 11회 증가해 준비 1회+기존 1회+새 방식 9회와 일치했다.

### 왜 새 방식은 더 많이 물었나

세 방식 모두 픽업 8회·작업대 이동 6회·복귀 6회, 총 **20회 경로 적용 기록**을 남겼다. 각 기록의 로봇·이동 단계·적용 경로 순서가 세 방식에서 같았다. 복귀 중 새 주문으로 전환되는 경우도 있으므로, 적용 기록이 같다는 것이 20개 경로를 모두 끝까지 똑같이 주행했다는 뜻은 아니다.

- 기존 선택은 경로를 생성·검사한 뒤 판단한다. 20건 중 19건은 유효 경로가 하나라 KEV를 생략했고, 두 경로가 남은 1건에서만 호출했다. 이때 KEV와 코드는 같은 경로를 골랐다.
- 새 방식은 구체적인 우회 경로를 만들기 전에 전략 순서를 묻는다. 11건은 처음부터 전략이 하나여서 생략했지만, 9건은 여러 전략이 있어 호출했다. 그 9건 중 8건은 나중에 검사하니 유효 경로가 하나뿐이었고, 1건만 둘이었다.
- 새 방식이 검토한 전략은 총 33건이었다. 유효 21건, 예약상 진행 불가 6건, 회피 조건 때문에 경로 자체가 없는 경우 6건이다. 유효 21건이 20개 요청에 걸쳐 분포하며 그중 1요청에 두 경로가 있었다. 이번에는 정한 한도 안에서 모든 제시 전략을 검토해, 순서를 바꾸는 것만으로 생성·검사할 일을 줄이지 못했다.

즉, **미리 전략을 물은 9번이 실제로 최종 선택지가 여러 개인 9번은 아니었다.** 이 작은 지도·주문표에서는 앞 단계에 AI를 넣은 비용이 늘었으며, 더 좋은 경로나 완료 시간을 얻은 근거는 없다. 기존 KEV와 코드의 약 0.08초 차이로 우열을 판단할 수도 없다. 한 번씩의 실행이며 관측·실행 주기 차이가 포함된다. 새 방식의 약 0.73초 증가를 전부 모델 호출 때문이라고 단정하지 않는다.

### 실행 조건과 종료 확인

시작 위치·지도·주문표·속도·예약 마진·작업 시간 일치, 등록 요청 지연 0.5초 이하, 기존 화면 서버의 모드·주문·시나리오 전후 동일을 모두 확인했다. 실제 최대 등록 요청 지연은 세 방식에서 각각 약 0.140·0.182·0.188초였다.

노드·물리 엣지 점유 표본은 각각 286·290·294회, 총 870회이며 중복 점유 관측은 0회다. 이는 표본 시점의 검사이며 연속 시간의 물리 안전 증명은 아니다. `WAITING` 상태 누적 관측값은 셋 다 0초지만, **픽업·작업대·배차 대기가 없었다는 뜻은 아니다.** 표의 배차 대기도 별도로 존재한다.

최종 세 로봇은 각 홈 N0·N1·N2에서 IDLE이었다. 비교용 8030 자식 서버는 모두 종료했고 사용자 화면 8000·5173과 모델 8012는 유지했다. 실기체 명령은 보내지 않았다.

### 도구 오류와 이어서 실행

첫 코드 시험이 완료된 뒤, 다음 서버를 열기 전 포트 확인 도구가 종료 직후 남은 소켓 때문에 `Address already in use`로 멈췄다. 기존 KEV 시험은 아직 시작되지 않았다. 비교 도구의 포트 확인에 `SO_REUSEADDR`를 적용하고 완료된 시험을 건너뛰는 `--resume`을 추가했다. **코드 시험을 다시 하지 않고 나머지 두 방식만 실행했다.** 정책·경로 생성·모델·지시문·주문표 소스는 변경하지 않았다. 이전 오류·완료 결과와 수정한 실행 도구 사본을 함께 보관했다.

원본 기록: `logs/order-traffic-policy-comparisons/20261023-three-way-once/`. `comparison.json`, `summary.md`, 방식별 `trial/report.json`·`observations.jsonl`, 경로 적용 기록·모델 요청과 응답 원문, `source/`, 수정 실행 도구 `source_revisions/1/`, `history/before-resume-1.json`을 보관한다. 기존 KEV 결과는 `KEV-resume-1/`에 있다. 로그는 Git 제외 대상이다.

관련 자동 검사 **256개 통과, 기존 경고 4개**. 시간 집계·미완료 표시·복귀 실패·초기 상태 비교·이어 실행 조건도 포함한다. 이는 256개의 실제 모델 시험을 뜻하지 않는다. 별도 평가 도구의 기존 지도 입력 오류가 있어 프로젝트 전체 검사 통과로 표현하지 않는다. 프런트는 이번에 수정하지 않았다.

## 판단과 다음 검토

일반 주문에서 세 방식을 바꿔 실행할 수 있고 새 방식도 연속 처리는 된다. 다만 **이번 조건에서 새 전략 순서 방식의 성능 이점은 확인하지 못했다.** 운영 기본값을 바꾸거나 좋은 결과가 나올 때까지 자동 반복하지 않는다.

후속 비교를 한다면 먼저 여러 전략을 실제로 선택할 여지가 있고 탐색 한도의 영향을 받는 상황을, 모델 결과를 보기 전에 고정해야 한다. 같은 생성·검사 예산에서 코드 순서와 KEV 순서의 성공률·계획 품질·생성 횟수·판단 시간을 함께 비교한다. 현재처럼 전략을 모두 검사하는 작은 문제에서는 순서만 바꿔 얻을 이점이 작다는 점을 기준으로 삼는다. 기존 최종 선택과 새 순서 제안의 역할 차이, jhlee의 별도 배치 시험도 계속 구분한다.
