# A·B 주문이 N5에 몰리는 경우: 기존 알고리즘과 우리 KEV

2026-10-24. 기능 확인 시험이며, 두 방식 중 어느 쪽이 더 빠른지 확정하는 시험은 아니다.

## 확인할 문제와 실행 조건

앞 로봇이 픽업대 N5를 사용하고 떠난 뒤 다음 로봇이 이동할 수 있는지, 주문이 쌓여도 작업과 홈 복귀까지 끝나는지 확인한다. 주문 실패·복귀 실패·300초 안에 끝나지 않는 정체·노드와 물리 엣지 중복 점유를 함께 본다.

| 항목 | 이번 시험 |
| --- | --- |
| 비교 | 시뮬·알고리즘의 기존 관제 → 시뮬·AI의 A*＋KEV 전략 순서 |
| 주문 | 같은 A·B 주문 12건, 총 물품 37개, C·D는 0개 |
| 접수 계획 | 처음 3건은 0초에 순차 등록, 나머지 9건은 5초부터 45초까지 5초 간격 |
| 입력 생성 | 기존 `order_traffic_load_cases.json`의 `pickup_ab`, 기존 `make_orders()`, seed 137 |
| 로봇 | 3대, N0/N1/N2에서 새 상태로 시작 |
| 공통 조건 | 같은 지도·초기 상태·주문표, 속도 0.2m/s, 예약 여유 0.2초, 작업 시간 1.5초 |
| 완료 기준 | 각 방식에서 주문 12건의 작업 완료 후 남은 복귀까지 확인, 최종 3대 홈·IDLE |
| 실행 횟수 | 각 방식 1회. 서로 독립적인 반복 실험 24회라는 뜻은 아님 |

이 입력에는 1개 주문부터 최대 적재량인 5개 주문까지 포함된다. 다만 현재 시뮬 작업 시간은 물품 수와 관계없이 1.5초이므로 실제 로봇팔의 집기 시간이나 물품별 작업 차이는 검증하지 않는다.

기존 알고리즘은 기존 예약·시간을 고려하는 경로 계산과 교통 제어를 사용한다. 우리 AI는 기본 A* 경로를 받은 뒤 KEV로 전략 검토 순서를 정하고, 코드가 경로 생성·사전 검사·최종 적용을 수행한다. AI는 다른 로봇의 이미 진행 중인 계획을 유지하면서 새 이동 요청을 조정한다.

## 기존 관제와 분리한 실행

사용자 관제의 5173·8000과 KEV 8011은 조회만 한다. 시험은 코드·지도 사본에서 백엔드 8035와 전용 KEV 8012를 사용한다. 모델은 기존 캐시의 `jaredpalmer/kev-0.8b@v1.0`을 사용하며 새로 내려받거나 환경을 설치하지 않는다. ROS·MQTT 시작 함수와 실기체 명령을 실행하지 않는다.

운영 코드와 화면을 수정하지 않고 기존 비교 도구를 재사용한다. 시험을 실행한 절차도 결과 폴더의 `run.py`에 보존한다. 전용 서버는 실행이 끝나거나 실패하면 종료하고, 실패 결과를 덮어쓰거나 성공할 때까지 자동 재시도하지 않는다.

## 결과

**두 방식 모두 12건의 작업과 홈 복귀를 완료했다.** 총 24건·물품 74개를 처리했다. 주문·복귀 실패, 300초 한도 초과, 모델 오류가 없었다. 노드·물리 엣지 점유 표본 1,306회에서 중복은 관측되지 않았다.

| 항목 | 기존 알고리즘 | 우리 KEV |
| --- | ---: | ---: |
| 주문 작업 완료 | 12/12건 | 12/12건 |
| 평균 주문 시간 | 52.82초 | 54.68초 |
| 가장 오래 걸린 주문 | 81.59초 | 85.22초 |
| 전체 주문의 작업이 끝난 시각 | 시험 시작 후 126.62초 | 시험 시작 후 130.31초 |
| 마지막 홈 복귀까지 | 136.73초 | 140.70초 |
| 최대 배차 대기 주문 | 7건 | 7건 |
| 실제 주문 판단 모델 요청·응답 | 0/0회 | 27/27회 |
| 점유 관측 표본 / 중복 | 654회 / 0회 | 652회 / 0회 |

이번 실행은 우리 방식의 평균 주문 시간이 약 1.86초 길고, 마지막 복귀는 약 3.97초 늦었다. **이번 조건에서 KEV가 더 빠르다는 결과는 나오지 않았다.** 한 번의 실행으로 항상 느리다고 확정하거나, 차이 전부를 모델 응답 시간 때문이라고 단정하지도 않는다.

KEV 방식에는 교통조정 적용 36회가 기록됐고, 전략 검토 묶음도 36개였다. 준비한 전략 중 검토를 생략한 전략은 0개였다. 따라서 이번 결과는 전략 순서 제안으로 탐색량을 줄였다는 근거도 아니다. 기존 알고리즘의 추가 교통조정 기록 0개는 로봇이 움직이지 않았다는 뜻이 아니라 추가 서비스 분기를 사용하지 않았다는 뜻이다.

### N5가 비면 다음 로봇이 진행했는가

**앞 로봇이 홈으로 돌아오기 전에 다음 로봇이 픽업을 시작하는 동작을 두 방식 모두 확인했다.** 첫 교대 장면은 다음과 같다. 아래 시각은 조회에서 처음 확인한 시각이다.

| 장면 | 기존 알고리즘 | 우리 KEV |
| --- | ---: | ---: |
| R1이 N5를 비운 것을 관측 | 10.06초 | 10.01초 |
| R2가 N5로 가는 엣지에서 이동 중인 것을 관측 | 10.06초 | 10.22초 |
| 그때 R1의 주문 단계 | 작업대로 이동 중 | 작업대로 이동 중 |
| R2가 N5에 도착한 것을 관측 | 16.80초 | 16.92초 |
| 그때 R1의 주문 단계 | 작업대 작업 중 | 작업대 작업 중 |

즉, `R1 픽업 → R1 작업대로 이동`과 `R2 픽업대로 이동`이 겹쳐 진행됐다. 관측 시각 차이가 정확한 반응 지연이라는 뜻은 아니다. 각 방식에서 N5 픽업 방문 12회를 확인했고, 첫 방문 이후 11번의 교대 모두 앞 주문의 최종 복귀 완료 단계 전에 이루어졌다. 이 교대 동작은 공통 주문 처리 흐름에도 있으므로 KEV만의 성능 개선으로 설명하지 않는다.

### 조건과 원문 재확인

같은 주문표·초기 상태·지도·주행 설정·정상 등록 지연 범위, 실제 주문 모드와 교통조정 분기 검사가 모두 통과했다. 별도 모델 서버 카운터는 0→28로, 실제 주문 판단 27회와 준비 요청 1회에 일치했다.

별도 분석에서 원문의 완료·점유·호출 수와 N5 교대를 다시 집계했고 원문 해시도 유지됐다. 시험 종료 후 백엔드 8035·KEV 8012와 시험 자식 프로세스가 모두 종료된 것을 확인했다. 사용자 5173·8000·8011은 계속 열려 있었으며 이 서버들에 변경 명령을 보내지 않았다.

## 결과를 읽을 때 지킬 기준

- 시간은 약 0.2초 간격 조회로 확인한 값이다. 평균 주문 시간은 접수 응답부터 작업대 작업 완료까지이고, 홈 복귀는 별도다.
- `WAITING` 시간 합계를 두 방식의 전체 대기 시간으로 비교하지 않는다. AI 판단 중에는 로봇이 `IDLE`일 수도 있다.
- 컴퓨터 자원을 사용자 관제와 공유하며, 같은 조건을 한 번씩만 실행한다. 작은 시간 차이나 이번 한 쌍의 결과로 AI의 성능 우위를 확정하지 않는다.
- 점유 검사는 관측한 표본에 대한 것이다. 표본 사이의 모든 순간이나 실기체 충돌 안전을 입증하는 것은 아니다.
- 앞 주문의 복귀가 끝나기 전에 다음 주문이 N5를 이용하는지 따로 확인한다. 이 동작이 두 방식에 모두 있으면 공통 주문 처리 기능의 확인이며, KEV만의 효과로 설명하지 않는다.
