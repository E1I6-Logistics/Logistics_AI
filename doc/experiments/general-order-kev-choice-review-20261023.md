# 일반 주문에서 KEV가 느린 후보를 고른 세 건 분석

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-23 정리. 분석 대상은 2026-10-21의 동일 주문 18건씩 비교 기록이다. **새 주문·가상 주행·모델 호출 없이 저장된 입력·응답·관측만 분석했다.** 운영 설정이나 관제 실행 코드는 변경하지 않았다.

## 결론부터

세 건 모두 **짧은 길에서 기다리기와 긴 길로 바로 가기** 사이의 선택이었다. 대기 시간을 포함하면 긴 길이 더 빠른 것으로 계산됐지만 KEV는 짧은 기존 길을 선택했다.

전체 예상 시간과 대기 시간은 실제 요청에 들어 있었고 응답도 그대로 실행됐다. 따라서 이번 기록에서는 대기 시간 필드 누락이나 응답 전달 오류가 원인이라는 근거가 없다. **지정한 예상 도착 시간 최소 기준을 모델 선택이 따르지 않은 경우**다. 모델이 내부에서 왜 그렇게 판단했는지는 저장된 선택·확률만으로 확정할 수 없다.

일반 주문 18건을 완료한 연결 동작은 유효하다. 이를 KEV의 시간·처리량 개선으로 해석하지 않는다. 현재 역할이 이미 계산한 시간의 최솟값 선택이라면 코드 비교가 그 기준을 직접 보장한다.

## 어떤 입력이었나

세 건은 모두 R2가 홈 N1에서 OMX1 픽업대 N5로 가는 상황이었다. R3의 복귀 경로는 N3→N11→N7→N9→N2로, R2의 기존 길과 N7·N9 및 그 사이 통로가 겹쳤다.

```text
짧은 기존 길: N1 → N9 → N7 → N5
                 예약 때문에 출발 전 대기

긴 우회 길:   N1 → N9 → N10 → N8 → N7 → N5
                 예약 대기가 거의 없어 전체 예상은 더 짧음
```

요청에는 로봇별 점유 자원·상태·목표·남은 경로, 예약 개수, 보호 자원 목록, 새 이동 요청과 후보가 들어 있었다. 지시문은 `new_request_completion_seconds`가 가장 작은 후보를 고르고 동률이면 거리로 비교하라고 명시했다. 상세 예약 시간표 전체와 지도 인접 관계 전체는 모델에 주지 않았다. 다만 이번 지정 기준을 비교하는 데 필요한 전체 예상 값은 이미 제공돼 있었다.

11번 주문의 실제 후보를 쉽게 풀면 다음과 같다.

| 항목 | 기존 길 KEEP_PATH | 우회 REROUTE_2 |
| --- | ---: | ---: |
| 거리 | 1.356m | 2.029m |
| 거리 ÷ 속도 0.2m/s | 6.780초 | 10.146초 |
| 예약 대기 예상 | 4.494초 | 거의 0초 |
| 합계 도착 예상 | **11.274초** | **10.146초** |
| KEV 선택 | 선택함 | 선택하지 않음 |

우회는 더 멀지만 이동 시간 증가보다 대기 시간 감소가 커서 전체 예상이 짧다. 모델이 이 계산을 새로 해야만 하는 요청도 아니었다. 두 합계가 후보에 명시돼 있었다.

## 세 건의 선택

| 주문 순번 | 기존 길 대기 예상 | 기존 길 합계 | 우회 합계 | KEV 선택의 예상 초과 |
| --- | ---: | ---: | ---: | ---: |
| 11 | 4.494초 | 11.274초 | 10.146초 | 1.128초 |
| 14 | 4.210초 | 10.991초 | 10.146초 | 0.845초 |
| 17 | 4.181초 | 10.961초 | 10.146초 | 0.815초 |

세 건 모두 KEEP_PATH를 골랐고, 응답 확률에서도 그 후보가 가장 높았다. API 응답·클라이언트 결과·예약 적용 기록 사이 선택 불일치는 없었다. 각 건은 모델 한 번 호출 뒤 재검사·적용됐고 선택 결과를 바꿔 적용한 재시도는 없었다.

첫 우회 생성 REROUTE_1은 N9·N7을 모두 피하도록 요청했다가 경로를 만들지 못했다. 두 번째 REROUTE_2는 N9–N7 통로만 피하는 경로로 생성·사전 검사됐고 실제 모델 입력에도 포함됐다. 첫 우회 생성 실패 때문에 더 빠른 우회를 전달하지 못한 경우가 아니다.

## 19/22회라는 숫자에서 추가로 구분할 것

| 분류 | 결과 |
| --- | ---: |
| 실제 KEV 선택 요청 | 22회, 모두 후보 2개 |
| 제공된 예상 시간 최소와 일치 | 19/22회 |
| 두 후보의 예상 시간이 같은 선택 | 7회 |
| 예상 시간이 다른 선택만 비교 | **12/15회 일치** |
| 더 먼 길이 대기를 줄여 더 빠른 선택 | **0/3회 일치** |

동률은 기존 비교와 같은 1e-9초 이내 기준을 사용했다. 동률 7회는 어느 쪽을 골라도 시간 기준에 맞으므로, 서로 다른 시간을 판별한 성공 7회라고 설명하면 안 된다. 이 표는 시간 기준이며 동률일 때의 거리 규칙까지 새로운 성능 지표로 평가한 것은 아니다.

이번 기록에서 거리와 시간의 선호가 갈리는 세 선택이 모두 위 N1→N5 유형이었다. 나머지 시간 차이가 있는 12회는 시간 최소 후보가 최소 거리 후보이기도 했고 모두 맞았다. 다만 같은 지도·같은 배차 주기에서 반복된 세 선택을 서로 독립된 세 종류의 교통 문제로 해석하지 않는다. 다른 지도·입력·모든 KEV에 대한 일반 성능 수치도 아니다.

## 계산과 실제 이동은 어느 정도 맞았나

원래 지도 해시가 같은지 확인한 뒤, 22회 요청의 총 44개 후보에 대해 노드 연결과 좌표 거리 합을 재계산했다. 모두 저장 값과 일치했고 다음 관계도 성립했다.

```text
거리 / 0.2m/s + 예약 대기 예상 = 전체 도착 예상
```

하지만 이 검사는 **거리와 합계의 일관성**을 확인한 것이다. 당시 상세 예약표 원문 전체는 보관되지 않아 예약 대기 예상 자체를 같은 시점의 예약표로 독립 재계산한 것은 아니다. 모델에 없던 예약 정보를 새로 추정해 채운 분석도 아니다.

실제 표본에서도 R2가 N1에서 WAITING인 상태를 각각 20·18·19회 관측했다. 입력의 대기 시간이 이름만 있는 값이 아니라 실제 출발 대기와 연결된 상황이었다.

| 주문 순번 | KEV 실행의 첫 픽업 이동 단계 | 코드 실행의 같은 단계 | 관측 차이 |
| --- | ---: | ---: | ---: |
| 11 | 11.241초 | 10.275초 | KEV 쪽 0.966초 길었음 |
| 14 | 11.169초 | 10.323초 | KEV 쪽 0.846초 길었음 |
| 17 | 10.968초 | 10.425초 | KEV 쪽 0.542초 길었음 |

이는 MOVING_TO_PICKUP을 처음 관측한 시각부터 WORKING_AT_PICKUP을 처음 관측한 시각의 차이다. 정확한 바퀴 이동 시간이나 연속 시각 측정값이 아니다. 대기·준비·추론이 일부 포함되고 관측 간격 오차도 있다. 두 실행은 그때의 예약·출발 시각이 달라 **같은 상태에서 선택 하나만 바꾼 반사실 시험이 아니다.**

전체 18건의 출고 완료는 KEV가 약 3.351초 늦었다. 세 선택의 예상 초과 합계는 약 2.788초이고 저장된 모델 응답 소요 합계는 약 1.987초다. 이 값들을 더해 전체 지연의 원인으로 분해할 수 없다. 다른 로봇은 추론 중에도 움직이고 이후 배차·예약·픽업 차례가 달라진다. 세 선택만 고치면 전체가 정확히 몇 초 빨라지는지는 이번 기록만으로 확정하지 않는다.

## 원인에 대해 말할 수 있는 범위

확인한 사실:

- 실제 요청에 전체 예상·거리·예약 대기와 시간 최소 지시가 있었다.
- 응답에서 KEEP_PATH를 골랐고 그대로 적용됐다. 후보 ID 변환·클라이언트 선택 뒤집힘은 없었다.
- 입력 토큰은 전체 22회에서 469~551개였고 저장된 런타임은 상태 자르기가 꺼져 있었다. 길이 제한으로 이 입력이 잘렸다는 근거는 없다.
- 세 건 모두 더 긴 전체 예상 후보를 골랐고 실제 관측에서도 N1 대기가 있었다.

아직 확정하지 않은 것:

- 거리·기존 길 이름·후보 순서·동률 지시문의 영향 중 무엇이 결정적이었는가.
- 모델이 대기 시간을 이해하지 못했는가, 다른 정보에 더 높은 점수를 줬는가.
- 우회를 골랐다면 같은 전체 주문 묶음이 정확히 얼마나 빨라졌을 것인가.

[이전의 다른 일반 주문 진단](order-traffic-selection-diagnosis-20261020.md)에서는 표현·순서 민감성이 있었지만 그 결과로 이번 세 건의 내부 원인을 확정하지 않는다. 이번에는 새 입력 변형·재질문·튜닝을 수행하지 않았다.

## 권장 방향

1. 현재 연결 동작과 예약 검사는 유지한다. 일반 주문 완료와 KEV의 추가 기여를 구분해 보고한다.
2. 이미 계산된 예상 시간 최소를 반드시 지켜야 한다면 `MIN_EXPECTED_TIME` 코드 정책을 기준으로 삼는다. 실제 운영 기본값 변경은 별도 결정이며 이번에 바꾸지 않았다.
3. KEV 모드를 비교용으로 남길 수 있지만 계산 방식보다 우수하다고 주장할 근거는 없다. 더 많은 호출 자체가 보완책은 아니다.
4. 현 단계에서는 같은 표현을 끝없이 바꾸는 대신 팀원과 주고받는 입력·출력의 책임, 현재 일반 주문에 적용되는 범위를 확정하는 것이 우선이다. KEV의 새로운 역할·학습·다른 모델은 필요성과 평가 기준이 정해졌을 때 별도 검토한다.
5. 통신 끊김 검증은 현재 발견한 고장에 대한 조치가 아니다. 사용자의 확인대로 실기체 코드에 연결 상태·경로 보호·정지 관련 처리가 있으므로 당장 필수인 다음 작업으로 고정하지 않는다.

## 근거와 재현

분석 도구는 `backend/simulation/order_traffic_saved_choice_review.py`다. HTTP·모델 클라이언트를 사용하지 않으며 보고서·표본·실행 당시 소스 사본을 읽는다. 내부 검증 조건으로 요청·응답·실행 대응과 수치 일관성을 확인하고 원본 해시가 변하지 않았는지도 검사했다. 새로 전체 자동 검사 묶음을 실행한 결과나 모델 정답 시험으로 세지 않는다.

- 원본: `logs/order-traffic-comparisons/20261021-090506-continuous18/`.
- 최종 분석: `logs/order-traffic-reviews/20261022-general-orders-3cases-final/review.json`.
- 실제 요청·응답·후보·관측: 같은 폴더의 `order-11.json`, `order-14.json`, `order-17.json`.
- 초기 집계: `logs/order-traffic-reviews/20261022-general-orders-3cases/`. 최종본은 대기 표본까지 포함한 `-final` 폴더다.

분석은 10월 22일 시작해 23일 정리했으므로 기록 폴더의 20261022 이름을 유지했다. 로그는 Git 추적 대상이 아니어서 공유 시 별도로 포함해야 한다.

다시 분석하려면 새 출력 폴더를 지정한다. 기존 결과 덮어쓰기는 거부하며 아래 실행도 서버나 모델에 요청하지 않는다.

```bash
# 로컬 보관 도구와 원문이 있을 때의 과거 재현 예시
PYTHONNOUSERSITE=1 /home/woozoo/venv/robot/bin/python \
  -m backend.simulation.order_traffic_saved_choice_review \
  --output /tmp/kev-general-order-review-new
```
