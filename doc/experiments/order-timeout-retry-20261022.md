# 길이 계속 막힌 주문의 시간 한도와 재시도

2026-10-22. 기존 관제에서 새 시뮬 주문 1건으로 출발 대기 한도·실패 상태·복귀 처리·명시적 재시도를 확인했다. A* 경로와 코드 선택만 사용하며 실기체·모델 호출·실행 코드 변경은 없다.

## 이번에 구분할 문제

[직전 시험](reservation-wait-cancellation-20261022.md)은 예약 가능한 경로를 기다리는 주문을 취소한 뒤, 길이 비어도 그 취소 주문이 다시 출발하지 않는지 확인했다. 이번에는 취소하지 않고 길을 계속 막아 둔다.

```text
새 주문이 R1에 배정됨
  ↓
N10의 R3 때문에 R1이 홈 N0에서 나갈 수 없음
  ↓
예약 가능한 경로를 0.25초 간격으로 재검사
  ↓
기본 60초 한도 초과 → 주문 FAILED, 단계·이유 기록
  ↓
기존 알고리즘으로 복귀 처리
  ↓
길을 비워도 실패 주문은 자동 재시작하지 않음
  ↓
운영자가 주문 재시도를 요청
  ↓
대기열 재등록 → 다른 가용 로봇 우선 → 작업·복귀 완료
```

의도적으로 R1=N0, R2=N1, R3=N10으로 배치한다. 운영에서 자연 발생한 장애나 로봇 고장이 아니다. R3는 시험 도구가 기존 수동 이동 API로 N2에 보내 통로를 비운다. KEV가 막힘을 푼 결과로 세지 않는다.

## 코드의 기존 정책

- 일반 주문의 경로 예약 대기 기본 한도는 `FMS_TRAFFIC_WAIT_SECONDS=60`초이며, 한도 전에 실행 가능한 경로가 생기면 재검사로 진행할 수 있다.
- 한도 초과는 **이번 제공·생성 경로로 예약하지 못했다**는 뜻이다. 지도 전체에 해결책이 없다는 수학적 판정이 아니다.
- 실패 시 주문 상태·단계는 `FAILED`가 되고, `failed_phase`, `error`, `failures`에 실패한 이동 단계와 이유를 남긴다.
- 실패 후 복귀는 기존 알고리즘 기능이다. 실패한 주문을 자동으로 PENDING으로 바꾸지는 않는다.
- 복귀 자체가 막히면 `BLOCKED`와 원인을 기록하고 해당 로봇을 새 배차에서 제외하는 코드가 있다. 홈 복귀 확인 없이 주문 재시도를 허용하지 않는다.
- `/api/orders/{order_id}/retry`는 시뮬 실패 주문을 명시적으로 다시 대기열에 넣는다. 기존 실패 이력을 보존하고 `retry_count`를 늘리며 `last_robot_id`를 기록해 다른 가용 로봇을 먼저 고려한다.
- 이 정책의 코드 위치는 `order_traffic_service.py`, `order_manager.py`, `simulation_order_runner.py`다.

복귀 실행기의 기존 180초 제한과 출발 전 교통조정 대기 60초는 다른 한도다. 이번에 둘을 변경하거나 새 무한 재시도를 추가하지 않았다.

## 화면과 알림을 구분한다

기존 주문 상세는 실패 단계·실패 이유·복귀 상태·복귀 오류를 표시하는 코드와 시뮬 실패 주문의 ‘주문 재시도’ 버튼을 갖고 있다. 실제 실패 API 값이 이 필드에 채워지는지를 확인한다. 이번에는 브라우저 화면을 직접 조작해 검증한 것으로 세지 않으며 새 팝업·외부 알림 기능을 추가하지 않는다.

## 이번 시험의 범위

R1이 실패하는 위치는 이미 자기 홈 N0이다. 따라서 복귀 완료 처리를 확인하더라도 **홈 밖에서 막힌 복귀 경로를 실제 주행으로 해소한 시험이 아니다.** 복귀 경로의 장기 차단·180초 후 중단은 별도 실시간 시험 범위다.

기존 자동 검사에서 픽업 후 실패·알고리즘 복귀·다른 로봇 우선 재시도, 복귀 불가 로봇의 배차 제외, 다른 로봇의 대기 주문 처리 세 경우가 모두 통과했다. MQTT의 기존 API 경고 1개는 남아 있다. 자동 검사의 대체 경로·시간 설정과 기존 관제 실시간 관측은 구분한다.

## 결과 기록

시각은 시험 도구 시작 기준으로, 준비·백엔드 재시작 시간도 포함한다.

| 시각 | 관측 결과 |
| --- | --- |
| 약 2.07초 | R1의 경로 예약 대기 확인. 위치 N0, 경로·이동 목표 없음 |
| 약 62.12초 | 대기 확인 후 약 60.04초에 FAILED. 실패 단계와 대기 한도 초과 이유 기록 |
| 약 62.15초 | R1 복귀 상태 RETURNED. 이미 홈이므로 새 복귀 주행은 없음 |
| 약 68.56초 | R3를 N2로 보낸 뒤에도 실패 주문은 자동으로 재출발하지 않음 |
| 약 68.71초 | 같은 주문 ID로 명시적 재시도 후 R2에 배차 |
| 약 94.70초 | 주문 작업·복귀 완료. 기존 실패 이력 보존 |

- 상태 관측 **687회**, 노드·물리 엣지 중복 점유 관측 0회.
- 최초 대기 중 R1이 N0에 머물고 경로·목표가 없는 상태를 441회 관측했다.
- 통로 해제 구간에서 실패 상태가 유지되고 과거 이동이 재출발하지 않은 상태를 48회 관측했다.
- 최종 주문은 COMPLETED, `retry_count=1`, `last_robot_id=robot1`, 재배차 로봇은 R2다. `failures`의 원래 단계·사유·시각은 그대로이며 해결된 현재 오류 표시만 해제됐다.
- 종료 시 픽업 대기열·예약 로봇 목록이 비고 작업대가 FREE다. 모든 로봇의 목표·경로가 해제됐다.
- 모델 요청 0회. 기존 실행 코드·프런트 파일 해시 변경 없음.
- 원래 시뮬·AI / A* 경로 / KEV 선택, N0·N11·N10 위치·자세·배터리를 복원했다.
- 기존 이력 15건은 내용까지 보존했고 같은 주문 ID로 실패·재시도한 신규 1건을 더해 최종 16건이다. 현재 상태 합계는 완료 14·실패 1·취소 1이며, 새로 완료한 주문에도 이번 실패 이력이 남는다.

이 한 번의 시험에서 확인한 범위에서는 실행 코드를 고칠 문제가 발견되지 않았다. 막힌 원인을 해소하지 않고 자동으로 무제한 재시도하는 기능은 추가하지 않는다. 기존의 명시적 재시도와 실패 기록을 유지한다.

## 재현과 근거

기록 폴더는 `logs/order-failure-runs/20261022-timeout-retry/`다.

- `driver.py`: 기본 실행은 시험 계획만 표시한다. `--run`은 가상 관제에 주문 1건을 넣고 일시적으로 코드 방식·시험 위치로 바꾼 뒤 원래 설정·위치를 복원한다. 기존 기록 덮어쓰기는 거부한다.
- `samples.jsonl`, `report.json`: 원본 관측과 단계 기록.
- `failed-order-before-retry.json`: 실패 단계·이유와 당시 로봇 상태.
- `unblocked-before-explicit-retry.json`, `retry-response.json`: 길이 빈 뒤 실패 유지와 명시적 재시도 응답.
- `settled-before-restore.json`, `final-server-state.json`: 완료·자원 해제와 원래 상태 복원.
- `verify.py`, `verified.json`: 원본 관측을 다시 읽어 완료·687회 점유·재시도 이력·기존 이력·설정·위치 보존을 확인한다. 이 검증 도구는 관제 명령을 보내지 않는다.
- `source-sha256.json`: 실행 전후 코드 불변 확인.

약 0.1초 대기와 API 호출 시간이 합쳐진 표본이다. 모든 순간의 안전·실기체 성능·장시간 복귀 차단을 증명하지 않는다. 로그 폴더는 저장소 추적 대상이 아니므로 공유 시 별도로 포함한다. 문서 변경 전 백업은 `logs/change-snapshots/20261022-before-timeout-retry-docs/`에 보관했다.
