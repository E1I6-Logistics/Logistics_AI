# 같은 전략 흐름에서 KEV와 고정 순서 비교

2026-10-23. [저장 로그 분석](order-traffic-load-review-20261023.md)에서 제안한 대조 시험이다. 새 KEV 방식에서 모델이 제안한 순서의 영향과 응답을 기다린 시간의 영향을 구분할 단서를 찾는다.

## 세 조건

| 조건 | 순서 제안 | 인공 대기 |
| --- | --- | --- |
| 새 KEV | 실제 KEV의 확률 순서 | 없음. 실제 응답을 기다림 |
| 고정 순서 | 기본 경로 → 생성된 우회 1 → 우회 2 | 없음 |
| 고정 순서＋평균 대기 | 같은 고정 순서 | 제안마다 약 0.190514초 |

인공 대기 값은 지난 `mixed_pickups-seed-137`의 실제 응답 15회 평균으로 **시험 전에 고정**했다. 이번 실행 결과에 맞춰 조정하지 않는다. 입력마다 달라지는 응답 시간을 정확하게 재현하거나 입력 상태를 고정한 시험은 아니다.

세 조건 모두 새 전략 흐름의 후보 생성·예약 검사·최소 예상 시간 최종 선택·최신 상태 확인·실행을 그대로 사용한다. 우회 경로는 기존 A* 생성기를 사용한다. 전략이 하나면 제안기를 호출하지 않는 조건과 호출·경로·시간 한도도 같다. 고정 순서는 임의의 새로운 우회나 이동 권한을 얻지 않는다.

현재 관제의 선택 목록이나 서비스 소스는 바꾸지 않는다. [시뮬 전용 제안기](../../backend/simulation/order_traffic_ranking_control.py)를 [별도 진입점](../../backend/simulation/order_traffic_ranking_preview.py)에서만 설치한다. 모델 응답을 기다리던 동일한 스레드 호출 위치에서 고정 응답 또는 짧은 대기를 사용한다.

## 실행 조건

- 지난 두 픽업대 방문·seed 137의 고정 주문표 12건을 사용한다. 모든 주문이 A/B와 C/D를 포함하고 주문당 총 2~5개다. 처음 3건·이후 5초 간격, 총 물품 41개.
- 순서는 새 KEV → 고정 순서 → 고정 순서＋평균 대기, 조건마다 한 번이다. 세 조건은 매번 빈 주문·홈 위치의 새 프로세스에서 실제 시간으로 실행한다.
- 속도 0.2m/s, 작업 1.5초, 예약 마진 0.2초, 출발 대기 60초·전략 검토 주기 한도 10초·우회 호출 2회·전략 제안 8회. 관측 한도 300초.
- 같은 8012 CUDA 0.8B 모델 서버를 공유한다. 시험 전체에 공통 준비 요청 1회만 보낸다. 고정 순서 조건은 모델 요청을 보내지 않는다.
- 시험 포트는 8034. 기존 화면용 8000 서버의 주문·위치·모드·시나리오는 조회만 한다. 실제 로봇·MQTT 시작 함수를 호출하지 않는다.
- 실패·복귀 오류·점유 중복이 나오면 해당 결과를 보존하고 남은 조건은 중단한다. 성공 결과만 골라 다시 실행하지 않는다.

## 기록을 읽을 때

기존 이동 이벤트에는 `kev_calls`, `selected_by=KEV_STRATEGY_ORDER_CODE_MIN_TIME`이라는 필드명이 남는다. 대조군도 동일한 원래 함수를 거치므로 **이 실험에서 그 필드를 실제 모델 호출이라고 읽으면 안 된다.**

추론 기록에 `ranking_ablation_arm`, `ranking_source`, `model_request_sent`를 추가한다. 실제 모델 요청과 고정 제안기 호출을 별도로 집계하며, 고정 제안기는 실제 전송 원문이 없다고 표시한다. 서버 요청 카운터는 실제 모델 요청 + 공통 준비 1회와 대조한다. 이 시험을 일반 KEV 성능 기록에 섞지 않는다.

확인할 값은 주문·복귀 완료, 평균 주문 시간·최종 작업/복귀 시간, 모델/고정 제안 횟수와 대기, 최대 대기열, 노드·물리 엣지 중복 점유 표본, 처음 배차·경로가 갈라지는 주문이다. 조건마다 주문표·시작 위치·지도·설정·접수 지연·소스 보존도 확인한다.

## 결과

세 조건 모두 **12건·41개를 작업·홈 복귀까지 완료**했다. 총 36건·물품 합계 123개다. 실패·복귀 오류·모델 오류가 없었고 노드·물리 엣지 점유 표본 1,821회에서 중복 관측이 없었다. 전체 실행은 약 402초였다.

| 조건 | 평균 주문 시간 | 마지막 작업 완료 | 홈 복귀까지 | 실제 모델 요청 | 고정 순서 제안 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 새 KEV | 50.48초 | 119.05초 | 128.79초 | 19회 | 0회 |
| 고정 순서 | 54.15초 | 131.08초 | 141.37초 | 0회 | 19회 |
| 고정 순서＋평균 대기 | 50.37초 | 118.95초 | 128.67초 | 0회 | 17회 |

평균 주문 시간은 접수 응답부터 작업 완료까지다. 마지막 작업 완료·홈 복귀는 이번 접수 시작부터 관측한 시각이다. 실제 모델 응답 대기 합계는 3.71초, 평균 약 0.195초였다. 인공 대기는 지난 기록으로 정한 약 0.191초이며 이번 응답 평균과 정확히 같지는 않다. 대기 조건의 고정 제안기 응답 시간 합계는 약 3.24초였다.

서버 요청 카운터는 549→569로 20회 증가했다. 실제 교통조정 모델 요청 19회와 공통 준비 1회에 해당한다. 고정 순서 두 조건은 실제 요청 0회였고 고정 제안기 기록만 남았다. 모델은 같은 CUDA `jaredpalmer/kev-0.8b@v1.0`이었다.

주문표·시작 위치·지도·속도·작업 시간·접수 지연 0.5초 이내·제안기 구분·모델 원문·요청 카운터·소스 보존 대조를 모두 통과했다. 각 조건의 48회 이동은 준비한 전략을 모두 시도했고 코드의 최소 예상 시간 규칙으로 최종 선택했다. 한도 때문에 전략을 건너뛴 경우는 없었다.

### 6번 주문이 다시 갈라졌다

| 조건 | 6번 주문 배차 관측 | 배차 로봇·출발 위치 |
| --- | --- | --- |
| 새 KEV | 약 46.65초 | R2, N3 |
| 고정 순서 | 약 47.61초 | R3, N2 |
| 고정 순서＋평균 대기 | 약 46.63초 | R2, N3 |

관측 간격은 약 0.2초이며 이 시각은 최초 확인한 상한이다. 정확한 시각은 직전 관측과의 구간 안에 있다. 한 표본의 주문·로봇 응답도 완전히 동시인 것은 아니다.

새 KEV와 고정 순서＋대기는 모든 주문의 배차 로봇과 작업대가 같았다. 48개 적용 경로 중 47개도 같았다. 다른 하나는 9번 주문의 R1 복귀였다.

```text
새 KEV:            N3 → N11 → N7  → N8 → N10 → N0
고정 순서＋대기:   N3 → N11 → N12 → N8 → N10 → N0
```

두 경로는 기록된 거리 약 2.197m·예상 시간 약 10.985초가 같았다. 세 조건의 작업대는 모두 N3이었다. 고정 순서와 새 KEV는 6번 주문에서 배차·출발 위치가 처음 갈라졌고, 이후 적용 경로 26회가 달랐다.

## 해석과 여기서 멈추는 기준

**모델을 쓰지 않고 일정 시간만 기다려도 이번 빠른 흐름이 재현됐다.** 따라서 이전 속도 차이를 KEV가 더 좋은 전략을 제안한 증거로 삼기 어렵다. 이 장면에서는 응답 대기와 배차·이동 갱신 시점이 중요한 설명이다. 준비 전략을 모두 검사한 만큼 탐색 절감도 확인되지 않았다.

이것은 아무 때나 0.191초를 기다리면 물류가 좋아진다는 뜻이 아니다. 인공 대기는 원인을 살펴보기 위한 시험 조건이며 운영에 추가하지 않았다. 같은 주문표의 한 번씩 실행이고, 입력 상태·응답 지연을 요청마다 정확히 맞춘 시험이 아니다. 제안 횟수도 19·19·17회로 달라졌다. 대기가 시간 차이의 유일한 원인이라고 확정하거나 통계적 동등성을 주장하지 않는다.

이번 진단은 계획한 세 실행으로 종료한다. 빠른 결과를 얻을 때까지 재시험하거나 대기 값을 조정하지 않았다. **현재 세 로봇·이 장면에서 KEV의 전략 판단이 별도 성능 이점을 제공한다는 근거는 부족하다.** 정상 주문 처리 기능과 AI 기여 검증을 구분해 기록하고, 관제 기본 정책·배차 규칙·실기체 코드는 바꾸지 않는다.

후속 검토는 두 방향을 구분한다. 실제 물류 개선은 복귀 로봇의 재배차가 짧은 노드 체류·갱신 시점에 좌우되는 부분을 검토할 수 있다. KEV 연구는 전략을 모두 검사할 수 없는 더 큰 문제에서 제안 순서가 계산량·계획 품질을 개선하는지 별도로 검증할 수 있다. 둘 다 아직 구현하거나 실행하지 않은 후속 제안이다.
