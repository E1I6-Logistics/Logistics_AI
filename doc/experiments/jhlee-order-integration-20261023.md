# jhlee 일반 주문 연결과 단계별 검증

2026-10-23. 사용자 승인으로 별도 시뮬 서버에서만 연결한다. 현재 사용자 화면과 기존 주문·운영 기본값은 유지한다. 아래 조건은 실제 모델 시험 전에 정한다.

## 비교하려는 것

같은 주문·배차·지도·가상 주행에서 교통 판단을 코드 / 우리 새 KEV 전략 순서 / jhlee로 바꿨을 때 작업이 이어지는지 확인한다. 기존 우리 KEV 최종 선택은 앞선 비교 기록에 보존한다.

jhlee는 검토한 고정 커밋 `d0ccc7de3980aa64afa79a7c43487c6372c88650`을 사용한다. 실시간 최신 브랜치를 자동으로 받거나 병합하지 않는다. 원본 8파일을 Git 객체에서 별도 패키지로 읽고 원문·해시를 시험 폴더에 남긴다.

## 유지하는 부분과 바꾸는 부분

- 원본 유지: 공유 구간 → 우선순위 → 대기·우회 판단 지시문, score 방식, 원본 엔진, Active/Pending 수집, 이동 중 엣지·상태 변화 검사, 기존 Active를 바꾸는 제안 거부, Pending의 실제 출발 검토·게이트. 단독 Pending에서 모델 호출을 생략하는 동작과 처음 0.5초 대기도 유지한다.
- 공통 경로 생성기: 초기 경로와 우회 생성은 기존 A*. jhlee가 공유 구간을 제거해 만든 가상 그래프를 유지한다. 최종 연결 프로필은 `OCCUPANCY_AVOID_IF_REACHABLE`이다. 원본의 점유 회피 의도를 보존해 타 로봇 점유 노드(출발·목적지 제외)를 피할 수 있으면 피하고, 불가능하면 원래 그래프의 A* 경로로 돌아가 최종 게이트에서 검사한다. 원본 AI 경로 생성의 모델 선택·남은 경로 soft 정보까지 재현하는 것은 아니다.
- 시험 설정: 원본 최대 대기 기본 180초 대신 60초, 우회 기본 3회 대신 2회. 우리 일반 주문도 출발 대기 60초·우회 최대 2개를 사용한다. jhlee의 우회 상한은 한 번의 원본 분석별 상한이고 우리 쪽의 캐시 한도와 완전히 같은 예산은 아니다. 원본 엔진 반복 20회·score 우선순위를 유지한다. 따라서 전체 방식의 비교이며 AI 단독 효과 비교가 아니다.
- 공통 실행: 기존 주문 관리자·픽업 차례·작업대·가상 로봇·TrafficManager의 점유·시간 예약. jhlee 결과를 정지 배치의 순차 계획으로 바꾸지 않고 원본 주문 게이트가 직접 공통 FMS에 요청한다.
- 설치 범위: 별도 `jhlee_order_preview` 프로세스에만 동적 연결. 일반 `start_fms.sh`, 기존 선택기 세 종류, 프런트 화면은 수정하지 않는다. 실기체 및 실행 중 정책 변경을 거부한다.

모델에 최적 시간 계산식을 새로 주거나 원본 지시문을 고쳐 우리 방식으로 바꾸지 않는다. 기록용으로만 실제 요청·응답과 보류 이유를 감싼다. 모델 서버는 현재 8012의 동일 CUDA 0.8B를 사용한다.

## 단계별 진행과 중단

1. 코드 검사: 원본 로더·A* 우회 그래프 보존·단독 Pending 출발·취소·실기체 거부·모델 원문 기록을 확인한다.
2. 주문 1건: A1 한 건을 새 서버에서 작업·홈 복귀까지 확인한다. 이 시험은 단독 요청 연결 확인으로 모델 성능 시험이 아니다.
3. 겹치는 주문: A1과 C1을 0초에 각각 넣고 Active/Pending과 실제 판단·보류·재개를 관측한다.
4. 앞 두 실제 단계가 실패·미완료·중복 점유 없이 끝났을 때만, 같은 6건·8개 표로 코드 → 우리 새 전략 순서 → jhlee를 각각 새 서버에서 한 번 비교한다. 이전 코드·새 방식 수치를 새 비교의 결과로 재사용하지 않는다.

주문 실패·복귀 오류·중복 점유가 생기면 해당 단계와 원문을 보존하고 다음 실제 단계는 자동 실행하지 않는다. 정상 주문 한 건을 해결하지 못하면 모델을 튜닝하거나 계속 재시도해 성공 기록으로 바꾸지 않는다. 각 단계 최대 관측 180초·실행 도구 상한 200초. 종료 시 도구가 시작한 서버만 종료한다. 원본 게이트의 대기 중 재분석은 모델 호출 수에 모두 포함한다.

고정 주문표는 앞선 일반 주문 비교와 같다. 0초 A1·C1 별도 주문, 2초 B1, 4초 D1, 6초 A1+C1, 8초 B1+D1. 초기 위치 N0/N1/N2, 속도 0.2m/s, 예약 마진 0.2초, 작업 1.5초, 갱신 약 0.1초. 등록 요청 지연 0.5초 이하·지도·설정 일치도 검사한다.

### 점유 정보 누락이 있었던 첫 6건 실행 — 비교 기준에서 제외하고 보존

`20261023-common-orders-three-way-once/`에서 코드·우리 방식은 각각 6/6 완료했지만 jhlee 연결은 약 93.08초에 복귀 오류를 관측해 종료했다. 작업 완료 2건·미완료 4건·복귀 오류 1건, 모델 요청 8회 모두 정상 응답, 점유 표본 414회 중복 없음이었다. R1은 N4에서 홈 복귀를 약 60.16초 기다리다 한도를 넘었다.

당시 R2가 N6에서 작업대 차례를 기다리는 정차 로봇이었고, R3의 기본 경로 `[5,6,11,3]`에 포함됐다. 원본 입력 수집은 이 로봇을 `UNMODELED_IDLE_OCCUPANCY`로 판정해 Pending 묶음 전체를 보류했다. N6을 지나지 않는 R1의 `[4,12,8,10,0]` 복귀까지 멈췄다. 같은 배치를 원본 함수로 모델 없이 재현했다. 이 보류 구간에서 두 요청의 모델 호출은 0회였다.

그러나 원본 `iterative_route_policy.py`는 점유 노드를 피해서 도달할 수 있는 다음 노드를 우선 남기고, 도달 불가일 때 기존 후보로 돌아간다. 최초 A* 어댑터는 전달받은 `traffic`을 기록만 하고 점유 회피를 적용하지 않았다. 따라서 이 실행은 **공통 A* 연결에 원본 경로 입력의 중요한 동작이 빠진 통합 실패**이며 jhlee 원본 전체나 모델 판단의 성능 실패로 결론 내리지 않는다. 실제 실패·모델 원문·소스는 지우지 않는다.

후속은 모델·지시문을 고치는 재시도가 아니라 A* 연결의 점유 회피 누락을 보완하는 것이다. 위 최종 프로필로 점유 회피·도달 불가 fallback·원본 가상 그래프 복원 금지 검사를 추가했다. 두 건 연결 확인 후 세 방식 모두 새 상태에서 다시 한 번 비교한다. 원본과 정확히 같은 AI 경로 후보 집합을 제공하는 시험은 아니며, 경로 생성기는 공통이지만 각 방식의 회피 요청·기본 경로는 달라질 수 있는 전체 흐름 비교로 범위를 명시한다.

최종 프로필의 두 건 확인은 `20261023-overlap-occupancy-profile-once/`다. 작업 끝 약 33.19초·홈 복귀까지 약 54.10초, 모델 호출 4회·오류 0회, 점유 표본 251회 중복 없음으로 완료했다. 이후 관련 자동 검사 **270개 통과·기존 경고 4개**를 확인하고 최종 세 방식 비교를 시작했다. 모델 호출이 끝나고 나서 입력을 좋은 결과 쪽으로 바꾸는 튜닝은 하지 않았다. 이번 수정은 실제로 전달된 점유 정보의 처리 누락을 바로잡은 것이며 앞선 실패는 모두 남겼다.

지도·초기 위치·주문 일정·속도·예약 마진·작업 시간 일치는 확인했다. 각 방식의 점유 표본은 283·289·396회로 총 968회이며 중복 관측은 없었다. 표본 안전 확인이지 지속 시간의 안전 증명은 아니다. 사용자 화면의 모드·기존 주문·시나리오는 전후 같았고 비교용 8031 서버는 모두 종료했다. 원래 화면과 모델 서버는 유지했다.

### 최종 실패에서 실제로 반복된 판단

이번에는 누락했던 점유 회피 입력이 반영됐다. 그러나 R3의 준비된 우회 경로가 `[2,9,10,8,12,11,6,5]`인 상태에서 R2가 N6, R1이 N4에 정지한 새 상황이 생겼다. 원본은 Pending 세 로봇을 함께 분석했고 다음 판단이 반복됐다.

1. 공유 구간 N6–N11에서 **R3 우선, R2 양보**를 선택했다.
2. R2의 현재 위치 N6이 회피 구간에 포함돼 우회를 만들 수 없었다. 원본은 `REROUTE_FAILED`와 `reroute cannot exclude current/goal node`를 기록하며 R2를 HOLD로 처리했다.
3. 다른 공유 구간에서는 R1 우선·R3 WAIT를 제안했지만, 앞의 HOLD 때문에 전체 제안은 BLOCKED였다.
4. 원본 실행 게이트는 이 경우 상태가 그대로여도 다시 분석했다. 동일 전송 본문 3종이 각각 **112회** 반복됐고, 이유 없는 동일 현상이 아니라 같은 차단 판단이 계속 재생산됐다. 원본 BLOCKED 제안 110개를 보존했다.

따라서 확인된 문제는 **선택한 우선순위에서 유효 계획을 완성하지 못한 것과, 같은 BLOCKED 상태를 반복 호출한 것**이다. 시간 한도는 있었지만 호출 중복을 억제하지 않아 비용이 늘었다. 원본의 지시문·우선순위·재시도 로직을 고쳐 성공 결과를 만들지 않았으며, 이 시험 뒤 추가 실제 모델 호출도 하지 않았다.

현재 결론은 이 고정 버전·A* 연결·상태 시점·60초 조건에서 연속 주문의 안정성이 부족했다는 것이다. jhlee의 원래 AI 경로 생성·모든 설정·다른 모델이 항상 실패한다고 일반화하지 않는다. 우리 방식의 6/6 완료도 모든 부하에서의 무고장이나 AI 성능 우수성 증명은 아니다. 지속 처리량 검증은 여전히 별도다.

### 호출 수와 종료 시점의 제한

jhlee의 348은 전송 직전에 남긴 REQUEST 시도 수다. 응답 원문은 347건이며 종료 시 R1 복귀 문맥의 `action_1` 요청 1건에 응답 기록이 없었다. 모델 서버 requests는 50→407로 357 증가해, 공통 준비 1회+우리 9회+jhlee 응답 347회와 일치하지만 **REQUEST 시도 합계와는 1회 차이**가 났다. 따라서 비교 도구의 엄격한 `model_counter_matches`와 요청·응답 개수 일치 검사는 통과하지 않았다. 이 사실을 지우거나 ‘검증 전부 통과’로 표시하지 않는다.

응답 원문에 CUDA 실행이 기록돼 있고 소스·격리·점유·서버 종료는 별도로 대조했다. 동시에 진행된 응답 시간 합계는 약 119.14초이며 실제 경과 시간과 다르다. 이 종료 불완전성과 실패를 고려해 jhlee의 정확한 평균 지연이나 처리량 우열을 계산하지 않는다. 결과 요약·원본·소스·보류 로그·`verification.json`을 함께 읽는다.

## 다음 작업의 경계

기능 연결 자체는 단독·두 건에서 확인했다. 일반 주문에서 안정적으로 교체해 쓰기 전에는 같은 상태 재호출 방지, 실패 우선순위 재검토, 준비 경로와 변경된 점유 사이의 재계획 책임을 정해야 한다. 이것은 jhlee 원본의 판단·운영 방식을 바꾸는 후속 작업이므로 이번에는 적용하지 않는다. 현재 일반 관제 기본 선택과 UI 목록도 유지한다.
