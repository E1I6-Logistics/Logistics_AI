# 실제 지도에서 두 로봇 양보가 필요한 배치 확인

**현재 배치 변경:** 화면의 같은 네 다중 양보 항목은 이제 R1=N3→N0, R2=N11→N6 양보, R3=N10→N8 양보를 사용한다. [작업대 복귀 배치·새 확인 결과](workstation-return-input-diagnosis-20261020.md). 아래 N1 배치와 시간은 당시 기록으로 보존하며 현재 실행 시간으로 읽지 않는다.

2026-10-20. 현재 `routes/test.geojson`과 기존 사전 검사기로 확인하고, **기존 관제에 고정 5단계 시나리오를 등록해 가상 로봇으로 실행까지 확인했다.** 이번 시험은 KEV를 호출하지 않는다. 일반 주문의 후보 생성기가 두 로봇 양보를 자동으로 찾도록 확장한 상태는 아니다.

## 배치

| 로봇 | 시작 | 원래 목적지 | 상태 |
| --- | --- | --- | --- |
| R1 | N1 | N0 | 이동할 로봇 |
| R2 | N9 | N9 | 정차, 시험에서 양보 허용 |
| R3 | N10 | N10 | 정차, 시험에서 양보 허용 |

필요한 연결만 표시하면 `N1 ↔ N9 ↔ N10 ↔ N0`이고, `N9 ↔ N2`, `N10 ↔ N8`을 양보에 사용할 수 있다. 실제 지도에는 다른 연결도 있다.

N1은 N9로만 나갈 수 있고 N0에는 N10에서만 들어갈 수 있다. 따라서 R1이 N0에 도착하려면 처음 N9·N10을 점유한 두 로봇 모두 그 노드를 비워야 한다. 다른 통로를 골라도 이 두 지점을 모두 피할 수 없다.

N2·N8의 양보 정차는 이번 가상 시험의 허용 설정이다. 실기체에서 정차할 수 있다는 검증이나 운영 정책 확정이 아니다. 세 로봇은 작업·예약이 없는 IDLE 상태로 가정하며 비상정지 해제를 대신하는 예제가 아니다.

## 기존 생성기와 검사 결과

기존 `TrafficSituation._build_plans()`에 다음 경로를 제공했다.

- R1 경로: N1 → N9 → N10 → N0.
- R2 양보: N9 → N2, 복귀: N2 → N9.
- R3 양보: N10 → N8, 복귀: N8 → N10.

| 현재 생성한 후보 | 결과 |
| --- | --- |
| R1만 진행 | R2·R3가 길을 막아 예약 불가 |
| R2만 양보 후 R1 진행 | R3가 N10에 남아 예약 불가 |
| R3만 양보 후 R1 진행 | R2가 N9에 남아 예약 불가 |
| 전원 대기 | 최종적으로 이것만 남음 |

반면 아래 계획을 별도로 구성해 **같은 `_preflight()`**에 넣었을 때 통과했다.

1. R2: N9 → N2.
2. R3: N10 → N8.
3. R1: N1 → N9 → N10 → N0.
4. R2: N2 → N9.
5. R3: N8 → N10.

R3를 먼저 양보시키고 R2를 양보시키는 다른 순서도 통과했다. 특정 순서 하나만 가능한 문제는 아니다.

이는 **현재 생성기가 두 로봇의 양보를 한 계획으로 묶지 못하는 한계**를 확인한 결과다. 코드 일반의 해결 불가능이나 AI 필요성을 증명한 결과가 아니다. 이번에 추가한 고정 계획은 위 5단계를 시험 설정에 직접 적어 실행한다. 별도 일반 주문 연결도 다른 로봇의 계획을 고정하므로 이 두 양보를 자동 수행하지 않는다.

원본: 검사 입력·제외 이유·통과 계획 (`logs/traffic-joint-actions/two-yield-real-map-check-20261020.json`, 로컬 보관).

## 관제에서 직접 보기

1. [기존 관제](http://100.81.82.30:5173/)에서 **시뮬 · AI**를 사용한다. 이 시험은 시뮬 · 알고리즘에서도 같은 고정 계획을 실행한다.
2. 시나리오 목록의 **기본 동작 확인 → 두 대가 비켜주고 R1 통과**를 고른다.
3. 주문 처리·복귀가 끝나고 세 로봇이 IDLE일 때 **테스트 실행**을 누른다. 실행기는 활성 예약·작업을 확인하며, 진행 중인 주문을 지우거나 대신 정지시켜 시작하지 않는다.
4. 가상 화면에서 시작 위치를 자동 배치한다. 이것은 실기체를 그 자리까지 주행시키는 과정이 아니다.
5. `1/5 R2 양보 이동`부터 `5/5 R3 원래 자리로 복귀`까지 확인한다. 이전 로봇의 도착을 확인해야 다음 단계가 시작된다.

화면이 좁으면 주문 입력창·하단 주문 현황·오른쪽 로봇 제어 패널을 접으면 지도를 크게 볼 수 있다. 중단할 때는 기존 **전체 비상정지**를 사용한다. 이 경우 뒤 단계는 보내지 않고 시나리오를 중단한다. 중단한 로봇을 다음 시험에서 다시 움직일 때는 정지 상태를 확인한다.

완료 후 로봇은 **R1=N0, R2=N9, R3=N10**에 남는다. 홈 N0·N1·N2로 추가 복귀시키지 않는다. 같은 시나리오를 다시 실행하면 시작 배치를 다시 준비한다.

### 설정과 실행 위치

| 역할 | 파일 |
| --- | --- |
| 시작 배치·고정 5단계 | `tests/traffic_scenarios.json`의 `fixed_two_robot_yield` |
| 고정 계획 형식·예약 사전 검사·실행 직전 재검사 | `backend/app/services/traffic_joint_actions.py` |
| 기존 가상 관제에 순차 이동 명령·진행 표시·중단/시간 제한 | `backend/simulation/traffic_joint_action_scenario.py`, `backend/app/services/scenario_service.py` |

`traffic_selector: fixed`와 `fixed_plan`을 함께 지정한다. `fixed_plan.steps`는 공통 실행기에서 처리하므로 로봇 두 대의 양보만 별도 동작으로 하드코딩하지 않았다. 1~32단계 형식 검사를 하고, 전체 계획이 기존 `_preflight()`를 통과해야 한다. 원래 목적지 복귀가 빠진 계획도 거부한다. 일반 후보 생성과 KEV 선택 방식의 기본값은 유지했다.

기존 관제의 **시뮬 · AI**에서 실행했다. KEV 경로 생성 0회, 조정안 선택 0회다. 모델 객체도 만들지 않고 고정 계획을 검사해 실행한다.

- 167회 위치 관측에서 노드·물리 엣지 중복 점유 0회. 실행기 자체의 점유 검사도 실패하지 않았다. 연속 물리 공간에서 충돌이 없다는 실기체 검증을 뜻하지 않는다.
- 완료된 주문 102건을 백업·복원해 재시작했고, 시험 전후 주문 API 내용이 같았다.
- 전체 자동 검사 **215개 통과**, 프런트 타입 검사·빌드 통과. 자동 검사는 별도 가상 상태에서 오류·회귀 여부를 확인한 것이며 KEV 호출 215회를 뜻하지 않는다.
- 추가 검사에는 존재하지 않는 경로, 대기 불허 노드, 한 로봇의 양보 누락, 복귀 누락, 중단 후 다음 단계 차단, 시간 초과 시 전체 정지, 실제 모드 실행 거부가 포함된다.

## 공정한 비교의 의미

AI만 두 로봇 양보를 허용하고 현재 단일 양보 생성기를 비교하면, 기능을 추가한 효과와 AI의 판단 효과가 섞인다.

양쪽 모두 같은 양보·이동·복귀 동작과 같은 단계 한도를 사용하게 한다. 일반 코드는 허용된 움직임을 차례로 조합해 보고, KEV는 같은 움직임에서 시도할 순서를 제안한다. 계획 생성·검사 횟수와 전체 시간도 함께 기록한다. 검증용 정답 계획을 모델에게 미리 주고 이를 탐색 성능으로 보고하지 않는다.

이 작은 사례는 복구 조합의 기능 확인용이다. AI가 더 좋은 계획을 더 적은 시도로 찾는지 평가하려면 다른 배치와 일반 탐색 기준이 추가로 필요하다.

## 한도는 어디까지 있는가

| 항목 | 현재 코드 |
| --- | --- |
| 일반 주문의 예약 가능한 경로 대기 | `FMS_TRAFFIC_WAIT_SECONDS`, 기본 60초 |
| 모델 선택·개별 우회 생성 응답 한도 | `FMS_TRAFFIC_SELECTION_SECONDS`, 기본 10초. 남은 전체 한도와 함께 적용 |
| 우회 경로 생성 요청 수 | `FMS_TRAFFIC_REROUTE_LIMIT`, 기본 2개 |
| 새 AI 복구의 전략 제안·실패 피드백·횟수/시간 한도 | 미구현 |
| AI 복구 실패에서 전용 운영자 확인 요청으로 전환 | 미구현. 기존 주문 실패 표시와 복구 흐름은 있음 |

## 다음 제안

1. **완료:** 고정 계획을 시나리오에 등록하고 기존 검사·실행기로 화면에서 확인했다.
2. **실험 범위에서 완료:** 위 5단계를 직접 적지 않고 제공한 이동 경로에서 순서를 찾는 코드 탐색을 추가했다. [자동 탐색 입력·한도·결과](two-yield-search-20261020.md). 여러 로봇을 순서대로 움직이는 실행 기능과, 그 순서를 자동으로 찾는 기능은 별개다.
3. **다음:** 같은 허용 동작·탐색 한도로 일반 탐색과 KEV의 전략 제안을 비교한다.
4. 복구 한도와 운영자 요청 상태를 정의한 뒤 일반 주문·모니터링 연결을 검토한다.

고정 계획 시험과 제공 경로 기반 코드 탐색까지 구현·확인했다. KEV 전략 제안, 일반 주문에서의 여러 로봇 양보 자동 실행은 아직 적용하지 않았다.
