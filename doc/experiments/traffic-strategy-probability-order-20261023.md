# 같은 가상 상태에서 KEV의 후보 확률 순서를 재사용하는 비교

2026-10-23. 사용자 승인으로 호출 절감 방식을 별도 비교한다. 기존 관제·일반 주문·실기체 연결은 바꾸지 않는다.

후속 [새로운 네 장면 비교](traffic-strategy-probability-new-cases-20261023.md)도 완료했다. 두 KEV 방식이 같은 최종 계획을 찾으면서 호출 합계 51회→15회, 판단 시간 합계 약 10.89초→2.93초였다. 각 시험의 조건과 한계는 분리해 기록한다.

## 왜 비교하나

[이전 시험](traffic-strategy-three-way-20261023.md)의 세 로봇 출발 장면에서 새 KEV 전략 탐색은 모델을 25회 호출하고 약 5.53초를 썼다. 코드보다 좋은 계획을 찾지는 못했다. 호출 수 자체를 낮추는 것이 목표는 아니다. **같은 상태를 반복 질문하는 비용을 줄이면서 해결률과 계획 품질을 유지할 수 있는지** 확인한다. 여러 기능이 동시에 요청하는 서버 부하 시험은 별도이며 이번에 수행하지 않는다.

## 세 방식의 차이

| 방식 | 다음에 시도할 전략을 정하는 방법 |
| --- | --- |
| 코드 탐색 | 기존 요청 순서로 시도 |
| 기존 KEV 전략 탐색 | 전략 하나를 시도할 때마다 남은 후보와 최신 실패·현재 최선 지표를 다시 질문 |
| KEV 확률 순서 재사용 | 같은 가상 상태의 후보를 한 번 질문하고 확률이 높은 순서대로 생성·검사 |

KEV는 완성된 순서 목록을 반환하지 않는다. 기존 choice 응답의 후보별 확률을 **코드가 정렬**한다. 동점은 입력 순서를 유지한다. 이 순서는 해당 상태의 모델 선호도이며 실제 도착 시간·실행 가능성의 순위나 보증이 아니다. 후보를 제거하고 다시 질문했을 때와도 같은 결과를 보장하지 않는다.

## 다시 질문하는 시점

여기서 같은 상태는 **고정된 입력 사본과 지금까지 선택한 이동 단계가 같은 탐색 지점**을 말한다. 로봇 위치만 같다고 서로 다른 예약·계획의 응답을 공유하지 않는다.

1. 새 탐색 지점에 들어가면 그 지점의 전체 전략 후보를 한 번 질문한다.
2. 받은 확률 순서로 경로를 생성·검사한다. 실패한 후보는 실제로 실행하지 않는다.
3. 같은 지점에서 다른 후보를 시도할 때는 다시 질문하지 않는다. 자식 탐색에서 되돌아와도 그 지점의 순서는 유지한다.
4. 유효한 이동을 계획에 추가하고 다음 가상 상태에 들어가면 새로 질문한다. 그때까지의 최근 실패 기록과 현재 최선 지표를 입력에 반영한다.
5. 후보가 하나면 모델을 호출하지 않는다. 시간·검사·우회·모델 상한은 매 단계 적용한다.

따라서 같은 지점의 순서를 정한 뒤 발생한 실패는 **그 지점의 남은 순서에는 반영하지 않는다.** 실패 피드백을 덜 반영하는 대가로 호출을 줄이는 방식이다. 이를 단순한 속도 최적화로 단정하지 않고 별도 정책으로 비교한다. 실시간 상태가 바뀐 요청에 과거 확률을 재사용하는 기능은 아니다.

확률이 누락되거나 후보 ID가 다르거나 유한한 0~1 값이 아니거나 합계가 1에서 크게 벗어나면 오류로 끝낸다. 순서를 임의로 채우지 않는다. 이미 검사를 통과한 완성 계획은 보존하지만 미완성 계획은 실행하지 않는다.

## 비교 전에 고정한 조건

- 이전과 동일한 5장면, 지도, 입력 어댑터, 공통 A*, 정지한 로봇, 활성 예약 없음, 한 대씩 목적지까지 순차 이동.
- 공통 판단 시간 10초, 예약 검사 128회, 우회 경로 생성 16회, 이동 단계 8개, 개별 모델 요청 2초. 총 모델 호출 상한만 없는 `equal_time` 조건.
- 같은 모델·지시문으로 각 장면·방식을 한 번씩 실행한다. 기존 세 방식 비교의 기본값과 과거 결과는 유지한다. 이번에는 jhlee를 재실행하지 않는다.
- 비교할 값: 해결 여부, 예상 평균 도착 시간, 가상 실행 평균, 첫 완성 계획까지의 시간, 전체 판단 시간, 실제 모델 호출·우회·검사 수.
- 25회였던 과거 기록과 새 결과를 단순 비교하지 않고 **같은 실행에서 기존 방식도 다시 실행**한다. 한 번씩의 결과로 일반적 우열이나 처리량 개선을 주장하지 않는다.
- 개선이 없으면 추가 튜닝·반복을 자동으로 이어가지 않는다. 기존 관제의 기본 판단기를 바꾸지 않는다.

```bash
cd ~/dev/Logistics_AI
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python \
  -m backend.simulation.traffic_strategy_comparison --run \
  --comparison repeat_vs_rank --profile equal_time \
  --host http://127.0.0.1:8012 \
  --output logs/traffic-strategy-comparisons/새로운-확률순서-비교폴더
```

기본 `--comparison three_way`는 기존 코드·KEV·jhlee 비교를 유지한다. 결과 폴더는 덮어쓰지 않는다. 원본 소스·입력·질문·응답·검사·실행 결과를 저장한다. 확률 순서와 그 순서가 정해진 계획 단계도 기록한다.

## 실제 KEV 비교 결과

같은 5장면을 세 방식으로 한 번씩, 총 15회 실행했다. `jaredpalmer/kev-0.8b@v1.0`, CUDA / torch / bfloat16, temperature 2.3510958125672174, prefix cache 꺼짐으로 시험용 8012 서버를 사용했다. 시작 전 8011·8012는 꺼져 있었고, 시험 후 직접 켠 8012 서버만 정상 종료했다. 기존 관제·주문·실기체에는 명령하지 않았다.

원본: `logs/traffic-strategy-comparisons/20261023-real-model-probability-order-once/`의 `report.json`, `summary.md`, `verification.json`, `source/`, `local_source/`. 로그는 Git 제외 대상이므로 별도 보관이 필요하다.

### 세 로봇 출발 장면

| 항목 | 코드 탐색 | 기존 KEV: 매번 질문 | KEV: 확률 순서 재사용 |
| --- | ---: | ---: | ---: |
| 모델 호출 | 0회 | 25회 | **8회** |
| 전체 판단 시간 | 약 0.019초 | 약 5.667초 | **약 1.723초** |
| 첫 완성 계획 발견 | 약 0.002초 | 약 0.506초 | 약 0.314초 |
| 찾은 유효 완성 계획 | 12개 | 11개 | 11개 |
| 예약 검사 | 36회 | 32회 | 32회 |
| 우회 경로 생성 | 16회 | 16회 | 16회 |
| 선택 계획의 예상 평균 도착 | **19.327초** | 20.143초 | 20.143초 |
| 가상 이동의 실제 평균 도착 | **19.900초** | 20.717초 | 20.717초 |

세 방식 모두 우회 생성 16회 한도에서 끝났다. 이미 전체 검사를 통과한 완성 계획만 실행했다. 전역 최적을 구한 결과가 아니다.

두 KEV 방식은 이번 장면에서 **같은 최종 계획**을 골랐다. R2가 N1→N9→N7→N11→N6로 우회한 뒤 R1·R3가 이동했다. 코드는 같은 R2 우회를 쓰되 R1을 먼저 보내는 순서를 찾아 평균이 더 작았다.

따라서 이번 호출 감소는 계획 품질을 유지하며 질문 비용을 줄인 결과다. **코드보다 좋은 계획을 찾았다는 결과는 아니다.** 판단 시간을 가상 이동 시간에 더한 값도 실측 주문 처리량이나 실제 연속 주문 처리 시간이 아니다.

### 코드 검사와 한계

관련 비교 도구 검사 24개가 통과했다. 교통조정·주문·시나리오·예약·배차 연결을 명시해 실행한 회귀 검사도 **238개 통과, 기존 경고 4개**였다. 이는 가짜 응답과 고정 입력으로 코드 동작을 확인한 숫자이며 모델 성능 성공 횟수가 아니다.

프로젝트 전체 검사 수집은 기존 `test_selector_latency_benchmark.py`, `test_selector_question_types.py`의 지도 입력 오류로 중단됐다. 두 파일을 단독으로 실행해도 각각 `Point 노드 없음`, `0→2 노드 없음` 오류가 났다. 이번에 변경한 탐색기·비교 실행기를 사용하지 않는 평가 모듈이며, 해당 평가 도구나 지도 파일은 수정하지 않았다. 따라서 전체 검사가 통과했다고 표현하지 않는다.

이번 검증은 고정된 정지 장면을 한 번씩 비교한 결과다. 실패 피드백이 중요한 다른 장면에서 순서 재사용이 손해를 볼 수 있다. 서버 동시 요청·GPU 사용률·일반 주문 처리량 시험은 하지 않았다.

**현재 판단:** 확률 순서 재사용은 별도 실험 방식으로 유지할 가치가 있다. 기존 KEV 반복 질문 방식도 보존한다. 이번 결과만으로 일반 주문의 기본 판단기를 바꾸거나 추가 모델 튜닝을 이어가지 않는다.
