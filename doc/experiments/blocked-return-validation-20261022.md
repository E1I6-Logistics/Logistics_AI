# 홈 밖에서 복귀 길까지 막힌 경우

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-22. 기존 관제의 가상 로봇으로 출발 실패·복귀 한도·배차 제외·운영자 조치 후 복귀·명시적 재시도를 확인했다. 관제 실행 코드와 기본 시간 한도는 바꾸지 않았다. 경로는 A*, 후보 선택은 시험 중에만 코드 방식이며 KEV 성능 시험이 아니다.

## 이전 시험과 다른 점

[직전 60초 한도 시험](order-timeout-retry-20261022.md)은 R1이 이미 홈 N0에 있었다. 이번에는 R1을 홈 밖 **N3**에 두고 유일한 출입 길목 **N11**을 R3로 막았다. 배치는 기존 시뮬 좌표 설정으로 만든 시험 조건이며, 자연스럽게 주문을 처리하다 발생한 고장 사례나 실제 로봇 주행이 아니다.

```text
R1=N3 ── R3=N11에서 운영자 정지 ── … ── R1 홈 N0
            ↑ 이곳을 지나야 출발·복귀 가능

R2는 다른 통로로 N6 픽업 → N4 작업대 → 홈 N1을 이용
```

분리된 상태 사본에서 먼저 확인했다. 단순히 대기하는 R3는 기존 `TrafficManager`가 N12로 자동 양보시킬 수 있다. 기존 정지 명령으로 `stop_requested=true`가 된 R3는 자동으로 비켜주지 않으므로 장기 차단을 재현할 수 있다. 고장·작업 중인 로봇을 임의로 IDLE로 바꾸거나 예약 검사를 제거한 것이 아니다. R3의 표시 상태 IDLE과 운영자 정지 플래그를 함께 확인했다.

## 실제 관제에서 관측한 흐름

| 시험 시작 후 | 관측 결과 |
| --- | --- |
| 약 1.93초 | R1의 A 1개 주문이 출발 전 예약 대기 |
| 약 62.02초 | 약 60.09초 대기 뒤 FAILED. 단계·이유 기록 |
| 약 62.06초 | 기존 알고리즘으로 홈 N0 복귀 시도. N3에서 WAITING, 복귀 상태 RETURNING |
| 약 99.29초 | R1이 복귀를 기다리는 동안 R2의 별도 C 1개 주문이 픽업·N4 작업·복귀까지 완료 |
| 약 242.14초 | 복귀 대기 약 **180.09초** 후 BLOCKED. R1 정지, 목표·경로 해제, 복귀 오류 기록 |
| 약 242.17초 | 홈 밖 R1의 실패 주문 재시도는 HTTP 409로 거부 |
| 약 279.29초 | BLOCKED 뒤 등록한 다음 C 1개 주문도 R1을 제외하고 R2가 작업·복귀 완료 |
| 약 290.15초 | 운영자가 R3를 N2로 보내 길을 비워도 R1은 N3에 그대로 있음. 홈 밖 재시도는 계속 409 |
| 약 301.47초 | 운영자 이동 명령으로 R1이 N3에서 홈 N0까지 실제 가상 주행. 복귀 상태 RETURNED |
| 약 327.56초 | 같은 실패 주문을 명시적으로 재시도. 이전 R1 대신 R2가 작업·복귀 완료 |

출발 전 60초와 복귀 시도 후 180초는 별도 한도다. 복귀 타이머는 복귀 경로 요청이 반환된 뒤 시작한다. 이번에는 그 요청이 WAITING으로 반환되어 180초 대기 분기를 실제로 관측했다. 연결 끊김·경로 계산 예외처럼 그 전에 실패하는 분기까지 같은 시간만큼 기다린다는 뜻은 아니다.

길이 비는 것만으로 실패 주문·복귀가 자동 재시작되지는 않았다. 통로 해제 후 정차 유지는 이동 시간과 추가 1초 동안 관측했다. 운영자가 정상 홈 복귀를 시킨 뒤에만 재시도를 허용했다.

## 결과를 어떻게 해석할까

- 신규 주문은 3건이다. 그중 하나가 한 번 실패한 뒤 **같은 주문 ID**로 재시도해 완료됐고 나머지 두 건도 완료됐다. 실패·재시도를 별도 신규 주문으로 세지 않는다.
- 원래 실패의 `failures` 기록을 보존했다. 재시도에는 `retry_count=1`, `last_robot_id=robot1`이 남고 R2로 재배차됐다. 해결 후 현재 오류 필드만 정리됐다.
- 관측 1,748회에서 노드·물리 엣지 중복 점유 관측 0회. 연속된 모든 순간이나 실기체 안전을 증명하는 수치는 아니다.
- 모델 선택 요청 0회. 일반 주문의 코드 선택과 기존 알고리즘 복귀를 확인한 시험이며 KEV가 막힘을 풀었다고 세지 않는다.
- 기존 이력 16건을 내용까지 보존했고 시험 종료 시 19건이 됐다. 원래 시뮬·AI / A* 경로 / KEV 선택과 가상 위치 N0·N11·N10을 복원했다.
- 관제 실행 코드 7개 파일의 전후 해시가 같았다. 실행 코드를 수정할 결함은 이번 흐름에서 발견하지 않았다.

## 복귀한 R1의 새 주문 재사용

위 시험의 명시적 재시도는 다른 로봇 우선 정책에 따라 R2가 맡았다. 이것만으로 R1이 새 주문을 실제로 처리했다고 세지 않고 별도 한 건을 더 확인했다.

- 기존 19건 이력을 보존하고 가상 로봇 시작 위치만 홈 N0·N1·N2로 맞췄다. 새로운 복귀 차단 상황을 다시 만든 시험은 아니다.
- 새 A 1개 주문이 R1에 배정돼 작업 완료 약 18.16초, 홈 복귀까지 약 29.25초에 끝났다.
- 관측 155회에서 중복 점유 0회. 후보 선택은 3번 모두 단일 후보여서 모델 요청 0회다.
- 다시 원래 KEV 선택과 N0·N11·N10 배치로 복원했다. 최종 이력은 **20건 = 완료 18·실패 1·취소 1**이다. 원래 16건과 이번 신규 4건을 모두 보존했다.
- 관련 자료는 완료한 시험 폴더의 `r1-reuse/`에 있다. `tests/blocked_return_reuse_live.py`가 실행 도구이며 기존 본 시험 검증이 완료돼야 실행할 수 있다.

두 시험 표본을 합치면 1,903회지만 서로 다른 흐름이므로 본 시험 1,748회와 재사용 155회를 구분해 보고한다. 현재 원래 배치 N0·N11·N10에서는 R3가 R1 출구를 막을 수 있으므로 일반 주문을 다시 시험할 때는 시험 배치를 먼저 확인해야 한다.

## 첫 준비 시도와 수정한 시험 도구

최초 준비에서는 재시작 직후 R1을 N3에 배치했다. 재시작 도구의 ‘작업대가 비어 있어야 한다’는 조건에 걸려 **주문 등록 전에 중단**됐다. 가상 배치가 일부 변경되어 원래 16건 이력·설정·위치를 먼저 복원했고 그 근거를 따로 남겼다. 관제 처리 실패나 정상 시험 성공으로 세지 않는다.

다시 시도할 때는 재시작을 작업대가 빈 배치로 완료하고 기존 시뮬 좌표 설정 API로 R1을 N3에 놓았다. 재시작 도구의 조건을 완화하거나 관제 코드를 바꾸지 않았다.

## 기록과 재현

- 준비 중단·원상 복원: `logs/order-failure-runs/20261022-blocked-return/`.
- 완료한 시험: `logs/order-failure-runs/20261022-blocked-return-verified/`.
- `isolated-setup-probe.json`: 일반 정차와 운영자 정지의 자동 양보 차이.
- `return-wait-start.json`, `return-blocked.json`: 홈 밖 복귀 대기와 180초 뒤 차단 상태.
- `other-order-during-return.json`, `other-order-after-blocked.json`: R2 작업 지속.
- `retry-rejected-*.json`, `returned-before-retry.json`, `retry-response.json`: 재시도 거부·정상 복귀·재시도 허용.
- `samples.jsonl`, `report.json`, `verified.json`: 관측·단계 기록과 읽기 전용 재검사 결과.
- `source-sha256.json`, `original.json`, `final-server-state.json`: 실행 코드 불변·기존 이력·설정·위치 보존.

주문을 등록하고 서버를 재시작하는 시험은 다음 도구의 `--run`일 때만 실행된다. 기본 실행은 계획만 보여준다.

```bash
# 로컬 보관 도구와 원문이 있을 때의 과거 재현 예시
PYTHONNOUSERSITE=1 /home/woozoo/venv/robot/bin/python tests/blocked_return_live.py
```

기록만 다시 확인하려면 다음을 실행한다. 관제 명령이나 모델 요청을 보내지 않는다.

```bash
# 로컬 보관 도구와 원문이 있을 때의 과거 재현 예시
PYTHONNOUSERSITE=1 /home/woozoo/venv/robot/bin/python tests/verify_blocked_return.py \
  logs/order-failure-runs/20261022-blocked-return-verified
```

이번에 새로 만든 것은 시험 실행·관측·저장 기록 검사 도구다. 관제 화면의 시나리오 목록을 추가·삭제하지 않았다. 실행 당시 도구는 `executed-driver.py`, 지도 저장을 추가한 재현용 사본은 `driver.py`로 구분해 보관했다. 실제 시험 중 지도 사본은 별도로 저장했다. 로그는 Git 추적 대상이 아니므로 공유 시 별도로 포함한다.
