# 보통 주문과 중간 주문 폭증: 기존 알고리즘·우리 AI 비교

## 목적과 사전 조건

먼저 **시뮬·알고리즘(기존 관제)**과 **시뮬·AI(A*＋우리 KEV 전략 교통조정)**의 전체 흐름을 비교한다. 일반 주문에도 두 방식이 모두 동작하는지, 주문이 갑자기 몰릴 때 실패·장기 정지 없이 해소하는지 확인한다. 아직 실기체 비교나 KEV 판단 하나의 기여를 분리한 시험은 아니다.

이전 혼합 12건은 모든 주문이 두 픽업대를 방문했다. 이번에는 픽업대 한 곳만 방문하는 주문과 두 곳을 방문하는 주문을 섞는다. 실제 물류 주문 통계가 없는 상태에서 정한 시험 구성이므로 현실 전체를 대표한다고 주장하지 않는다.

## 주문표와 실행 순서

- 주문표 번호(seed) 42·137. 각각 12건, A/B 픽업대만 방문 4건·C/D 픽업대만 방문 4건·두 픽업대 방문 4건. 주문 순서와 수량은 번호로 고정한다.
- 주문별 A+B+C+D 합계 1~5개. 두 조건은 품목·수량·순서를 완전히 같게 하고 접수 시각만 바꾼다.
- 보통 접수: 0·12·24·…·132초에 한 건씩 접수한다. 12초는 이번 시험을 위해 정한 간격이며 실제 시스템의 표준 주문 간격이 아니다.
- 중간 폭증: 0·12·24초에 한 건씩 접수한 뒤 36초에 남은 9건을 연달아 접수한다. API 요청은 순차 처리하므로 정확히 같은 순간의 동시 접수는 아니다.
- 순서: 보통42 알고리즘→AI, 폭증42 AI→알고리즘, 보통137 AI→알고리즘, 폭증137 알고리즘→AI. 총 8회 운행·96건. 각 주문표·모드는 한 번씩 실행하므로 동일 조건의 반복 성능이나 통계적 우위를 확정하지 않는다.
- 지도·초기 위치 N0/N1/N2·로봇 3대·속도 0.2m/s·예약 여유 0.2초·작업 1.5초·갱신 0.1초·관측 약 0.2초를 공통으로 유지한다.
- 각 운행 300초, 새 교통조정 대기 60초·검토 주기 한도 10초·우회 생성 2회·전략 제안 8회. 기존 알고리즘의 원래 예약·주행 흐름은 바꾸지 않는다.
- 시험 실패 또는 조건 불일치가 나오면 기록을 보존하고 남은 시험을 중단한다. 결과를 유리하게 만들기 위해 수치·지시문을 바꾸거나 자동 재시험하지 않는다.

## 왜 12건인가: 선택 근거와 한계

**12건은 통계 계산이나 MAPF 표준에서 나온 최소 시험 건수가 아니다.** 짧은 초기 연결·부하 확인을 위해 선택한 규모다. 이번 생성기는 A/B 픽업대 전용 4건·C/D 픽업대 전용 4건·두 픽업대 방문 4건으로 균형을 맞춘다. 이는 시험 구성의 설명이며 12건이면 성능이 검증된다는 근거가 아니다. 로봇이 3대여서 반드시 12건이어야 하는 것도 아니고, 각 로봇에 4건씩 배차된다는 뜻도 아니다.

현재 자료로 말할 수 있는 것은 정해진 짧은 주문표에서 작업·복귀가 완료되고 관측한 점유에 중복이 없었다는 것이다. 장시간 처리량·드문 실패·특정 로봇의 장기 대기·일관된 AI 속도 이점을 충분히 확인한 것은 아니다.

시험 규모는 다음 세 가지를 따로 정해야 한다.

| 구분 | 의미 | 현재 상태 |
| --- | --- | --- |
| 한 운행의 길이 | 한 번에 몇 건 또는 몇 분 동안 공급하는가 | 12건, 보통 접수 132초·폭증 접수 약 36초까지 공급한 뒤 복귀까지 관측 |
| 주문표의 다양성 | 품목·수량·순서가 다른 입력을 몇 개 쓰는가 | 2개 |
| 반복 실행 | 같은 입력과 조건을 초기 상태부터 몇 번 다시 실행하는가 | 주문표·접수 조건·모드별 1회 |

따라서 **96건 처리는 독립적인 비교 실험 96회가 아니다.** 한 운행의 주문들은 같은 로봇·픽업대·예약을 공유해 앞 주문이 뒤 주문에 영향을 준다. 두 입력에 접수 조건 두 개·모드 두 개를 적용한 8회 운행으로 읽는다.

반복 횟수는 우선 소규모 예비 실행에서 결과가 얼마나 흔들리는지 확인하고, 어느 정도 차이를 구별할 것인지와 허용 오차·신뢰 수준을 정한 뒤 산정하는 것이 적절하다. [FHWA 2019 시뮬레이션 대안 비교 지침](https://ops.fhwa.dot.gov/publications/fhwahop18036/chapter6.htm)은 여러 초기 실행의 변동을 이용해 필요한 반복 횟수를 정하는 절차를 제시한다. 도로교통 분야의 일반적인 실험 설계 원칙을 참고하는 것이며 AMR에서 12건이나 특정 반복 횟수가 필수라는 규정으로 적용하지 않는다.

우리 프로젝트에 적용할 예시는 평균 주문 시간 차이를 1초 정도까지 구별할지 먼저 정하고, 같은 주문표에 두 방식을 짝지어 예비 반복한 뒤 필요한 횟수를 계산하는 것이다. 1초 역시 아직 합의한 판정 기준이 아닌 제안이다. 12건을 36건으로 늘리거나 반복을 5회로 정하는 것만으로 통계적 충분성이 자동 확보되지는 않는다.

## 주문표와 접수 조건은 어떻게 다른가

| 주문표 | 주문 수 | 물품 합계 | 방문 구성 | 보통/폭증 사이 품목·수량·순서 |
| --- | ---: | ---: | --- | --- |
| 주문표 1: seed 42 | 12건 | 32개 | A/B 전용 4건·C/D 전용 4건·두 픽업대 4건 | 완전히 동일 |
| 주문표 2: seed 137 | 12건 | 43개 | 같은 구성 비율 | 완전히 동일 |

주문표 1과 2는 품목 조합의 배치 순서와 수량이 다르다. 단순히 같은 주문 목록의 접수 시각만 바꾼 두 목록이 아니다. 반면 **각 주문표 안에서 보통 접수와 폭증은 접수 시각만 다르며**, 같은 조건의 알고리즘/AI에도 같은 입력을 전달한다. 물품 합계와 방문 구성은 저장된 네 주문표를 직접 대조해 확인했다.

## 추가로 검토할 시나리오와 우선순위

아래는 후속 제안이며 이번에 새 운행을 실행하거나 운영 규칙을 변경한 결과가 아니다.

| 우선순위 | 상황 | 확인할 내용 |
| --- | --- | --- |
| 1 | A/B 주문만 집중, 별도로 C/D 주문만 집중 | 한 픽업대의 작업·통로가 몰릴 때 차례 유지, 대기 해소, 뒤 주문 진행 |
| 2 | 물건을 집는 작업 시간이 길어지거나 한 작업대가 오래 사용 중 | 정상적인 작업 대기와 통행 막힘을 구분하고, 뒤 주문까지 불필요하게 정지하는지 확인 |
| 3 | 세 로봇의 통로가 겹친 상태에서 새 이동 요청, 일시 점유 후 해제 | 실제 점유·기존 예약을 반영한 대기/우회, 자원 해제 후 재개. 우회가 있는 경우와 없는 경우를 구분 |
| 4 | 주문을 일정 시간 계속 공급하고 끝에 모두 처리 | 오래 밀리는 주문, 대기열의 증가·해소, 반복 배차·복귀, 같은 시간에 완료한 물품 수 |
| 5 | 진행 불가 또는 모델 응답 실패 | 억지로 출발하지 않는지, 정지·실패 이력·정해진 한도가 작동하는지. AI 성능 비교와 별도 운영 예외 검사 |

평가에서 두 방식에 같은 초기 점유·경로 제약·작업 지연을 줘야 한다. AI만 우회를 허용하거나 막힌 위치를 미리 알려주고 결과를 비교하면 AI 기여를 공정하게 판단할 수 없다. 현재의 자동 연결은 다른 로봇의 기존 계획을 유지한 새 이동 요청 조정이다. 여러 로봇을 순차 양보시키는 별도 시나리오가 일반 주문에서 자동 복구하는 기능으로 이미 연결된 것은 아니다.

관제의 대기/우회/양보 시나리오는 특정 장면의 동작을 확인하는 데 쓰고, 일반 주문 시험은 배차·픽업·작업대·복귀가 반복되는 전체 흐름을 확인하는 데 쓴다. 기존 여러 단계 양보 KEV 실험의 실패를 새 성능 근거 없이 재개하는 제안은 아니다.

연속 물류라는 목표에는 고정 주문 12건뿐 아니라, 예를 들어 정해진 10분 동안 같은 접수표로 공급하고 **그 시간 안에 완료한 주문·물품 수와 남은 주문**, 공급 종료 후 해소 시간을 따로 기록하는 시험이 잘 맞는다. 10분은 후속 시험 길이의 예시이며 충분성을 입증한 기준은 아니다. 새로운 목표가 계속 주어지는 물류를 다루는 [Lifelong MAPF 연구](https://arxiv.org/abs/2005.07371)와 문제 설정은 연결되지만, 그 논문이 우리 시험 건수나 10분을 정당화하는 것은 아니다.

## 사용자 관제와의 분리

사용자는 기존 화면 5173·백엔드 8000에서 다른 기능을 시험한다. 비교 도구는 이 관제에 조회만 하며 주문·모드·로봇을 변경하지 않는다. 사용자의 화면·주문·모드 변화나 관제 재시작은 관측 정보로만 기록하고 별도 시험 실패로 취급하지 않는다.

시험용으로 `backend`·`tests`·`routes`·`maps`를 복사한다. 복사본에서 서버를 시작하고 각 모드마다 빈 주문·별도 가상 로봇·예약·로그를 만든다. 원본 코드나 지도가 이후 수정돼도 이미 복사한 시험 내용은 변하지 않는다. 복사본 해시는 실행 전후 확인한다.

시험 백엔드는 localhost 8035, 전용 KEV는 localhost 8012를 사용한다. 이미 켜진 사용자 관제와 8011 KEV는 건드리지 않는다. 시험용 KEV는 기존 캐시의 CUDA `jaredpalmer/kev-0.8b@v1.0`을 사용하며 오프라인 모드로 시작한다. 시험이 끝나거나 실패하면 도구가 시작한 서버만 종료한다. ROS·MQTT 시작 함수나 실기체 명령을 실행하지 않는다.

**같은 컴퓨터의 CPU·GPU·메모리는 공유한다.** 이번 실행은 다른 기능 시험과 병행하는 초기 비교이며 시간을 최종 성능 수치로 확정하지 않는다. 최종 속도 비교에는 다른 부하가 적은 조건의 반복 확인이 필요하다.

## 결과를 읽는 기준

후속 [실험 방법 검토](order-traffic-method-audit-20261024.md)에서 같은 입력·초기 상태·지도·설정과 순서 균형을 재확인했다. 초기 두 모드 전체 비교로는 적절하지만, 실제 접수 시각 차이·조회 기반 시간·공유 자원 부하·서로 다른 WAITING/내부 대기 정책·반복 부족을 함께 해석해야 한다. 12건은 새 케이스 동작 확인에 유지하고, 확정적인 성능 결론에는 시간 기록 보완과 반복·긴 운행을 별도로 준비한다. 저장된 결과나 실행 코드는 이번 검토로 바꾸지 않았다.

1. 주문·복귀 실패, 시간 한도 초과, 관측 중복 점유가 없는지 먼저 본다.
2. 평균·최장 주문 시간은 접수 응답부터 작업대 작업 완료까지다. 최종 홈 복귀는 따로 기록한다.
3. 같은 주문표에서 보통 접수와 폭증의 최대 대기 주문·마지막 접수 이후 작업 완료 시간·전체 주문 완료 여부를 비교한다.
4. 모델 요청·응답·오류, 실제 검사한 전략과 건너뛴 전략, 추가 교통조정 적용 횟수를 함께 확인한다. AI 모드에서도 전략이 하나면 모델 요청 0회일 수 있다.
5. 현재처럼 코드가 준비 전략을 모두 검사했다면 시간 차이만으로 KEV의 전략 순서가 유용했다고 결론내리지 않는다. 이전 [응답 대기 대조](order-traffic-ranking-ablation-20261023.md)에서 모델 없이도 빠른 흐름이 재현된 사실을 함께 고려한다.

## 실행 도구와 상태

[order_traffic_ordinary_burst_comparison.py](../../tests/order_traffic_ordinary_burst_comparison.py)가 주문표·코드 사본·전용 모델의 수명을 관리한다. [기존 두 모드 비교 도구](../../tests/order_traffic_native_mode_comparison.py)에 외부 주문표·조건 순서·모델 주소·사용자 화면 변화 관측 옵션을 추가했다. 일반 관제 서비스·화면 코드는 바꾸지 않았다.

실행 원문: `logs/order-traffic-ordinary-burst/20261024-two-seeds-once/`.

- `batch.json`·`summary.md`: 전체 결과, 고정 주문표와 실행 순서.
- `frozen/`·`frozen-source-sha256.json`: 코드·지도 등 223개 파일의 사본과 해시.
- 각 조건 폴더: `/api/orders`·`/api/robots` 관측 원문, 모드·초기 상태·최종 상태·모델 요청/응답·교통조정 결정 기록.
- `analyze_raw.py`·`independent-verification.json`: 완료·평균 시간·점유·호출 수·원문 보존의 별도 재집계.
- `review_dispatch.py`·`dispatch-review.json`: 저장 자료에서 배차·작업대 차이와 전략 검사를 확인한 결과.

## 결과

### KEV의 기여를 읽을 때

보통 접수 두 주문표에서는 우리 AI가 평균 약 0.3초 느렸다. 폭증42도 AI가 약 1.01초 느렸고, 폭증137에서는 AI가 평균 약 3.72초 빠르고 최종 홈 복귀도 약 11.08초 빨랐다. **일관된 속도 개선은 확인되지 않았다.**

AI가 적용한 이동 결정은 160회이며 모두 코드의 최소 예상 완료 시간 선택과 일치했다. 실제 검사 묶음은 190회였고, 모든 묶음에서 준비한 전략을 전부 시도했다. 시간·생성 한도로 전략을 건너뛴 경우는 없었다. 검사는 VALID 207회·NO_FEASIBLE_RESERVATION 52회·ROUTE_REJECTED 37회로 집계됐다. 이 숫자는 서로 다른 완성 계획 수가 아니라 반복 검사 기록의 횟수다. 이번 범위에서 KEV가 탐색 순서로 검사량을 줄였다는 증거는 없다.

폭증137의 AI는 두 이동 요청에서 기다리며 재검사했고, 이 조건의 검사 묶음만 70회였다. 다른 세 조건은 각각 40회였다. 최종적으로 모든 요청을 처리했다. 재검사가 많았다는 사실만으로 AI가 더 우수하거나 열등하다고 단정하지 않는다.

### 빨랐던 폭증137에서 달라진 흐름

같은 주문의 배차 로봇이 처음 달라진 것은 7번이다. 기존은 약 63.09초까지 R3 배차가 관측됐고, AI는 약 55.12초까지 R1 배차가 관측됐다. 이는 약 0.2초 관측 주기의 상한이며 정확한 사건 시각은 직전 관측과의 구간 안에 있다. 이 시점이 전체 경로의 최초 차이라는 뜻은 아니다.

작업대 선택이 처음 달라진 것은 8번이다. 기존은 N3, AI는 N4를 사용했다. 배차와 작업대 선택 자체는 두 모드에서 기존 코드가 맡는다. 따라서 마지막 폭증의 빠른 결과를 **KEV가 배차 로봇·작업대를 직접 선택했기 때문**이라고 설명하면 안 된다. 교통조정·응답 대기·예약·배차 및 작업대 가용 시점이 함께 작용한 전체 흐름 결과다. 이번에는 지연 효과를 분리한 대조를 추가하지 않았다.

나머지 세 비교에서는 주문별 배차 로봇과 작업대 선택이 두 방식에서 같았다. 보통 접수는 모두 N3, 폭증42는 두 방식 모두 주문에 따라 N3·N4를 사용했다.

## 검증과 현재 해석

- 관련 자동 검사 307개 통과·기존 경고 4개. 실제 운행 8회·주문 96건·모델 요청 85회와 별개다.
- 각 쌍의 같은 주문표·초기 위치·지도·설정·접수 지연 0.5초 이내·실제 저장 주문 모드·추가 교통조정 분기·모델 호출 카운터·복귀 완료를 확인했다.
- 원문만 읽는 별도 재집계로 평균 시간·완료·5,103회 점유 표본·모델 85회·고정 사본 해시·원문 보존을 다시 확인했다.
- 시험용 8035 백엔드와 8012 KEV는 종료했다. 사용자 관제 5173/8000과 사용자 KEV 8011은 계속 실행 중인 것을 확인했다. 사용자 관제가 시험 중 재시작되거나 상태가 바뀌어도 사전에 정한 분리 조건에 따라 관측 정보로만 남겼다.
- 일반 관제 서비스·화면·실기체 코드는 이번 작업으로 바꾸지 않았다. 시험용 도구만 확장했다.

이번에 확인한 것은 **단일/두 픽업대 주문을 섞고 중간에 주문이 몰려도 두 방식 모두 이 시험을 끝까지 처리했다**는 것이다. KEV가 있어야만 주문이 해결되거나 처리량이 지속적으로 높아진다는 근거는 얻지 못했다. 동시에 더 큰 탐색 공간·다른 장애 상황에서도 KEV가 쓸모없다는 결론은 아니다.

현재 목표에 맞는 후속은, 기능 안정성을 더 보려면 한 픽업대 집중·긴 연속 운행을 추가하고, 최종 속도를 비교하려면 다른 부하가 적을 때 동일 조건을 반복하는 것이다. **주문 수만 계속 늘려 AI 효과가 나올 때까지 시험하거나 AI에만 더 많은 이동 권한·유리한 한도를 주지 않는다.** AI 판단 기여를 검토하는 별도 확장은 다른 과제로 설계한다.
