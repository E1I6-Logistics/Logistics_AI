# KEV가 더 오래 걸리는 복귀 경로를 고른 이유: 진단 결과

공유 범위: 이 문서의 과거 진단·수동 시험 도구와 `logs/` 원문은 기능 공유에서 제외하고 로컬에 보관한다. 아래의 관련 재현 명령은 해당 보관 자료가 있을 때의 실행 예시다.

2026-10-20. [무작위 주문 20건 시험](random-order-run-20261020.md)에서 발견한 선택 1건을 분석했다.

**이번 재검사에서는 API·클라이언트의 답 전달은 정상이었고, KEV 선택이 입력 표현과 표시 순서에 민감한 현상을 확인했다.**
다만 모델 내부에서 어떤 계산을 했는지까지 확정한 결과는 아니다. 짧은 문장으로 바꾸는 것만으로 문제를 해결했다고 판단하지 않는다.
이번에는 운영 지시문·선택 방식을 바꾸거나, KEV 응답을 코드 최솟값으로 바꿔 실행하지 않았다.

## 어떤 선택이 문제였나

`STREAM-7c889e-008`의 R3 복귀. 출발 N3, 목적지 N2.

| 후보 | 거리 | 예약 대기 예상 | 완료 예상 |
| --- | --- | --- | --- |
| 기존 길 3→11→7→9→2 | 2.046m | 4.532초 | 14.763초 |
| 우회 3→11→12→8→7→9→2 | 2.664m | 거의 0초 | 13.318초 |

목표는 예약 대기를 포함한 완료 예상 최소다. 따라서 이 비교에서는 우회가 목표에 맞지만 KEV는 기존 길을 선택했다.
실제 복귀는 다음 주문으로 전환됐으므로 이 선택 때문에 실제로 1.44초 늦어졌다고 해석하지 않는다.

## 재현할 때의 중요한 한계

후보 경로와 수치는 원본 기록에 남아 있다. 그러나 당시 전체 KEV 요청 원문은 저장하지 않았다.
약 0.5초 간격 관측 중 `SELECTING`으로 기록된 76.69초 시점으로 state를 재구성했다.

- 그 시점의 로봇 상태·점유 통로·목표·남은 경로를 사용했다.
- 예약 개수 14는 관측된 활성 경로에서 추정했다. 실제 예약표 원문은 없다.
- 보호 자원 목록은 비어 있다고 가정했다.
- 지시문은 해당 운영 호출부의 문자열을 읽었다.

따라서 **원문 바이트 단위 재전송은 아니다.** 재구성한 입력에서 같은 잘못된 선택이 반복되었다는 근거다.
새 시험에서 보낸 모든 요청과 응답은 JSON에 저장했다.

## 시험 결과

실제 KEV 서버 `jaredpalmer/kev-0.8b@v1.0`, CUDA·torch·bfloat16을 사용했다.
총 200회는 **KEV 선택 질문을 보낸 횟수**다. 주문 200건이나 주행 시험 200회를 뜻하지 않는다. 로봇 명령을 보내지 않았다.

### 1. 문제 상황의 표현을 바꾼 결과

각 항목은 원래 후보 순서 2회 + 반대 순서 2회다. 기준 일치는 제공 후보의 완료 예상 최솟값과 일치했다는 뜻이다.

| 바꾼 부분 | 기준 일치 |
| --- | --- |
| 재구성한 기존 입력 그대로 | 0/4 |
| 후보 이름만 중립 이름으로 변경 | 0/4 |
| 거리 정보만 제거 | 0/4 |
| 경로 목록만 제거 | 0/4 |
| 행동 이름만 제거 | 0/4 |
| 로봇 목록을 state에서 제거 | 4/4 |
| 지시문에서 ‘동률이면 거리 최소’ 문장만 제거 | 4/4 |
| 지시문을 짧은 ‘완료 예상 최소만 선택’으로 변경 | 4/4 |
| 목표를 말하는 첫 문장만 사용 | 2/4 |

‘동률이면 거리 최소’가 뒤에 있으면 모델이 조건을 무시하고 거리를 우선할 가능성은 있다.
하지만 로봇 목록 삭제도 결과를 바꾸고, 거리 정보만 지워서는 개선되지 않았다.
문장 의미·길이·위치·상황 정보가 함께 영향을 줄 수 있어 **어느 단일 규칙 때문이라고 확정하지 않는다.**
‘거리만 선호해서 틀렸다’, ‘로봇 위치를 몰라서 틀렸다’라고 단정할 수 없다.

### 2. 다른 저장 사례에도 적용했나

개선처럼 보인 표현을 무작위 주문 시험의 KEV 선택 14개에 적용했다.
각 비교의 후보·수치는 저장된 것이고, state는 새로 정한 간단한 표현이다. 원래 서버 시험의 13/14와 직접 성능 비교하지 않는다.
각 사례를 원래/반대 후보 순서로 한 번씩 질문해 총 28회다. 수치 차이가 1e-6초 이하인 후보는 같은 최솟값으로 취급했다.

| 표현 | 기준 일치 |
| --- | --- |
| 간단한 state + 전체 후보 정보 + 짧은 목표 지시문 | 25/28 |
| 중립 후보 이름 + 완료 예상만 표시 | 25/28 |

문제였던 8번 복귀는 맞게 바뀌었지만, 5번 복귀·10번 픽업·19번 픽업 등 다른 비교에서 오류가 나왔다.
두 표현이 틀린 사례가 완전히 같지는 않다. 특히 3개 후보가 있는 10번·19번은 표시 순서를 바꾸면 답이 달라졌다.
이 때문에 문제 1건에서 4/4가 나왔다고 운영 표현을 즉시 교체하지 않았다.

### 3. 로봇 정보 없이 숫자만 비교

`6.78`, `18.00`, `15.93`을 세 선택지에 순열 6가지로 배치하고, 표시 순서도 원래/반대로 바꿨다.
이 대조 시험은 가상 숫자 질문이며 로봇 경로·예약을 바꾼 것이 아니다.

- ‘가장 작은 수 선택’: **9/12** 기준 일치.
- 로봇 상태·거리·대기 정보가 없어도 일부 순서에서 최솟값을 놓쳤다.
- 앞선 두 숫자 최소 비교 대조는 8/8이었지만, 큰 수를 고르는 대조는 2/4였다.

그러므로 현재 모델·요청 형식에서 숫자 비교가 항상 보장된다고 가정할 수 없다.
반대로 모델이 모든 숫자 비교를 못한다는 결론도 아니다. 여기서 시험한 숫자와 표현에 한정된 관측이다.

## 코드·통신 오류 여부

200개 기록에서 API 응답 choice와 클라이언트가 반환한 choice가 다른 경우는 0건이었다.
선택은 모두 응답 확률의 최댓값에 해당했고, 후보 목록에 없는 답도 없었다. HTTP·파싱 오류도 없었다.
입력 토큰은 35~548개였고 실행 설정의 상태 자르기는 꺼져 있었다. 길이 제한 때문에 이 진단 입력이 잘렸다는 근거는 없다.

정상 HTTP 응답과 올바른 선택은 다른 문제다. 이번에는 요청·답 전달은 정상이고 선택 내용이 목표와 어긋났다.

## 원문 기록 보완

앞으로 정확한 재전송이 가능하도록 `order_traffic_service._select_choice_recorded()`를 추가했다.

- 선택 시작 전: 요청 ID, 주문·로봇·단계·목표, state·후보·지시문 기록.
- 성공 후: 실제 전송 요청과 모델 응답, 선택 결과, 걸린 시간 기록.
- 실패 후: 같은 요청 ID로 오류 기록. 기록 저장 실패가 선택 결과를 바꾸거나 주문을 실패시키지 않게 처리.
- 응답 기록은 실행 승인이 아니다. 실행은 기존 최신 상태·예약 검사를 그대로 따른다.
- 파일: `logs/order-traffic/selection-inferences.jsonl`.
- 진단 당시에는 코드와 검사만 반영하고 백엔드를 재시작하지 않았다. **후속 작업에서 2026-10-20 10:18(KST) 백엔드를 재시작해 원문 기록을 반영했다.** 진단 당시 재구성한 입력과 재시작 후 수집한 실제 입력은 구분한다.

전체 자동 검사 205개 통과. 이 숫자는 위 200회 모델 질문과 별개다.
원문 보존, 기록 실패 시 선택 유지, 통신 실패 전달, 기존 취소·예약·주문 흐름을 검사했다.

후속 [실제 관제 원문 기록 확인](selection-capture-live-20261020.md): 일반 주문 6건에서 KEV 호출 5회의 실제 전송 요청·응답을 확보했다. 이번 입력에서는 예상 최소 후보와 5/5회 일치했지만, 기존 오류 해결이나 운영 성능 개선을 뜻하지 않는다.

## 지금 내릴 판단과 다음 작업

1. 후보 생성·예약 검사는 유지한다. 운영 지시문과 KEV 선택은 이번 진단으로 교체하지 않는다.
2. **완료 예상 최솟값 준수를 반드시 보장해야 한다면 코드 비교가 적합하다.** KEV 선택 결과를 몰래 덮어써 성공률로 세지 말고 별도 정책으로 비교해야 한다.
3. KEV는 전략·우선 대상 제안으로 확장할 수 있지만, 그 판단의 가치도 새로운 시험으로 확인해야 한다. 숫자 최소 선택 문제를 피했다고 전략 판단 성능이 증명되지는 않는다.
4. 다음 서버 반영 때 원문 기록을 켠 뒤, 다른 seed와 3개 이상 후보의 새 상황을 저장해 비교한다. 지금 반복한 사례로만 표현을 계속 맞추지 않는다.
5. 파인튜닝·큰 모델 교체·입력 표현 개선 중 무엇이 유효한지는 별도 평가가 필요하다. 현재 결과만으로 하나가 필수라고 단정하지 않는다.
