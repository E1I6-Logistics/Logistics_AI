# 작업대 복귀 배치와 KEV 입력 표현 진단

2026-10-20. R1이 다른 로봇의 대기 노드 N1에서 출발하던 시험을 **작업대 N3에서 자기 대기 위치 N0로 복귀**하는 시험으로 바꿨다. 이전 N1 배치 로그·측정 결과는 수정하지 않고 보존했다.

## 현재 화면의 다중 양보 배치

| 로봇 | 시작 | 이번 역할 | 양보 위치 | 마지막 위치 |
| --- | --- | --- | --- | --- |
| R1 | N3 작업대 | N0로 복귀 | 해당 없음 | N0 |
| R2 | N11 | N3 출구를 막고 정차 | N6 | N11 |
| R3 | N10 | N0 입구를 막고 정차 | N8 | N10 |

R1의 공급 경로는 **N3 → N11 → N7 → N9 → N10 → N0**다. N3에서는 N11로만 나갈 수 있고 N0에는 N10에서만 들어갈 수 있다. 따라서 R2·R3 모두 점유를 비워야 한다. 어느 한 노드를 차단한 채 N3→N0 경로를 만들 수 없는지도 검사했다.

R1만 N3로 옮기고 R2를 N9에 그대로 두면, N9를 피하는 다른 경로가 있으므로 ‘두 로봇이 모두 비켜야 한다’는 구조적 조건이 사라진다. 그 조건을 유지하려고 R2를 N11로 함께 옮겼다. R3는 N10 그대로다.

N6·N8은 **이번 가상 시험에서 양보 정차를 허용한 노드**다. 특히 N6은 C/D 픽업대이므로 일반 주문 중 작업 중인 픽업대로 무조건 양보시키는 운영 규칙이 아니다. 시험은 작업·초기 예약이 없는 IDLE 로봇을 대상으로 한다. 실제 주문의 RETURNING 상태를 재현하는 시험도 아니며, 업무상 가능한 복귀 동선을 쓰는 교통조정 시험이다.

다음 네 항목을 같은 배치로 바꿨다. 일반 주문 경로·로봇 홈 위치·기존 지도는 바꾸지 않았다.

- 고정 5단계: `fixed_two_robot_yield`.
- 코드 BFS 자동 탐색: `search_two_robot_yield`.
- 코드 DFS 대조: `dfs_two_robot_yield`.
- KEV 제안 DFS: `guided_two_robot_yield`.

고정 계획은 **R2 N11→N6 양보 → R3 N10→N8 양보 → R1 N3→N0 통과 → R2 N6→N11 복귀 → R3 N8→N10 복귀**다. 자동 탐색에서는 양보·복귀 순서가 달라질 수 있다.

- 실제 실행 순서: **R3 N10→N8 → R2 N11→N6 → R1 N3→N11→N7→N9→N10→N0 → R3 N8→N10 → R2 N6→N11**.

## 이전 제안 8회의 대조

원본은 이전 N1 배치의 실행 상세 (`logs/traffic-joint-actions/run-fe5556d83fea49adac74f76bbf0673ce.json`, 로컬 보관)다. 아래 진단을 새 N3 배치의 관측처럼 바꿔 쓰지 않는다.

| 제안 | 당시 선택 | 해당 경로에서 남은 다른 로봇의 점유 | 검사 |
| --- | --- | --- | --- |
| 1 | R1 진행 | N9=R2, N10=R3 | 실패 |
| 2 | R3 N10→N8 양보 | 없음 | 통과 |
| 3 | R1 진행 | N9=R2 | 실패 |
| 4 | R3 N8→N10 복귀 | 없음 | 통과 |
| 5 | R1 진행 | N9=R2, N10=R3 | 실패 |
| 6 | R1 진행 | N10=R3 | 실패 |
| 7 | R1 진행 | 없음 | 통과 |
| 8 | R2 복귀 | 없음 | 통과 |

R1의 진행 제안 네 번이 남은 점유 때문에 실패했다. 매번 정확히 같은 상태를 재요청한 것은 아니다. 가상 상태가 바뀌거나 탐색기가 이전 분기로 돌아간 뒤의 제안들이었다.

4번 R3 복귀는 그 이동 자체는 가능하지만 R1이 지나야 할 N10을 다시 점유한다. 따라서 **이번 한 단계의 예약 가능성과 전체 해결 순서의 품질은 다르다.** 현재 계약에서는 각 로봇이 한 번만 양보할 수 있어, 일찍 복귀한 분기는 나중에 되돌아가 다른 순서를 검토해야 할 수 있다.

## 입력 표현·후보 표시 순서 대조

이 절의 후속 시험에서는 후보 이름과 표시 순서를 독립적으로 바꿨다.
[이름·표시 순서 분리 시험](candidate-id-order-diagnosis-20261020.md)에서 순서 영향과 전체 계획 탐색 결과를 함께 확인할 수 있다. 아래 표는 직전 시험의 결과로 유지한다.

모델·지시문·후보 ID와 경로는 유지하고 입력 상태 표현만 다음처럼 바꿨다. 후보를 미리 제외하거나 정답 후보 ID를 주지 않았다.

| 표현 | 바꾼 내용 |
| --- | --- |
| `original` | 기존 상태 그대로 |
| `occupancy_facts` | 기존 상태에 ‘후보 경로의 어느 노드에 누가 있는지’ 추가 |
| `compact` | 현재 가상 위치·목표·점유 관계·앞선 검사와 한도를 짧은 설명으로 표현 |

점유 관계는 각 요청의 **현재 가상 위치**를 기준으로 계산했다. 과거 검사 당시의 위치를 현재 상태에 덮어쓰지 않는다. 점유 사실은 전체 예약 검사 결과가 아니므로 후보는 그대로 남기고 실행 검사는 유지한다.

저장된 요청 8개 × 표현 3개 × 표시 순서 2개 × 반복 2회 = **실제 모델 요청 96회**다. 로봇은 움직이지 않았다. 평가용 예약 검사 결과는 모델 입력에 전달하지 않고 별도로 비교했다.

| 입력 표현 | 기존 후보 순서: 다음 이동 검사 통과 | 반대 후보 순서: 다음 이동 검사 통과 |
| --- | ---: | ---: |
| 원본 | 8/16 | 12/16 |
| 점유 관계 추가 | 8/16 | 10/16 |
| 짧은 설명 | 8/16 | 12/16 |

각 16회는 같은 요청 8개를 두 번 반복한 숫자다. 새 상황 16개가 아니다. 각 표현·순서에서 두 번의 선택은 16/16쌍 동일했다.

같은 표현에서 후보 표시 순서만 바꾸면 선택은 원본 6/16쌍, 점유 관계 추가 6/16쌍, 짧은 설명 8/16쌍에서 달라졌다. **표시 순서가 선택에 영향을 주는 사례를 확인했다.** 후보 ID 자체의 영향까지 분리한 시험은 아니다.

이 표는 다음 한 단계의 예약 검사 통과율이다. 4번처럼 이동은 가능해도 전체 순서에는 좋지 않은 복귀가 있으므로, 전체 해결률이나 최적 순서를 맞힌 비율로 해석하지 않는다. 점유 설명을 추가한 것만으로 개선됐다는 근거는 얻지 못했다.

## 새 N3 복귀 배치의 전체 탐색 비교

새 배치의 기본 상황, 요청 순서 반대, R3 양보 경로 미제공의 세 입력을 썼다. 코드 DFS와 세 입력 표현의 KEV DFS를 같은 동작·검사·128회·8단계·10초 한도로 비교했다. KEV 요청 한도도 각 8회·개별 2초로 동일하다.

| 표현 | 기본·역순 각각의 검사 수 | 기본·역순 각각의 모델 제안 | 계획 시간 |
| --- | ---: | ---: | --- |
| 코드 DFS | 13회 | 0회 | 각각 약 0.006초 |
| KEV 원본 | 13회 | 8회 | 약 0.840 / 0.853초 |
| KEV 점유 관계 추가 | 13회 | 8회 | 약 0.860 / 0.880초 |
| KEV 짧은 설명 | 13회 | 8회 | 각각 약 0.763초 |

R3 양보 경로 미제공 상황은 네 방식 모두 5회 검사 후 이동 없이 미해결이었다. 모델 방식은 각 2회 요청했다. 전체 탐색 실행은 12회, 그중 모델 방식 9회이며 실제 모델 요청은 54회다. 앞의 요청 재현 96회와 합쳐 이번 격리 진단은 모델 요청 150회다.

**새 배치에서도 입력 표현 변경으로 검사 수가 줄지 않았다.** 짧은 설명의 시간이 약간 낮았지만 한 번씩의 관측이고, 모델 요청이 없는 코드보다 오래 걸렸다. 이를 성능 개선이나 우수성으로 확정하지 않는다. 입력 기본값은 `original`로 유지한다.

자료: 입력·실제 요청·응답·평가·새 배치 결과 (`logs/traffic-recovery/input-diagnosis-20261020-185602/report.json`, 로컬 보관).

## 코드와 적용 범위

- `traffic_recovery_input.py`: 후보를 유지한 채 현재 가상 점유를 설명하는 순수 변환 함수.
- `traffic_recovery_guidance.py`: `input_style` 선택 설정. 기본값은 기존 `original`.
- `traffic_recovery_input_diagnosis.py`: 저장된 요청 재현과 새 배치 비교. `--run` 없이는 모델에 요청하지 않는다.
- `tests/traffic_scenarios.json`: 네 항목의 새 시작점·경로·양보 위치.

전체 자동 검사 237개가 통과했다. 새 배치의 양쪽 필수 통과점, 노드·엣지 검사, 중단·한도, 입력이 현재 가상 위치를 사용하는지, 후보·원본을 수정하지 않는지를 포함한다. 일반 주문의 KEV 선택 방식은 유지했다.

입력에 점유 정보를 더 넣으면 해결된다고 결론낼 수 없다. 다음 검토는 후보 ID·표시 순서 영향을 더 분리하고, 다른 막힘 배치에서도 같은 문제가 생기는지 보는 것이다. 현재 데이터만으로 파인튜닝 필요성이나 모델 일반 성능을 확정하지 않는다.
