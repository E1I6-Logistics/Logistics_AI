# 같은 주문표로 KEV 선택과 계산값 선택 비교

2026-10-20 10:26~10:33(KST). **두 방식 모두 주문을 끝냈지만, KEV가 더 좋다고 결론 내릴 근거는 아직 부족하다.** 첫 주문표는 KEV 쪽이 빨랐고, 두 번째는 계산 방식이 조금 빨랐다. KEV는 14번 중 2번 제공된 예상 시간이 더 긴 후보를 골랐다.

## 무엇을 비교했나

```text
같은 주문표 + 같은 등록 일정 + 같은 로봇 시작 상태
  → 같은 A* 경로 생성
  → 같은 우회 후보 생성·예약 검사
  → 여기만 바꿈:
      KEV: 상황·후보·예상 시간을 보고 하나 선택
      계산: 예상 완료 시간이 가장 짧은 후보 선택
  → 같은 최신 예약 재검사·이동·주문 처리
```

계산 방식의 이름은 `MIN_EXPECTED_TIME`이다. KEV가 실패하면 몰래 대신 선택하는 기능이 아니라, 비교를 위해 별도로 설정한 방식이다. 동률이면 이동 거리가 짧은 후보, 다시 동률이면 후보 ID 순서를 사용한다. 기본 설정은 계속 KEV다.

- 기존 관제의 일반 주문 API와 가상 로봇 3대를 사용했다. 별도 움직임 구현이나 실기체 시험이 아니다.
- 모든 시험에서 시뮬·AI + A* 경로 생성 + 일반 주문 교통조정, 속도 0.2m/s를 유지했다.
- 주문표 두 종류: seed 42는 8건·22개, seed 17은 8건·34개. 각 주문의 물품 합계는 1~5개다.
- 각 주문표를 두 방식으로 한 번씩, 총 4번 실행했다. 실행 순서는 42/KEV → 42/계산 → 17/계산 → 17/KEV다.
- 처음 3건, 이후 5초마다 1건씩 등록해 25초까지 8건을 공급했다. 기존 자동 공급의 대기 상한 3건을 적용하면 실행마다 공급 시각이 달라질 수 있어, 이 비교는 주문 수 8건과 등록 일정을 고정했다. 기존 자동 공급 설정 자체는 변경하지 않았다.
- 작업이 없을 때만 백엔드를 재시작했다. 기존 이력을 보존하고, 각 시험의 시작 위치·자세·배터리를 동일하게 맞췄다. 원래 상태와 시험 시작 상태는 각각 백업했다.
- 두 방식의 주문표 해시·지도 해시·시작 상태 일치와, 실제 등록 지연이 목표 시각에서 0.5초 이내인 것을 확인했다. 최대 지연은 약 0.19초였다.

‘이번 묶음 처리율’은 물품 수 ÷ 전체 작업 완료 시간으로 계산했다. 공급 시작과 작업 마무리가 포함된 작은 시험의 수치이며, 장시간 연속 운용의 정상 상태 처리량으로 해석하지 않는다. 가상 OMX 작업도 실제 물품별 작업 시간을 검증한 것이 아니다.

**후속 반복:** 같은 seed 42를 한 쌍 더 실행했을 때 KEV 75.75초·계산 75.71초로, 최초 약 8초 차이가 유지되지 않았다. 실제 입력 14개를 각 3번 재질문했을 때는 기존 선택과 오답이 그대로 재현됐다. [후속 진단·역할 검토](order-traffic-followup-20261020.md).

총 32건·112개를 모두 처리했다. 주문 실패·취소·복귀 오류는 없었고, 노드·물리 엣지 점유를 1,971회 관측하는 동안 중복 점유는 없었다. 모든 순간이나 실기체 안전을 증명하는 결과는 아니다.

## KEV가 빠른 후보를 골랐나

| 주문표 | 방식 | 여러 후보 중 선택 | 예상 최소 후보와 일치 | 실제 KEV 호출 |
| --- | --- | ---: | ---: | ---: |
| 42 | KEV | 7회 | 6/7 | 7회 |
| 42 | 계산 | 4회 | 4/4 | 0회 |
| 17 | 계산 | 7회 | 7/7 | 0회 |
| 17 | KEV | 7회 | 6/7 | 7회 |

KEV 요청·응답 14쌍을 대조했다. 기록 예정 요청과 실제 전송 요청이 일치했고, 모두 등록된 후보 중 하나를 반환했다. 통신 오류는 없었다. 후보가 하나인 이동은 모델을 호출하지 않았다.

계산 방식의 11/11은 최소값을 직접 고른다는 구현 확인이다. 전체 시스템이 최적이라는 뜻은 아니다. 실행 중 점유·배차·예약이 달라지므로 이후 후보도 달라져, 두 방식의 다중 후보 선택 횟수가 같을 필요는 없다.

예상 최소 후보를 고르지 않은 두 사례:

| 주문표·주문 | 이동 단계 | KEV가 고른 경로 예상 | 더 빠른 후보 예상 | 차이 |
| --- | --- | ---: | ---: | ---: |
| 42의 7번 주문, R2 | 복귀 N1 | 기존 경로 11.91초 | 우회 11.32초 | 약 0.58초 |
| 17의 3번 주문, R3 | 복귀 N2 | 기존 경로 14.60초 | 우회 13.32초 | 약 1.28초 |

둘 다 출고 작업 완료 후 복귀 판단이다. 복귀 중 새 주문으로 전환될 수도 있으므로, 위 예상 차이를 그대로 실제 주문 지연으로 더하면 안 된다. 기록에는 당시 상태·후보·지시문과 서버 응답이 모두 있다.

## 이 결과를 어떻게 해석하나

1. **일반 주문에 두 선택 방식을 연결하고 비교하는 기능은 동작했다.** 기존 후보 생성과 예약 검사는 양쪽에서 같다.
2. **이번 시험만으로 KEV의 우수성은 확인하지 못했다.** 주문표별 결과가 다르고, 각 조건은 한 번씩만 실행했다. 실행 순서를 바꿨지만 반복 변동을 측정한 실험은 아니다.
3. **새 이동 요청 하나의 예상 도착 시간 최소와 전체 물류 처리량은 다르다.** 첫 주문표의 후반에는 담당 로봇도 달라졌다. 예를 들어 5번 주문은 KEV 실행에서 R2, 계산 실행에서 R3가 맡았다. 이 변화가 KEV의 유리한 교통 추론 덕분인지, 추론 지연·배차 주기·예약 시점의 영향인지는 분리하지 않았다.
4. **KEV의 숫자 최소 선택 오류는 여전히 남아 있다.** 입력·지시문을 교체하거나 응답을 코드의 답으로 덮어쓰지 않았다. 숫자 최소를 보장하는 역할은 계산 방식이 직접 수행할 수 있다.
5. 전략·우선 대상 제안으로 KEV의 역할을 넓히는 방식은 여전히 별도 설계·실험 대상이다. 이번 결과가 그 확장 방식의 성능을 증명하지는 않는다.

다음에는 같은 주문표를 여러 번 반복해 변동을 확인하고, 저장된 동일 입력에서의 선택 비교와 전체 주문 처리 비교를 구분한다. 전략 제안 실험을 진행할 때도 기존 방식과 분리하고, 같은 계획 생성 시도 한도로 비교한다.

## 코드와 다시 실행하는 방법

- 선택 설정·계산 방식: [order_traffic_service.py](../../backend/app/services/order_traffic_service.py).
- 설정 확인: `/api/mode`의 `order_traffic.selection_policy`.
- 관제 주문 상세: KEV·코드 선택·후보 하나 적용을 구분해 표시한다.
- 실행·재시작·관측: [order_traffic_comparison.py](../../tests/order_traffic_comparison.py). 기본 실행은 계획 출력이며 `--run`일 때만 반영한다. 재시작은 현재 백엔드가 쓰는 Python을 재사용한다.

```bash
PYTHONNOUSERSITE=1 ~/venv/robot/bin/python tests/order_traffic_comparison.py --run --count 8 --seeds 42 17 --timeout 300
```

선택 방식 분리 후 전체 자동 검사 208개, 이후 비교 보고서의 미완료·시간 구분 검사 2개를 별도로 통과했다. 기존 경고 4개가 있다. 프런트 타입 검사·빌드도 통과했다. 이 숫자는 실제 KEV 호출 14회와 별개다.
