# 여러 대 양보: KEV에 거리·시간 정보를 추가한 결과

2026-10-22. 별도 정지 상태 시뮬레이션의 변경·검증 기록이다.

## 무엇을 바꿨나

이전에는 KEV가 제공된 경로, 현재 점유와 길을 막는 관계를 보고 다음에 검사할 이동을 골랐다. 이번에는 **각 이동 거리와 예상 시간**도 코드에서 계산해 함께 전달한다. 코드 비교 방식도 같은 값을 사용한다.

```text
경로·상태·길막 관계
  ↓
지도 좌표에서 거리와 이동 시간 계산 ← 이번 추가
  ↓
코드 또는 KEV가 다음에 검사할 이동 선택
  ↓
기존 예약 검사 → 실패 이유 전달 또는 다음 이동 검토
  ↓
양보·통과·복귀까지 완성된 계획이 있을 때만 실행
```

KEV가 지도 전체를 직접 해석하거나 통행 허가를 내리는 구조로 바꾼 것은 아니다. 이번 범위는 관제의 ‘두 대 양보 · 코드만 / KEV만 / KEV 후 코드 보완’ 세 항목이다. 일반 주문·실기체·아루코 처리·경로 생성·예약 검사 구현은 그대로다.

## 계산값은 무엇을 뜻하나

지도 노드의 실제 좌표 사이 직선거리를 경로 순서대로 더한다. 화면 픽셀이나 노드 개수로 거리를 추정하지 않는다. 그 거리를 현재 가상 로봇과 같은 **0.2m/s**로 나눈다. 계산 기본값은 `traffic_metrics.DEFAULT_TRAFFIC_ESTIMATE_SPEED_MPS`, 실제 가상 주행 속도는 기존 `mock_data.SIMULATION_SPEED_MPS`다. 둘이 같은지 자동 검사한다. 이 설정은 실기체의 controller 속도를 바꾸지 않는다.

실제 첫 입력의 예:

| 다음에 검사할 이동 | 거리 | 그 이동만의 예상 시간 |
| --- | --- | --- |
| R2 N11→N6 양보 | 약 0.377m | 약 1.886초 |
| R3 N10→N8 양보 | 약 0.459m | 약 2.294초 |
| R1 N3→N11→N7→N9→N10→N0 | 약 2.277m | 약 11.386초 |

마지막 이동은 길목을 다른 로봇들이 막고 있으므로 당장 출발할 수 없다. **시간 값이 짧아도 실행 가능하다는 뜻이 아니다.** 관계 정보와 예약 검사로 구분한다.

입력은 `traffic-recovery-dependencies/0.2`이며 선택지 설명과 `dependency_facts.offered_moves`에 같은 `estimated_motion`을 넣는다. 아래는 실제 입력에서 발췌해 반올림한 값이다.

```json
{
  "estimated_motion": {
    "distance_m": 0.377,
    "travel_seconds": 1.886,
    "start_seconds": 0.0,
    "completion_seconds": 1.886,
    "mean_goal_completion_lower_bound_seconds": 13.272,
    "all_returns_completion_lower_bound_seconds": 15.158,
    "moving_request_count": 1
  }
}
```

- `start_seconds`는 앞서 검토한 가상 이동 순서를 실행했다고 가정한 누적 시각이다. 탐색 도중 로봇을 움직인 것이 아니다.
- `mean_goal_completion_lower_bound_seconds`는 **다른 로봇이 먼저 비켜주는 시간과 이후 차례 대기를 무시한 낙관적인 도착 시간 평균**이다. 완성 계획의 실제 도착 예정 시각이 아니다. 원래 이동 요청만 평균에 넣고, 지원 로봇의 복귀를 새 요청 완료로 세지 않는다. 이미 완료한 요청의 시각은 유지하며 알 수 없는 값은 `null`이다.
- `all_returns_completion_lower_bound_seconds`는 지원 로봇의 복귀까지 포함한 남은 이동 시간을 순서대로 더한 최소 예상값이다. 예약·회전 등으로 더 늦어질 수 있다.
- 속도·가정은 `motion_estimation`에 명시한다. 모델 응답 시간·회전·예약 정지·확인 지연은 포함하지 않는다.

[전체 설계의 시간 정의](../continuous-order-traffic-design.md#traffic-time-metrics)를 공통 기준으로 사용한다. 전체 연결표나 상세 예약 시간표를 KEV에 새로 제공한 것은 아니다.

## 코드 방식은 어떻게 고르나

현재 다른 로봇이 점유한 이동과 나중에 필요한 길목을 막고 끝나는 이동을 먼저 뒤로 둔다. 그 뒤 낙관적인 평균 도착 시간, 필요한 길 비우기, 성급한 원위치 복귀 방지, 복귀까지의 시간·이번 이동 시간과 안정적인 식별자 순서로 비교한다. 비용이 없던 기존 설정은 기존 규칙을 유지한다.

KEV에도 같은 관계·시간 정보를 준다. KEV는 다음 검사 동작을 고르고 코드는 예약 검사를 담당한다. **둘 다 한도 안에서 처음 찾은 완성 계획을 반환한다. 전체 평균 시간의 최적 계획을 찾는 알고리즘으로 바꾸지 않았다.**

## 실제 모델 비교

같은 지도·허용 경로·시작 상태에서 정보 제공 전후를 비교했다. 모델은 실행 중인 `jaredpalmer/kev-0.8b@v1.0`이다. 검사 128회·계획 8단계·전체 10초, 모델 제안 8회·개별 응답 2초를 적용했다. 일반 주문과 실제 로봇에는 명령을 보내지 않았다.

총 **24회 계획 시험, 실제 KEV 호출 108회, 점유 위반 0건**이다. ‘계획 시험 1회’ 안에서 KEV를 여러 번 부를 수 있다.

### 두 로봇이 비켜줘야 하는 상황: 방식별 3회

R1=N3→N0, R2=N11→N6 양보, R3=N10→N8 양보 후 원위치 복귀다.

| 방식 | 정보 전 성공 | 정보 후 성공 | 전→후 평균 계획 시간 | 전→후 KEV 호출, 시험당 |
| --- | --- | --- | --- | --- |
| 코드만 | 3/3 | 3/3 | 약 0.005→0.004초 | 0→0 |
| KEV만 | 0/3 | 0/3 | 약 0.956→1.481초 | 8→8 |
| KEV 후 코드 보완 | 3/3 | 3/3 | 약 0.935→1.471초 | 8→8 |

성공한 계획의 가상 시계 기준 평균 이동 완료 시간은 전후 모두 **16.60초**, 지원 로봇 복귀를 포함한 모든 단계 완료는 **21.80초**다. KEV 단독은 완성 계획을 찾지 못해 이동을 시작하지 않았다. 실패 결과의 실행 경과 0초를 빠른 완료로 해석하지 않는다.

**이 상황에서는 보완으로 문제가 해결되지 않았다.** 모델 판단 시간이 늘었고, 혼합 방식의 성공은 코드 보완을 포함한 결과다.

### 우회로도 있는 상황: 방식별 1회 탐색 확인

R1이 막힌 기존 경로 대신 N3→N11→N12→N8→N10→N0으로 갈 수 있다.

| 방식 | 성공, 전→후 | KEV 호출, 전→후 | 계획 시간, 전→후 | 가상 이동 완료, 전→후 |
| --- | --- | --- | --- | --- |
| 코드만 | 1/1→1/1 | 0→0 | 약 0.0008→0.0009초 | 11.0→11.0초 |
| KEV만 | 1/1→1/1 | 5→1 | 약 0.558→0.176초 | 11.0→11.0초 |
| KEV 후 코드 보완 | 1/1→1/1 | 5→1 | 약 0.568→0.183초 | 11.0→11.0초 |

최종 경로는 전후 동일하다. **더 빠른 경로를 찾은 결과가 아니라 같은 경로를 찾는 판단 과정이 짧아진 한 사례**다. 반복 성능을 입증하지 못하며 연속 주문 처리량 개선도 측정하지 않았다.

이번 전후 비교는 값 추가와 그 값에 맞춘 지시문·코드 순서 규칙을 함께 바꿨다. 따라서 입력 숫자만의 효과를 분리한 실험은 아니다. 같은 동작·검사·한도를 쓴 비교이지만 적은 상황·반복 수와 실행 순서에 따른 영향도 남아 있다.

## 이후 실패 기록 분석

[거리·시간 보완 뒤에도 놓친 선택](kev-mapf-motion-answer-analysis-20261022.md)에서 저장된 108개 답변을 새 모델 호출 없이 분석했다. KEV 단독 세 실행은 막힌 출발·조기 복귀·해결 가능한 순서 미루기를 같은 패턴으로 반복했다. 원인에 대한 추정과 확인된 선택 결과를 구분했다.

## 구현·검사·확인 방법

- `traffic_recovery_motion.py`: 제공된 경로와 가상 순서에서 거리·시간 계산. 미래 전체 순서를 미리 탐색하지 않는다.
- `traffic_recovery_dependencies.py`: 같은 값을 관계 정보·선택지에 추가하고 코드 규칙과 모델 지시문에 반영한다.
- `traffic_recovery_search.py`: 검토한 앞 순서를 전달하고 활성 여부를 기록한다.
- `traffic_joint_actions.py`: 설정이 참·거짓인지 검증한다.
- `traffic_joint_action_scenario.py`: 시험 설정을 전달한다.
- `tests/traffic_scenarios.json`: 비교 세 항목에 `recovery_motion_estimates=true`를 지정한다. 기본값은 꺼짐이다.
- `ScenarioControls.tsx`·`fmsApi.ts`: 결과에 거리·시간 활성 문구와 제안별 거리·이동 예상 시간을 표시한다.

관련 자동 검사 **68개 통과**, 프런트 타입 검사와 빌드 통과. 자동 검사는 모델의 우수성을 뜻하지 않는다. 좌표 거리, 이전 완료 시각 보존, 모르는 시각의 `null`, 양보 복귀 처리, 입력 동일성, 기존 실패 처리와 예약 검사가 유지되는지를 확인했다. 기존 MQTT 경고와 검사 도우미 클래스 관련 경고 2건은 남아 있다.

실행 근거는 `logs/traffic-recovery/motion-input-20261022/`의 `report.json`, `summary.json`, `input-example.json`이다. 같은 폴더의 `run.py`가 격리 비교 재현 도구다. 로그 폴더는 저장소 추적 대상이 아니므로 공유할 때 별도로 포함해야 한다.

관제에서는 시뮬·AI → ‘두 대 양보’ 세 항목을 선택해 실행한다. 진행 주문·복귀가 없어야 한다. 결과의 ‘거리·이동 시간 정보 포함’과 KEV 제안별 이동 예상 시간을 확인한다. 이번 Python 실행 코드 보완을 반영하려면 백엔드 재시작이 필요하다. 2026-10-22 백엔드만 재시작했고 시뮬·AI 설정, 주문 이력 0건과 로봇 위치 보존을 확인했다. `deployment/verified.json`에 기록했다. KEV·프런트·인프라는 재시작하지 않았다. 관제 시뮬에서도 새 입력 형식과 거리·시간 활성 여부를 확인했다. KEV 제안 8회 후 코드 보완 4회로 양보·통과·복귀 5단계를 완료했고 점유 위반은 없었다. 관제 실행 경과는 약 21.81초였다. 이는 위 격리 시험의 가상 시계 수치와 구분한다. 일반 주문 이력은 실행 전후 동일했다. `live-scenario.json`에 기록했다.

이번 변경만 되돌리는 백업은 `logs/change-snapshots/20261022-144138-before-recovery-motion-estimates/`다. 복원 도구는 이후 수정이 감지되면 덮어쓰지 않도록 한다. 실제 복원은 수행하지 않았다.
