# KEV가 다음 검사 동작을 제안하는 교통 복구 시험

**현재 배치·후속 진단:** 현재 시나리오는 작업대 N3에서 N0로 복귀하는 배치를 쓴다. 이전 요청 8회의 표현·순서 대조와 새 배치 비교는 [작업대 복귀 배치와 입력 진단](workstation-return-input-diagnosis-20261020.md)에 정리했다. 아래 N1 배치의 실행 기록은 보존했다.

2026-10-20. **KEV 제안 → 코드 예약 검사 → 실패 이유 피드백 → 다음 제안**을 구현했다.
기존 관제의 별도 정지 상태 시나리오에서 확인했다. 일반 주문의 기존 후보 선택 방식과 실제 로봇 주행은 바꾸지 않았다.

## 무엇이 바뀌었나

| 구분 | 기존 완성 후보 선택 | 새 전략 제안 시험 |
| --- | --- | --- |
| 모델 입력 후보 | 이미 실행 가능 검사를 통과한 전체 계획 | 다음에 검사할 로봇 하나의 이동 동작 |
| KEV가 고르는 것 | 실행할 완성 계획 하나 | 먼저 검토할 진행·양보·복귀·공급 우회 동작 |
| 예약 검사 시점 | 모델 선택 전, 실행 직전 | 모델이 동작을 제안한 뒤, 완성 계획 생성 시, 실행 직전 |
| 실패 시 | 후보 생성·검사에서 제외 | 해당 상태의 해당 제안을 제외하고 실패 기록을 다음 요청에 전달 |
| 실제 이동 | 최종 계획 검사 뒤 | 전체 통과·복귀 계획을 찾고 검사한 뒤 |

기존 KEV 선택 기능은 유지했다. 새 기능이 일반 주문에서 자동으로 여러 로봇을 멈추고 비켜주게 하는 상태는 아니다.

## 입력과 흐름

각 로봇이 움직일 수 있는 경로를 공급한다. 정답 실행 순서는 공급하지 않는다. N1의 R1은 N0으로 가야 하며, R2는 N9에서 N2로, R3는 N10에서 N8로 양보할 수 있다.

```text
진행·양보·복귀 경로 + 현재 위치 + 원래 목적지
  ↓
아직 검사하지 않은 다음 동작 목록 구성
  ↓
KEV: 이번에 검사할 동작 하나 선택
  ↓
코드: 복사한 상태에서 기존 TrafficManager 예약·진입 검사
  ├─ 실패 → 이유 기록, 같은 상태의 다른 동작 검토
  └─ 통과 → 가상 계획 상태 갱신, 다음 동작 검토
  ↓
모든 이동 요청 완료·양보 로봇 복귀까지 가능한 계획 발견
  ↓
최신 관제 상태와 전체 계획 재검사 → 한 단계씩 실제 가상 로봇 이동
```

모델이 받는 값은 **가상의 계획 상태**다. 탐색 도중에는 관제의 로봇을 움직이지 않는다. 원래 위치·현재 가상 위치·원래 목적지·작업 요청 유무·앞서 선택한 동작·최근 검사 결과 8건·남은 한도를 제공한다. 후보 설명에는 로봇 ID·동작 종류·경로·복귀 여부가 있다.

공식 KEV의 choice API를 프로젝트의 `KevSelector.select_choice()`로 호출한다. 질문 ID는 `traffic_recovery_move`다. 모델은 허용된 이동 ID를 선택하며 새 노드·로봇 명령을 자유 텍스트로 만들지 않는다. 후보는 지도·경로 형식 검사를 거치지만 **현재 점유·예약 가능성 검사 전**에 제시한다.

다음 동작이 하나뿐이면 KEV를 호출하지 않고 코드가 검사한다. 잘못된 ID·모델 오류·응답 한도·취소에는 출발하지 않는다. 오류를 코드의 성공으로 몰래 대체하지 않는다.

이번 실제 모델은 처음 막혀 있는 R1의 진행을 제안했고 검사가 거부했다. 이후에도 다른 가상 상태에서 R1 진행을 다시 제안해 탈락한 기록이 있다. 실패 피드백이 전달됐다는 것과 모델이 이를 잘 활용했다는 것은 별개다.

## 공정하게 비교하는 방법

| 방식 | 다음에 검사할 대상을 고르는 방법 |
| --- | --- |
| BFS | 단계 수가 적은 중간 상태부터, 코드의 동작 순서로 검사 |
| 코드 DFS | 한 가지 순서를 깊게 살피고 막히면 이전 상태로 돌아감. 다음 동작은 코드 순서 |
| KEV 제안 DFS | **같은 DFS 실행기**에서 다음 동작만 KEV가 선택 |

BFS와 DFS는 탐색 방식 자체가 다르다. 모델 제안 효과를 구분하려면 코드 DFS와 KEV 제안 DFS를 비교한다. 셋 모두 같은 허용 이동, 상태 중복 제거, 예약 검사, 128회 검사·8단계·10초 한도를 사용한다. 모델 응답 시간도 10초에 포함한다.

추가 모델 한도는 최대 8회, 개별 응답은 최대 2초이며 남은 전체 시간도 함께 적용한다. 전체 HTTP 호출을 기다리는 시간을 별도로 제한하므로 metadata 조회와 추론 요청을 합친 대기가 한도를 넘으면 결과를 버린다. 이미 시작한 HTTP나 서버 추론이 뒤늦게 끝날 수 있지만, 그 응답으로 계획이나 로봇 상태를 갱신하지 않는다.

현재 범위는 정지한 로봇·초기 활성 예약 없음·공급한 경로·로봇별 양보 최대 1회·순차 이동이다. 지도 전체에서 대기 위치를 찾거나, 이동 중인 로봇의 경로를 교체하거나, 반복 양보를 하는 기능은 포함하지 않는다.

**현재 작은 사례에서는 KEV의 이점을 확인하지 못했다.** 같은 DFS보다 검사 횟수를 줄이지 못했고 모델 요청으로 전체 계획 시간이 늘었다. BFS보다 적게 검사한 것은 DFS 자체의 효과와 섞이므로 AI 우위로 보고하지 않는다. 반복·다양한 배치에 대한 성능 결론은 아직 낼 수 없다.

## 기존 관제에서 확인한 결과

**시뮬·AI → 전략 탐색 비교 → KEV 제안 · 두 대가 비켜주고 R1 통과 → 테스트 실행**으로 확인한다.
코드 대조 항목은 **코드 순서 · 두 대가 비켜주고 R1 통과**다. 기존 **자동 찾기** 항목은 BFS이며, 이전 1초 한도의 기능 시험으로 유지했다. 성능 비교의 10초 한도와 구분한다.

화면의 **KEV가 제안한 동작 보기**를 펼치면 제안과 예약 검사 통과·탈락을 확인할 수 있다. 제안 기록은 탐색 과정이며, 표시된 모든 제안을 실제로 실행했다는 뜻이 아니다.

이번 관제 실행 결과:

- 실제 KEV 제안 8회, 예약 검사 13회, 계획 탐색 약 0.968초.
- 찾은 실행 순서: **R3 양보 → R2 양보 → R1 통과 → R2 복귀 → R3 복귀**.
- 복귀까지 약 19.42초에 완료. 순서가 다를 수 있으며 R2·R3 모두 비워야 한다는 조건은 같다.
- 위치 관측 166회에서 노드·물리 엣지 중복 점유 0회. 실기체의 물리 충돌 검증은 아니다.
- KEV 경로 생성 0회, 완성 조정안 선택 0회, **다음 검사 동작 제안 8회**. 서로 다른 호출 종류다.
- 완료된 주문 102건 보존, 시험 전후 주문 API 내용 일치.
- 최종 R1=N0, R2=N9, R3=N10. 홈 N0·N1·N2로 추가 복귀시키지 않는다.

## 코드·검증·남은 일

| 파일 | 역할 |
| --- | --- |
| `traffic_recovery_search.py` | BFS/DFS 공통 허용 동작·예약 검사·한도·되돌아가기 |
| `traffic_recovery_guidance.py` | 모델 입력·제안·호출 한도·취소·늦은 응답 무시 |
| `traffic_joint_actions.py` | 탐색 선택과 완성 계획 재검사 |
| `traffic_joint_action_scenario.py` | 기존 가상 관제 연결, 정지 요청, 호출 종류별 기록 |
| `traffic_recovery_comparison.py` | 공통 입력·한도로 세 방식 격리 비교 |

전체 자동 검사 233개와 프런트 타입 검사·빌드가 통과했다. 추가 검사는 검사 전 제안, 실패 피드백 전달, 잘못된 응답·모델 오류·호출 한도·시간 초과·취소 시 이동 차단, 늦은 응답 무시, 동일 한도 비교, 실제 모드 실행 거부를 포함한다. 이 숫자는 모델 정답률·실제 호출 횟수가 아니다.

먼저 모델이 점유 관계와 실패 이유를 활용하는지, 후보 ID·표시 순서에 따라 고르는지 추가로 분리해 볼 수 있다. 이후 다른 막힘 배치와 더 많은 관련 로봇으로 해결률·검사 수·전체 판단 시간을 비교한다. 전체 평균 도착 시간 최소화, 장기 대기 보호, 일반 주문의 막힘 복구 연결은 아직 남아 있다. 현재 구현은 첫 유효 완성 계획을 찾으면 종료하며 최적 시간 계획을 탐색한 것은 아니다.
