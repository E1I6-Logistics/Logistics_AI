# 이동·대기·작업 중 취소와 로봇 재사용 검증

2026-10-21. **네 가지 취소 상황에서 취소한 로봇은 복귀했고, 나머지 주문은 계속 처리됐다. 이후 새 주문 3건도 R1·R2·R3가 모두 다시 배차받아 완료했다.** 기존 관제 코드는 수정하지 않았다.

## 이번에 한 일

[앞선 시험](order-cancellation-validation-20261021.md)에서는 미배차 주문 취소와 픽업대 작업 중 취소를 확인했다. 이번에는 다음 네 경우를 같은 관제에서 이어서 실행했다.

매번 홈 N0·N1·N2에서 A 1개 주문 3건을 등록했다. 첫 번째 주문 또는 픽업 차례를 기다리는 두 번째 주문만 취소하고, 다른 두 주문의 작업·복귀 완료까지 지켜봤다. 네 시험이 끝난 뒤에는 재시작 없이 새 주문 3건을 추가했다.

| 시험 | 취소한 시점 | 확인한 결과 |
| --- | --- | --- |
| 픽업대로 이동하다 취소 | R1이 N0→N10 통로 내부를 약 30% 이동한 시점 | 통로 안에서 멈춘 위치를 출발점으로 복귀. R2·R3 주문은 완료 |
| 픽업 차례 대기 중 취소 | R2가 N1에서 N5 차례를 기다리는 시점 | R2는 이미 홈이므로 긴 복귀 이동 없이 정리. R3가 취소된 차례에 묶이지 않고 진행 |
| 작업대로 이동하다 취소 | R1이 N5→N6 통로 내부를 약 31% 이동한 시점 | 작업대 할당 해제, R1 복귀, R2·R3 주문 완료 |
| 작업대에서 취소 | R1이 N3에서 작업 중인 시점 | 작업대 할당 해제, 취소 상태 유지·복귀, R2·R3 주문 완료 |
| 취소 이후 새 주문 | 앞의 네 시험이 끝나고 새 주문 3건 등록 | R1·R2·R3 모두 다시 배차되고 작업·복귀 완료 |

이 시험까지 합쳐 미배차·픽업 대기·픽업 작업·픽업 이동·작업대 이동·작업대 작업의 여섯 취소 시점을 확인했다. 각각 한 번씩 확인한 범위이며 임의의 모든 시점·조건을 검증한 것은 아니다.

## 흐름을 쉽게 보면

```text
일반 주문 3건 등록
 → 로봇 3대 배차
 → 정한 상황에 도달했는지 실제 노드·통로 점유로 확인
 → 그 시험에서 등록한 대상 주문 하나만 취소
     ├─ 취소한 로봇: 현재 위치 유지·정지 → 기존 알고리즘으로 홈 복귀
     └─ 다른 로봇: 남은 차례·실제 점유·예약 검사 → 자기 주문 계속 처리
 → 모두 정리되면 다음 시험
 → 마지막에 새 주문 3건으로 세 로봇의 재사용 확인
```

통로 이동 중 취소 시험은 노드에 정지한 뒤 취소한 것이 아니다. `occupied_node=null`이고 실제 `occupied_edge`가 있으며, 통로 길이의 30~70% 안쪽인 상태에서 취소했다. 첫 시험은 엣지 20, 두 번째 이동 취소는 엣지 40에서 조건을 만족했다.

취소한 주문은 끝까지 `CANCELLED`로 남았다. 오래된 픽업·작업대 작업 타이머 때문에 `COMPLETED`로 바뀌는 현상은 관측하지 못했다. 작업대의 주문 할당은 취소 직후 후속 관측부터 해제된 것을 확인했고, 실제 로봇 점유는 복귀하면서 해제됐다.

## 결과

각 시간은 해당 세 주문 등록 직전부터의 경과 시간이다. ‘모두 정리’는 두 정상 주문의 작업·복귀와 취소 로봇의 복귀가 모두 끝난 시점이다.

| 시험 | 취소 시각 | 취소 로봇 복귀 확인 | 모두 정리 | 점유 관측 |
| --- | ---: | ---: | ---: | ---: |
| 픽업 이동 중 | 0.89초 | 1.96초 | 37.01초 | 226회 |
| 픽업 차례 대기 중 | 0.61초 | 0.96초 | 37.85초 | 233회 |
| 작업대 이동 중 | 11.40초 | 21.30초 | 46.28초 | 273회 |
| 작업대 작업 중 | 16.66초 | 27.89초 | 46.70초 | 276회 |
| 새 주문 3건 | 취소 없음 | 해당 없음 | 46.43초 | 272회 |

- 정상적으로 끝까지 관측한 다섯 실행: **15건 등록, 11건 완료, 4건 의도한 취소**.
- 주문 실패·복귀 오류 없음. 취소한 로봇들은 모두 `recovery_status=RETURNED`.
- 총 **1,280회**의 점유 관측에서 노드·물리 통로 중복 점유를 찾지 못했다.
- 각 실행 종료 시 픽업 대기열이 비고 작업대는 모두 FREE. 로봇도 모두 IDLE·경로 없음·목표 없음이었다.
- 이후 새 주문에는 R1·R2·R3가 모두 다시 배정됐다. 취소한 뒤 로봇이 계속 사용 불가로 남는 문제는 관측하지 못했다.

시뮬·AI에서 **A* 경로 + KEV 교통조정 선택** 설정을 유지했다. 이 15건의 정상 이동 처리에서 실제 KEV 요청·응답은 2회였고 오류 기록은 없었다. 실행 가능한 후보가 하나면 모델을 부르지 않는다. **취소 후 복귀는 기존 알고리즘 기능**이며, KEV가 막힘 해결 계획을 만든 시험은 아니다.

## 관측기 오류와 재시험을 구분한다

최초 시도에서는 시험 주문 3건 중 첫 주문을 통로 안에서 취소한 직후 관측기가 잘못 중단됐다. 취소 전 조회한 상태를 같은 반복 안에서 취소 후 상태와 비교한 관측기 오류였다. 기존 관제의 취소 처리 오류로 확인된 것은 아니다.

그 세 주문은 강제 초기화하지 않았다. 취소 1건의 정상 복귀와 뒤 주문 2건의 완료를 나중에 확인하고, 원래 위치를 복원했다. 관측기의 비교 시점을 수정한 뒤 위의 네 취소 시험과 새 주문 시험을 처음부터 다시 실행했다. 최초 시도의 짧은 관측 기록은 위의 1,280회에 포함하지 않는다.

따라서 이번 작업 전체에서 추가된 주문 이력은 재시험 15건과 최초 시도 3건, 합계 18건이다. 최초 시도의 별도 기록은 `logs/order-cancellation-runs/20261021-followup/`에 보관했다. `report.json`의 실패는 관측기 중단을 뜻하며, 이후 `settled-after-observer-error.json`에 관제 주문의 최종 상태를 남겼다.

## 원래 상태 보존

이번 작업 직전 이력은 142건이었다. 최초 시도 3건을 보존해 재시험 시작 시 145건, 재시험 15건을 더해 최종 **160건: 완료 153건·취소 7건**이다. 기존 주문은 삭제하거나 취소하지 않았고, 각 원래 주문의 내용이 그대로인지도 대조했다.

시험이 끝난 뒤 원래 시뮬·AI 모드와 A*·KEV 설정, 로봇의 N0·N11·N10 위치·자세·배터리, 기존 완료 시나리오 상태를 복원했다. 원래 상태에서 달라진 것은 시험 주문 이력이 추가된 점이다. 관제 실행 코드는 수정하지 않았으며 실행 전 보관한 코드 해시와 마지막 원본이 같은지 확인했다.

## 남은 범위

이번 관측은 약 0.075초 대기와 API 조회 시간을 합친 간격으로 수집했다. 모든 순간의 안전이나 실기체 안전을 증명하지 않는다. 전체 자동 검사 묶음을 이번에 새로 실행한 결과도 아니다.

다음은 별도 조건이 필요한 검증이다.

- 로봇 연결 끊김과 위치 정보가 오래된 상황에서의 차단·복구.
- 복귀 경로가 오래 막혔을 때 시간 한도 후 안전하게 중단하고 운영자에게 알리는 동작.
- 모델 응답 지연·오류 또는 예약 경쟁 중 취소의 실제 서버 반복 시험.
- 실제로 물품을 집은 뒤 취소했을 때 물품을 어디에 반납하고 수량을 어떻게 정산할지에 대한 운영 규칙.
- 별도 다중 양보 탐색을 일반 주문의 자동 복구로 연결할지에 대한 설계·검증. 현재 이 연결은 하지 않았다.
