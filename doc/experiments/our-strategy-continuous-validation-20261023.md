# 우리 KEV 전략 순서 방식: 연속 주문 점검

2026-10-23. 사용자가 jhlee와의 추가 비교를 중지하고 우리 방식을 계속 진행하도록 결정했다. 기존 비교·실패 기록은 보존한다. 이 문서는 우리 방식의 동작 점검이며 jhlee 대비 우수성 평가가 아니다.

## 오늘의 완료 범위

시뮬·AI에서 A* 경로 생성 → 새 이동 요청의 KEV 전략 순서 제안 → 경로 생성·코드 예약 검사 → 코드의 최종 선택 → 최신 상태 확인·실행이라는 현재 연결을 유지한다. 정지 배치의 전체 로봇 탐색, 여러 대 양보 자동 복구, 실기체 연결은 추가하지 않는다.

목표는 기존 자동 주문 공급으로 여러 주문을 계속 처리하고, 공급을 멈춘 뒤 접수 주문과 홈 복귀가 끝나는지 확인하는 것이다. 실패·복귀 오류·점유 중복·장기 무진행을 숨기지 않고 기록한다. 무기한 무고장과 AI 성능 우수성까지 확인하는 시험은 아니다.

## 역할 분리와 AI의 기여

경로 생성부가 기본 경로를 제공하고 교통조정부가 그 경로와 관제 상태를 바탕으로 통행을 조정한다는 책임 분리는 우리 프로젝트의 분담을 설명하기 좋다. 그러나 경로 생성 단계에서 다른 로봇의 점유를 피하는 방식도 충돌을 줄이는 설계다. 역할 분리만으로 우리 방식이 MAPF의 본질에 더 가깝거나 더 우수하다고 판단하지 않는다.

현재 KEV는 새 요청의 기본 경로 유지·공유 자원 회피 전략 순서를 제안한다. 코드는 계획을 생성·검사하고 유효 경로 중 예상 시간이 짧은 경로를 선택한다. KEV가 더 좋은 계획을 찾거나 생성·검사량을 줄였다는 성능 근거는 아직 없다. 이번 연속 주문 정상 동작 확인과 AI 기여 검증을 구분한다.

## 실행 조건

- 기존 화면 8000·5173의 모드·주문·시나리오는 조회만 한다. 별도 127.0.0.1:8032 시뮬 서버에만 주문을 공급하고 종료 시 이 서버만 정리한다.
- 선택은 `KEV_STRATEGY_ORDER`, 기본 경로·우회는 기존 A*, 모델은 8012의 동일 CUDA 0.8B 서버다. 시뮬 속도 0.2m/s·작업 1.5초·예약 마진 0.2초.
- 기존 `continuous_ai_orders`를 그대로 실행한다. seed 42, 최초 3건, 이후 5초 간격, PENDING 상한 3건, 주문당 물품 1~5개.
- 12건 접수 시 새 공급을 중지하고 접수한 주문은 계속 처리한다. 관측 한도 300초, 도구 상한 315초. 실패·복귀 오류·점유 중복이 생기면 새 공급을 멈추고 원문을 보존한다.
- 관측기는 위치·상태·주문 단계의 변화가 45초간 없으면 무진행으로 표시한다. 이것만으로 교착의 원인을 확정하지 않는다.
- 소스·지도·시작 상태·모델 정보·원문 추론·보류·최종 주문을 보존한다. 기존 제품 코드·주문 공급 규칙은 이번 점검을 위해 변경하지 않는다.

실행은 기존 [자동 주문 관측 도구](../../tests/random_order_observer.py), [공급기](../../backend/simulation/order_stream_scenario.py), [시뮬 전용 진입점](../../backend/simulation/order_traffic_preview.py)을 사용한다. 격리 실행·소스 사본·종료 확인은 `logs/our-strategy-validation/20261023-continuous-once/`에 기록한다. 관측 도구의 개별 출력 폴더는 그 안의 `run.json`에 보존한다.

약 0.5초 간격의 관측 시간이며 표본 점유 확인은 지속 시간의 안전 증명이 아니다. seed 하나·설정 하나의 시험으로 장시간 안정성·정상 상태 처리량·다른 방식 대비 우수성을 확정하지 않는다. 작업 끝과 홈 복귀를 구분하고, 33개/113.10초를 지속 주문 처리량이라고 부르지 않는다. 이번 결과는 현재 우리 방식이 이 연속 주문을 끝까지 처리했다는 근거다.

**당시 공급 중지 상태의 통계 표시 문제:** 이 시험 당시에는 공급 통계가 중지 때의 값에 머물렀다. 중지 시점의 완료 수는 7건이지만 이후 실제 주문은 12건 모두 완료했다. 주문 완료 여부는 최종 `/api/orders`와 로봇 상태로 확인했다. 이 표시 갱신 문제를 주문 누락으로 세거나, 공급기의 `completed` 상태를 모든 주문 완료로 해석하지 않는다. 원래 시험 결과와 로그는 그대로 보존했다.

후속 [공급 중지 후 완료·복귀 표시 수정](order-stream-stop-status-fix-20261023.md)으로 상태 조회 시 해당 공급 주문의 최신 통계를 보여주도록 바꿨다. 저장된 12건 결과의 API 재확인에서 완료 12건·복귀 중 0건을 확인하고 화면용 백엔드에도 반영했다. 이 후속 확인은 새 12건 운행 시험과 구분한다.

직전 관련 코드 검사 270개 통과는 별도 기록이며 이번 점검에서는 제품 코드를 수정하지 않아 같은 검사를 다시 반복하지 않았다.

## 직접 볼 때

현재 화면의 시뮬·AI에서 일반 주문 교통조정을 **새 방식 · KEV가 전략 순서 제안**으로 맞춘다. 기본 경로는 A* 설정을 확인한다. 진행 주문·복귀·다른 시나리오가 있으면 정책을 바꾸지 않는다.

시나리오 **일반 주문 · 계속 주문 넣기**를 실행하면 주문이 공급된다. **주문 공급 중지**는 신규 등록만 멈추며, 접수한 주문은 계속 처리한다. 자동 공급을 무기한 켜둘 필요는 없고 완료·실패·복귀 상태를 함께 본다. 기존 관제의 비상정지와 공급 중지는 용도가 다르다.
